Partners and partner groups

A partner is a company you exchange EDI files with, and your own company is a partner too. You enter partners in Bots when you want a translation, a route, a confirm rule or a mail address to depend on who sends or receives a file. Partner groups let you treat several partners the same way.

In plain words

Every file in Bots carries two labels: who sent it (frompartner) and who should get it (topartner). Bots reads those labels from the file itself, from the route, from a mail address, or your mapping sets them. The partner list in the web interface is the address book that gives those labels a meaning: a name, mail addresses, groups and some free fields.

How it works

A partner is identified by its partner ID (idpartner), for example PARTNERA. Bots stores the IDs of the sender and the receiver with every file and every message it handles (in the fields frompartner and topartner of its transaction table). These IDs are plain text. Bots does not check that a partner record exists for them: an envelope, for example, is made from the IDs alone. A partner record is needed where Bots looks the partner up:

  • choosing a translation for a partner or a partner group;
  • the outgoing filters of a route (Frompartner tochannel, Topartner tochannel), which also accept a group;
  • confirm rules for one sender or receiver;
  • mail: the partner of a received mail is found by its address, and the address of an outgoing mail is found by the partner (see Mail channels);
  • a mapping that reads partner data with transform.partnerlookup() (see Mapping functions).

How Bots finds the partners of a file

The partner IDs of a file are filled in steps. A later step overwrites an earlier one, but only with a value that is not empty.

  1. Mail address. A mail channel (pop3, imap4 and their variants) looks up the From address to find the frompartner and the To addresses to find the topartner. Bots searches, without regard to upper or lower case: first the email address per channel entries of active partners for this channel, then the Mail field of the active partners, then their Cc field. An address has to be equal to one of the addresses in the field. An unknown address is an error, unless the channel has No check from-address or No check to-address ticked; then that partner stays empty.
  2. Route. If the route part has a Frompartner or Topartner, every file received by that route part gets it. Use this when a channel only receives files of one partner (for example an SFTP folder of PartnerA).
  3. Envelope of the file. While Bots reads (parses) the file, the QUERIES of the grammar pick the IDs out of the file, for example the sender and receiver in the EDIFACT UNB segment or in the X12 ISA/GS segments. These are set per message. See Records and structure.
  4. Mapping. A mapping can set the partners of the outgoing message: out.ta_info['frompartner'] = 'MYCOMPANY', out.ta_info['topartner'] = 'PARTNERA'. Without this, the outgoing message gets the partners of the incoming message.

Partner groups

A partner group is a partner record with isgroup set. You make it under Partnergroups and you put partners in it from the partner itself (Is in groups). A partner can be in several groups. Bots uses groups in two places:

  • Translations: a translation with the group Retailers as frompartner (or topartner) is used for messages of every partner that is a member of Retailers.
  • Route filters for the outgoing channel: Frompartner tochannel and Topartner tochannel accept a partner or a group.

Groups are not used in confirm rules and in the Frompartner/Topartner of a route: those fields only offer partners. Bots only follows direct membership: a group inside a group does not make its partners members of the outer group.

What "active" does

Only active partners are found by mail address and only active partners give a mail address for outgoing mail. Active partners are also the ones offered in the selection lists of the report screens. The translation lookup and the route filters do not look at Active: an inactive partner still gets its partner-specific translation. The Startdate and Enddate fields are for your information only; Bots does not use them.

Partner-specific syntax

Some partners want their envelope or file a little different: another ID qualifier, the test indicator, another separator. For this you write a small Python file with a syntax dictionary in usersys/partners/<editype>/<partner ID>.py. When Bots writes an outgoing message or its envelope, it reads the grammar, then the syntax file of the frompartner, then that of the topartner; the topartner file wins. Values that the mapping set in out.ta_info win over all of these. See Envelopes for the settings that are used most.

How to add a partner

  1. Open the partner list. Click Configuration → Partners → Add.
  2. Tick Active. A new partner is not active by default.
  3. Type the partner ID in Partner identification, for example PARTNERA. Use exactly the ID that is in the files (for example the UNB sender of PartnerA), because Bots compares the text as it is. Use letters, digits and _ only if you want a partner-specific syntax file: the ID becomes a Python file name.
  4. Type a name in Name, for example PartnerA. The name is only shown to you.
  5. Type the mail addresses if you exchange mail with this partner: Mail orders@partnera.example; more addresses separated by commas. Cc gets the copy addresses.
  6. Optionally open Address, Is in groups and User defined and fill what you need.
  7. Click Save. The partner is in the list as PARTNERA (PartnerA).

Add your own company in the same way, for example MYCOMPANY, if a translation, route filter or mail depends on it.

How to make a partner group

  1. Add the group. Click Configuration → Partnergroups → Add.
  2. Fill in the group. Tick Active, type the ID Retailers and a name, and click Save.
  3. Open a member. Click Configuration → Partners and click PARTNERA.
  4. Add the group to the partner. Open Is in groups, select Retailers in the left list and click the arrow to move it to the right list.
  5. Click Save. In the partner list you can now filter on the group (filter By group on the right).

How to give a partner another mail address for one channel

Use this when PartnerA sends orders from one address and wants invoices at another address, each via its own mail channel.

  1. Open the partner. Configuration → Partners → PARTNERA.
  2. Go to the table Email address per channel at the bottom of the page.
  3. Choose the channel, for example mail_in, and type the address in Mail (required) and, if needed, Cc.
  4. Click Save. For that channel Bots now uses this address first, both to recognise incoming mail and to address outgoing mail. For other channels it uses the Mail field of the partner.

How to give one partner other envelope settings

  1. Make the file usersys/partners/x12/PARTNERA.py (for EDIFACT: usersys/partners/edifact/PARTNERA.py). The folder exists in a new usersys; the file name is the partner ID plus .py.
  2. Put the settings in it, for example the ID qualifiers and the test indicator: 
    syntax = {
    'ISA05': 'ZZ',   # qualifier of the sender ID (MYCOMPANY)
    'ISA07': 'ZZ',   # qualifier of the receiver ID (PARTNERA)
    'ISA15': 'T',    # T = test, P = production
}
  3. Run the route. With the log level at DEBUG the log shows Partner syntax imported "…PARTNERA.py".

How to use partner data in a mapping

The fields attr1 to attr5 are free fields for your own data, for example the customer number of PartnerA in your ERP system. Read them in a mapping:

from bots import transform

def main(inn, out):
    erp_customer = transform.partnerlookup(inn.ta_info['frompartner'], 'attr1')
    out.put({'BOTSID': 'HEADER', 'customer': erp_customer})

partnerlookup(value, field, search_field='idpartner', safe=False) searches the partner whose search_field equals value and returns field. With safe=True it returns value when nothing is found, with safe=None it returns None; otherwise it raises an error. An empty field counts as not found.

Translations

A translation rule tells Bots which mapping script turns a message of one type into a message of another type. You need one for every kind of message a route translates, and more when partners need different mappings.

In plain words

When Bots has read a message, it asks: "what is this, who sent it, who gets it?" and looks in the translation list for the best fitting line. That line names the mapping (the recipe) and what the result must be. No fitting line means the message stops with an error.

How it works

In a route part with Translate set to Translate, Bots reads each received file with its grammar and splits it into messages. For every message it knows five things: the editype (for example x12), the messagetype (for example 850004010), the frompartner, the topartner and the alt value (an extra label, empty by default). With these it searches the active translation rules:

How Bots chooses a translation

A rule matches a message when all of these are true:

  1. the rule is Active;
  2. Fromeditype and Frommessagetype are equal to those of the message (exact text);
  3. Alt of the rule is empty, or equal to the alt of the message;
  4. Frompartner of the rule is empty, or equal to the frompartner of the message, or a group of which the frompartner is a direct member;
  5. the same for Topartner.

When several rules match, Bots takes the first one in this order:

  1. a rule with an Alt before a rule without (alt sorted from high to low);
  2. then a rule with a frompartner before a rule without; among rules with a frompartner, sorted by the partner ID (as text, character by character, so upper-case letters come before lower-case letters);
  3. then the same for the topartner.
Watch out

A rule for one partner does not automatically win over a rule for a group. If PartnerA (PARTNERA) is in group Retailers and there is a rule for each, the one with the ID that sorts first wins (PARTNERA before Retailers). Give groups and partners IDs that sort the way you want, or avoid overlapping rules.

changed in 4.0 The order is made by Bots itself, the same on every database (as SQLite and Bots 3 on SQLite sort). In Bots 3 on another database the order could depend on the database.

When no rule matches, Bots calls the function gettranslation(idroute, message) in usersys/mappings/translation.py if that file exists. It must return (mapping script, toeditype, tomessagetype), or None values when it has no answer. When still nothing is found, the message gets the error Translation not found for ….

What happens with the chosen rule

  1. Bots imports the mapping usersys/mappings/<fromeditype>/<mapping script>.py. A dot in the name is a sub-folder: partnera.orders_x12_to_csv is usersys/mappings/x12/partnera/orders_x12_to_csv.py.
  2. It makes an empty outgoing message of Toeditype / Tomessagetype. The outgoing message gets the partners, test indicator and alt of the incoming message and a new message number (counter messagecounter, see Counters).
  3. It runs main(inn, out) of the mapping. See Mappings.
  4. What main() returns decides what comes next (see below). When it returns nothing, the outgoing message is written with the grammar usersys/grammars/<toeditype>/<tomessagetype>.py.

Chained translations with alt

One incoming message can give several outgoing messages: the mapping returns a value and Bots looks up a translation again for the same message, now with that value as alt.

Alt from the route

A route part has its own field Alternative translation. Every file received by that route part gets this alt. Use it when the same message type arrives on two routes and must be translated differently: route orders_in with alt shop uses the rule with alt shop.

How to add a translation

  1. Put the grammar and mapping files in usersys. For example usersys/grammars/x12/850004010.py, usersys/grammars/csv/orders_erp.py and usersys/mappings/x12/orders_x12_to_csv.py.
  2. Open the form. Configuration → Translations → Add.
  3. Tick Active.
  4. Choose Fromeditype x12 and type or choose Frommessagetype 850004010. The form offers the grammars it finds in usersys.
  5. Choose Mapping Script orders_x12_to_csv (without .py).
  6. Choose Toeditype csv and Tomessagetype orders_erp.
  7. Leave Alt, Frompartner and Topartner empty for a rule that is valid for everybody.
  8. Click Save. In the list, the mapping and message types are links; a red cross in front means the file is not found in usersys.

How to use another mapping for one partner or a group

  1. Keep the general rule (no partners) for all other partners.
  2. Add a second rule with the same Fromeditype and Frommessagetype, the special mapping (for example orders_x12_to_csv_partnera) and, under Multiple translations per editype/messagetype, Frompartner PARTNERA (or the group Retailers).
  3. Save and test. Open the result in Outgoing: the column with the mapping name shows which mapping was used.

How to make two outputs from one message

  1. End the first mapping with a return value. 
    def main(inn, out):
    # ... map the order to the ERP file ...
    return 'order_confirmation'   # next: translate the same order again with this alt
  2. Add a second rule with the same from-editype and messagetype, Alt order_confirmation, and the mapping and to-messagetype of the second output.
  3. Make the second mapping return nothing, so the chain ends.
  4. Send both outputs to their channels with the outgoing filters of the route (Toeditype, Tomessagetype); see Routes.

Confirm rules

Confirm rules decide when Bots sends an acknowledgement for a received file and when it expects one for a sent file. You need them for X12 997, EDIFACT CONTRL and mail MDN.

In plain words

An acknowledgement is a receipt: "I got your file". Confirm rules are your instructions to Bots: "send a receipt to everyone who sends X12, except PartnerC", or "remember that we want a receipt from PartnerA". How the receipts themselves are made and checked is in Acknowledgements.

How it works

Each rule has a confirm type (what kind of acknowledgement, and whether you send it or ask for it) and a rule type (to which files it applies). At the moment an acknowledgement could be made or asked, Bots checks all active rules of that confirm type:

  1. It starts with "no".
  2. It goes through the positive rules, then the negative rules (Negativerule ticked).
  3. Each rule that matches the file sets the answer: a positive rule to "yes", a negative rule to "no". The last matching rule decides.

So you include first and then exclude: rule 1 "all", rule 2 negative "frompartner PARTNERC" gives an acknowledgement to everyone except PartnerC.

How to send a 997 to all X12 partners except one

  1. Open the form. Configuration → Confirmrules → Add.
  2. Make the positive rule. Tick Active, choose Confirmtype send a x12 confirmation (997) when receiving and Ruletype Confirm all. Click Save and add another.
  3. Make the negative rule. Tick Active and Negativerule, the same confirm type, Ruletype Frompartner, Frompartner PARTNERC. Click Save.
  4. Send the 997. The 997 is made in the route that received the file; add a route part that sends it (see Acknowledgements).

How to send a 997 only when the partner asks for it

  1. Add a rule with Confirmtype send a x12 confirmation (997) when receiving and Ruletype Confirm asked.
  2. Save. A 997 is now made only for files whose ISA14 is 1 (acknowledgement requested).

How to expect a CONTRL from PartnerB

  1. Add a rule with Confirmtype ask an edifact confirmation (CONTRL) when sending, Ruletype Topartner, Topartner PARTNERB.
  2. Ask the partner in the envelope too. The rule only makes Bots remember that a CONTRL is expected. To ask for it in the file, set 'UNB.0031': '1' in the EDIFACT syntax for PartnerB (see Envelopes).
  3. Check. After the next run, All runs → Confirmations → Unconfirmed lists the interchange.

Code lists

Code lists (in the web interface: user codes) are tables of code pairs that mappings use to translate one code into another, for example your unit codes into the unit codes of an EDIFACT message. You keep them in the web interface, so you can change a code without changing a mapping.

In plain words

A code list is a two-column translation table: on the left the code as you know it, on the right the code the other side uses. A mapping asks "what is the right-hand code for PCS in the list units?" and gets PCE. Up to eight extra columns can hold more data per code.

How it works

There are two tables:

  • User code types (ccodetrigger): the names of your lists, for example units or article_numbers.
  • User codes (ccode): the entries. Each entry belongs to one list and has a leftcode, a rightcode and attr1 to attr8.

A mapping reads the lists with functions of transform:

FunctionWhat it returns
ccode(ccodeid, leftcode, field='rightcode', safe=False)The field of the entry with this leftcode.
reverse_ccode(ccodeid, rightcode, field='leftcode', safe=False)The field of the entry with this rightcode (lookup in the other direction).
getcodeset(ccodeid, leftcode, field='rightcode')A list with the field of all entries with this leftcode, in the order they were added. Empty list when there are none.
safe_ccode(), safe_reverse_ccode(); old names codetconversion, safecodetconversion, rcodetconversion, safercodetconversionDeprecated; kept so old mappings work. Use ccode(..., safe=True).

field can be 'leftcode', 'rightcode' or 'attr1' to 'attr8'. safe decides what happens when the code is not in the list: False raises an error (the message gets an error), True returns the code you gave, None returns None. When a code occurs more than once, ccode returns one of the entries; use getcodeset to get all.

from bots import transform

def main(inn, out):
    unit = inn.get({'BOTSID': 'ST'}, {'BOTSID': 'PO1', 'PO103': None})
    out.put({'BOTSID': 'LINE', 'unit': transform.ccode('units', unit)})               # error if unknown
    text = transform.ccode('units', unit, field='attr1', safe=None)                  # None if unknown
    ours = transform.reverse_ccode('units', 'PCE', safe=True)                        # 'PCE' if unknown

The list name shortcut is special: the web interface uses it for the shortcuts menu (see Web interface). Do not use that name for your own codes.

How to make a code list

  1. Add the list name. Configuration → User Code types → Add. Type units in Type of user code and a description. Click Save.
  2. Add an entry. Configuration → User Codes list → Add. Choose Type of user code units, type Leftcode PCS and Rightcode PCE, optionally Attr1 piece.
  3. Click Save and add another for the next entry, or Save when done. The list shows all entries; filter on the list name on the right.
  4. Use the list in a mapping as shown above.

How to copy code lists to another environment

Move code lists from one environment to another with a plugin:

  1. Select the entries. In User Codes list, filter on the list and tick the entries (or the box in the header for all on the page).
  2. Choose the action Make bots plugin with selected entries and click Go (superusers only). Do the same in User Code types for the list name.
  3. Read the plugin in the other environment with SysTasks → Plugins → Read plugin. See Plugins.
Tip

For large lists that come from another system, a small Python script that writes the rows with Django, or a database tool on the table ccode, is faster. Make a backup first.

Counters

Bots numbers interchanges, messages and file names with counters that it keeps in its database. You look at them when a partner reports a wrong or double control number, and you set them when you move to another system.

In plain words

A counter is a named number that goes up by one every time Bots uses it, like a ticket machine. Partners check some of these numbers (the interchange control numbers) to find missing or double files, so they must never go back.

How it works

All counters are rows in the table uniek: a name (domein) and the last number used (nummer). When Bots needs a number, it adds 1 to the row and uses the result. A counter that does not exist yet is made with 1. The database locks the row while it counts, so two engines running at the same time never get the same number. After 2147483647 the counter starts again at 0.

The counters Bots makes itself:

Interchange control numbers per sender or per receiver

By default there is one interchange counter per sender ID, so all your partners together see one running number from MYCOMPANY. Many partners prefer that the numbers they receive have no gaps. Then set in bots.ini:

[settings]
interchangecontrolperpartner = True

Now each sender/receiver pair has its own counter, for example isacounter_MYCOMPANY_PARTNERA.

changed in 4.0 Bots 3 named the counter after the partner ID (isacounter_MYCOMPANY, or after the topartner with interchangecontrolperpartner). Bots 4 names it after the IDs that are written in the envelope. When a counter with the new name is used for the first time, it continues from the counter with the Bots 3 name (if that exists), so the numbers do not start at 1 again.

Counters in mappings

  • transform.unique('my_counter'): the next number of a counter in the database, as text.
  • transform.unique('my_counter', updatewith=500): returns the current number and sets the counter to 500.
  • transform.unique_runcounter('my_counter'): a counter that starts at 1 in every run, not stored.
  • transform.checkunique('PARTNERA_orders', received_number): checks that a number received from a partner is exactly 1 higher than the previous one. Returns True or False; on False the counter is not moved.

How to view or change a counter

  1. Open the counters. SysTasks → View/edit counters (superusers).
  2. Find the counter. Type part of the name in the search box, for example isacounter.
  3. Click the counter name to open it.
  4. Change Last used number and click Save. The next number Bots uses is this number plus 1.
Watch out

Do not lower an interchange counter that is in use: partners reject or ignore a control number they already received. Change counters only while no engine is running.

You cannot add counters here (Bots makes them when it needs them). You can delete a counter, except messagecounter and bots_cleanup_day; a deleted counter starts again at 1 (an interchange counter continues from the Bots 3 counter if that still exists).

How to keep the numbers right when you switch systems

  1. Moving from Bots 3 to Bots 4: the counters move with the database (bots-portenv / bots-updatedb) and continue where Bots 3 stopped. See Upgrade from Bots 3.
  2. After a test period in which the new system did not send to partners, port the database again just before the switch, so the counters are current.
  3. On the first production run, check the control number of the first interchange per partner in Outgoing.
  4. If you go back to the old system, first copy the counters of the new system (table uniek, or by hand in View/edit counters) into the old one. Otherwise a partner gets a control number twice.
  5. Moving to another database (for example SQLite to PostgreSQL): copy the table uniek with the rest of the data.

Envelopes

An envelope is the header and trailer around one or more EDI messages: the UNB/UNZ of EDIFACT, the ISA/GS/GE/IEA of X12, the STX/END of TRADACOMS. Bots makes the envelope of outgoing files after translation, and can put many messages in one envelope.

In plain words

Your mapping writes the letters; the envelope step puts them in an envelope with the address of the sender and the receiver and a running number. Letters for the same receiver can go in one envelope together (that is merging).

How it works

After a mapping, the outgoing message is stored on its own, with the information Bots needs for the envelope: editype, messagetype, the envelope to use, merge yes/no, frompartner, topartner, test indicator, character set, and envelope data the mapping set. These come from the grammar syntax, the partner syntax and the mapping. Then, in the same route part, the envelope step runs:

  1. Messages with merge off each get their own envelope: one message, one file.
  2. Messages with merge on are grouped. Messages go into the same file when they have the same editype, messagetype, envelope, frompartner, topartner, test indicator, character set, envelope criterion (rsrv3) and envelope data from the mapping. Only messages of the same route and the same run are merged.
  3. For each file Bots chooses the envelope: no envelope when the envelope name is empty; else a user envelope script usersys/envelopescripts/<editype>/<envelope>.py with a class of that name; else the built-in envelope of the editype.
  4. The envelope is written: header, the messages, trailer. The interchange gets a control number from a counter (see Counters).

changed in 4.0 Messages for which the mapping set different envelope data are no longer merged into one interchange; the groups are numbered in the same order on every database.

Acknowledgements

An acknowledgement is a technical receipt for an EDI file: the X12 997, the EDIFACT CONTRL and, for mail, the MDN (message disposition notification). Bots can make them for files it receives and can keep track of the ones it expects for files it sends.

In plain words

When PartnerA sends you an order, PartnerA wants to know that it arrived: Bots sends back a short "received, OK" or "received, with errors" file. When you send an invoice, you want the same from them: Bots notes that a receipt is due and shows in a list which receipts came and which are still missing.

How it works

There are three tasks. Confirm rules switch each one on.

Sending a 997 (X12)

  1. After Bots translated a received X12 file, it checks the rules of type send-x12-997 for each message (ST), per group (GS). Groups with GS01 FA (a 997 or 999) are skipped.
  2. For each group with at least one matching message it makes one 997, with an AK1 for the group, an AK2/AK5 per acknowledged message and an AK9. The code is A (accepted) when the file was translated without error and R (rejected) when there was an error. Messages that do not match a rule are left out.
  3. The 997 goes from the receiver to the sender: frompartner is GS03, topartner is GS02 of the received group. Its ST02 comes from the counter messagecounter (at least 4 digits).
  4. The 997 is written with grammar 997004010 (file usersys/grammars/x12/997004010.py, which comes with the X12 grammars). new in 4.0 With [settings] x12_997_version_as_received = True in bots.ini Bots uses the version of the received GS08 when that grammar exists (for example 997004060), then the first 6 characters of GS08, then 997004010.
  5. The 997 is an outgoing message of the same route. It is enveloped (ISA/GS) like other X12 messages and goes to the outgoing channel of the route part whose filters let it pass.

A translation with fromeditype x12, frommessagetype 997 and frompartner = the receiver (your ID) replaces this: Bots runs its mapping with main(inn, out, routedict, ta_fromfile), where inn is the received GS group, and writes it with the to-messagetype of the translation. A mapping with only a function change(inn, out, routedict, ta_fromfile) lets Bots make the 997 and then changes it.

Bots does not make 999 acknowledgements. It does recognise a received 999: no 997 is made for it, and no 997 is asked for an outgoing 997 or 999.

Sending a CONTRL (EDIFACT)

  1. After translating a received EDIFACT file, Bots checks the rules of type send-edifact-CONTRL for each message (UNH), per interchange (UNB). CONTRL and APERAK messages are not acknowledged.
  2. For each interchange with a matching message it makes one CONTRL with a UCI (the UNB reference, sender and receiver of the received interchange) and a UCM per acknowledged message. The code is 7 (acknowledged) or 4 (rejected, when there was an error).
  3. It is written with grammar CONTRL22UNEAN002 (file usersys/grammars/edifact/CONTRL22UNEAN002.py), unless a translation with frommessagetype CONTRL gives a mapping and messagetype, as for the 997.
  4. It goes from the receiver to the sender (the UNB IDs, or the IDs the QUERIES of the envelope grammar found), and is enveloped and sent like the 997.

Asking for a 997 or CONTRL

When the outgoing interchanges of a route part are given to its outgoing channel, Bots checks the rules ask-x12-997 or ask-edifact-CONTRL. For a match it marks the interchange as "confirmation asked" (not for an outgoing 997, 999, CONTRL or APERAK). The interchange then appears under All runs → Confirmations as unconfirmed.

The rule does not change the file. To ask the partner in the file itself, use the envelope: ISA14 is 1 by default (set 'ISA14': '0' to not ask), and for EDIFACT set 'UNB.0031': '1'. See Envelopes.

How a received 997 or CONTRL is matched

Bots does not do this on its own for 997 and CONTRL: you need a translation for the received acknowledgement with a mapping that marks the sent interchange as confirmed. The interchange Bots asked a confirmation for is stored with:

  • reference: the interchange control number (ISA13 without leading zeros, which is also GS06; or UNB 0020);
  • status: 400 (merged, transform.MERGED);
  • confirmasked: true, confirmtype: ask-x12-997 or ask-edifact-CONTRL.

The 997 that comes back holds that number in AK102 (group control number); a CONTRL holds it in UCI 0020. The mapping sets confirmed and confirmidta (the number of the received file):

# usersys/mappings/x12/acks_997_in.py
from bots import transform

def main(inn, out):
    reference = inn.get({'BOTSID': 'ST'}, {'BOTSID': 'AK1', 'AK102': None})
    status = inn.get({'BOTSID': 'ST'}, {'BOTSID': 'AK9', 'AK901': None})
    if reference and status in ('A', 'E'):            # accepted, or accepted with errors
        transform.changeq(
            """UPDATE ta
               SET confirmed=%(confirmed)s, confirmidta=%(confirmidta)s
               WHERE reference=%(reference)s AND status=%(status)s
               AND confirmasked=%(confirmasked)s AND confirmtype=%(confirmtype)s""",
            {'confirmed': True,
             'confirmidta': inn.ta_info['idta_fromfile'],
             'reference': str(int(reference)),         # without leading zeros
             'status': transform.MERGED,
             'confirmasked': True,
             'confirmtype': 'ask-x12-997'})
    out.ta_info['statust'] = transform.DONE           # no output file for the 997

For a CONTRL read inn.get({'BOTSID': 'UNH'}, {'BOTSID': 'UCI', '0020': None}) and '0083' (7 = OK) and use 'ask-edifact-CONTRL'. The mpaths depend on your 997 and CONTRL grammars; check them with the grammar. This example is a starting point, test it with your own files.

Mail receipts (MDN)

  • Ask (ask-email-MDN): an outgoing mail gets the header Disposition-Notification-To with the sender address, and is listed as waiting for confirmation, with its Message-ID as reference.
  • Receive: a mail of type multipart/report that comes in on a mail channel is read as an MDN. Its Original-Message-ID is matched with the sent mail, which is marked confirmed. No mapping is needed. The incoming channel must accept the sender address (see Partners).
  • Send (send-email-MDN): when a received mail has Disposition-Notification-To and a rule matches, Bots makes an MDN (Return Receipt (displayed) - <subject>) with editype email-confirmation, from the address the mail was sent to, to the address that asked. A route part with an outgoing mail channel (smtp) sends it.

The confirmations screen

All runs → Confirmations lists every file for which a confirmation was asked or sent. Sub-menus: Confirmed, Unconfirmed, Manual confirm (confirmed by hand), Pending … (waiting), and Select confirmations to filter on date, partner, confirm type and more. For an asked confirmation that did not come, a user with the right to change transactions can confirm it by hand (confirm action); Bots then stores -1 as the confirming file.

How to send 997s for received orders

  1. Have a working route orders_in that receives and translates X12 850 from PartnerA (part 1, for example to erp_orders_out).
  2. Check the grammar usersys/grammars/x12/997004010.py exists.
  3. Add the confirm rule send-x12-997, Ruletype Route, Route orders_in (see Confirm rules).
  4. Limit part 1 to the order output. In route part 1 set under Filtering for outchannel Toeditype csv (the editype of your ERP file), so the 997 does not go to the ERP folder.
  5. Add route part 2 with the same Idroute orders_in, Sequence 2, no incoming channel, Translate Nothing, outgoing channel partnera_sftp_out, filter Toeditype x12 and Tomessagetype 997004010.
  6. Run and check. All runs → Confirmations shows the order file with a confirmation sent; Outgoing shows the 997 to PartnerA.

How to track 997s for your invoices

  1. Add the confirm rule ask-x12-997, Ruletype Route, Route invoices_out.
  2. Make the receiving side. A route acks_in that receives the 997s, and a translation x12 / 997004010 with the mapping acks_997_in shown above (any to-editype and to-messagetype that exist, for example csv and a small grammar; the mapping discards the output).
  3. Run invoices_out. The interchange is listed under Confirmations → Unconfirmed.
  4. Run acks_in after the partner sent the 997. The interchange moves to Confirmed, with a link to the 997.

How to send a CONTRL

  1. Check the grammar usersys/grammars/edifact/CONTRL22UNEAN002.py exists, or add a translation edifact / CONTRL with your own mapping and CONTRL messagetype.
  2. Add the confirm rule send-edifact-CONTRL with the rule type you want.
  3. Add a route part that sends editype edifact / messagetype CONTRL22UNEAN002 to the partner, as for the 997.

How to work with mail receipts

  1. To ask: add rule ask-email-MDN for the outgoing mail channel. Receive the answers on a mail channel of a route that runs regularly; the MDN needs no translation.
  2. To send: add rule send-email-MDN for the incoming mail channel, and a route part with an smtp channel and filter Toeditype email-confirmation.
