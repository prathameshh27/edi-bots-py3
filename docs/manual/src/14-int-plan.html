Planning an integration

A new partner rarely sends a finished design. You get a request such as "we want to send you orders as X12 850 over SFTP, and we expect 997, 855, 856 and 810 back". This page shows how to turn such a request into a design for Bots: what to ask the partner, which routes, channels, grammars, mappings, translations, partners, confirm rules and counters you need, how to name them, and how to bring the partner live. The tutorials after this page build such designs step by step.

In plain words

Before you click anything in Bots, write down what goes where: which documents, in which direction, over which connection, in which format, with which receipts. Then give every piece a clear name. With that list, setting up Bots is a matter of typing it in, and the partner's test is a check of the list, not a search for what you forgot.

What you will build

The example on this page is a retailer, PartnerA, that buys from MyCompany. PartnerA's request:

  • PartnerA sends purchase orders as X12 850, version 004010, by putting files on an SFTP server.
  • For every order file PartnerA expects a 997 (functional acknowledgement: "file received and readable").
  • For every order PartnerA expects an 855 (order response), an 856 (ship notice) when the goods leave, and an 810 (invoice).
  • PartnerA sends a 997 back for each 855, 856 and 810.

At MyCompany the ERP system reads orders from a folder as csv files and writes order responses, ship notices and invoices as csv files to other folders. Part 1: Collect the partner's specification

Most partners have an implementation guide: a document that says which segments and elements of a standard message they send or want, with which codes. It is the most important input. Ask for it first, together with the rest of this list.

  1. Ask for the implementation guide of every document (850, 855, 856, 810, 997). Note the standard (X12, EDIFACT, own XML or csv) and the version (for X12 the GS08, eg 004010).
  2. Ask for sample files: at least two real-looking files per document, one simple and one with many lines. Files beat documents: you test your grammar and mapping against them.
  3. Ask for the IDs. For X12: the qualifier and ID in ISA05/ISA06 and ISA07/ISA08 (eg ZZ / PARTNERA), the IDs in GS02/GS03, and which IDs PartnerA expects from you. They can differ between test and production. For EDIFACT: the UNB sender and receiver with their qualifiers (eg a GLN with qualifier 14).
  4. Ask for the connection details: protocol (SFTP, FTP/FTPS, mail, http), host and port, user, how you log in (password or key; for a key, send them your public key), the folders for "to PartnerA" and "from PartnerA", the file names they use and want, whether you must delete files after reading, and the IP addresses they need to allow.
  5. Ask about acknowledgements and control numbers: which 997s they send and expect, how fast, whether ISA14 must be 1, and whether interchange control numbers must run without gaps per partner.
  6. Ask about test and production: is there a separate test system (other host, folder or IDs)? Must test files have ISA15 = T? Who approves the test, and how is go-live agreed?
  7. Ask about timing: when orders come, cut-off times, how fast the 855 must follow, when invoices may be sent, and the contacts (technical and business) for problems.
Check

You have one file per document type from the partner, the IDs for test and production, and login details for the test connection. If one of these is missing, the build will stop at that point: ask again now.

Part 4: Split the work into routes

A route takes files from one or more incoming channels, translates them and gives the results to outgoing channels. Rules of thumb that keep routes easy to run and to fix:

  1. One route per incoming connection, not per document. An incoming channel with Remove ticked gives its files to the first route that runs it; a second route on the same channel finds nothing. When PartnerA puts 850s and 997s in one folder, one route receives both and the translations handle each type.
  2. One route per export of your own system. Each ERP export folder gets its own route (ordrsp_out, asn_out, invoices_out). You can then run, stop or re-run one flow without touching the others.
  3. Route parts for the results. Inside a route, extra parts with filters send each result to its channel: the ERP csv to the ERP folder, the 997 back to the partner. See How to send 997s for received orders.
  4. Per-partner parts for sending. When the same document goes to several partners over different channels, add a sending part per partner with Topartner tochannel, or per group. See How to send to a different channel per partner.
  5. Order by name. Routes run in name order. Name them so that dependent flows run in the right order, or name them on the command line.

Part 8: One partner or many

The second partner with the same documents is where a design shows its quality. Plan for it from the first partner:

  • Translations: make the general rule without partners, for the standard way. Add a rule for a partner (or a group) only where a partner really differs, eg orders_x12_to_csv_partnerb for PartnerB. See How to use another mapping for one partner or a group.
  • Mappings: put the differences in data, not in code, where you can: a code list per partner, or the free fields attr1…attr5 of the partner read with transform.partnerlookup().
  • Incoming: every partner with its own server or folder gets its own incoming channel. Either one route per partner (partnera_orders_in, partnerb_orders_in), which you can stop one by one, or one route with a receiving part per channel (see How to receive from several places in one route).
  • Outgoing: one route per document, with a sending part per partner channel and the filter Topartner tochannel, or one part per group when all members use the same channel.
  • Envelopes: one partner syntax file per partner that needs other qualifiers or a test indicator.
  • Counters: with many partners that check control numbers, switch on interchangecontrolperpartner before the second partner goes live.

Part 10: The partner onboarding checklist

  1. Kick-off. Agree the documents, the dates and the contacts. Send the worksheet back to the partner to confirm the IDs and the connection.
  2. Build in the test environment. Grammars, mappings, translations, partners, channels to the partner's test system, routes, confirm rules (see How to set up a test environment). Set ISA15 to T for this partner.
  3. Test the connection. Run only the incoming route by name (bots-engine orders_in) with an empty folder: no process error means the login works. Put one test file on the partner's side and receive it.
  4. Test every inbound document with the partner's samples: all translate, the ERP accepts the csv, the 997 leaves. Look at the output with the partner's guide next to it.
  5. Test every outbound document from real ERP exports. Send them to the partner's test system and ask them to check them; collect their findings and their 997s (they must show as confirmed in All runs → Confirmations).
  6. Test the unhappy cases: a file with an error (a 997 with R, an error mail to you), a file twice, a large file, an order with many lines.
  7. Freeze the test set. Keep the inputs and the accepted outputs for acceptance tests, so every later change can be checked against them.
  8. Get the sign-off from the partner in writing, with the go-live date and the first production document.
  9. Prepare production. Move the configuration (see Changes without downtime), set the production connection and IDs, ISA15 P, check the interchange counters, set the schedule and the monitoring.
  10. Go live and watch. Check the first files of each document in production by hand, with the partner, and look at the reports several times a day for the first week.

Run it end to end

The order in which a design becomes a working integration, with the page that shows each step in full:

  1. Fill the worksheet (Part 9) and the flow table (Part 2).
  2. Write and check the grammars: Grammars, bots-grammarcheck.
  3. Write the mappings with the guide next to you: Mappings, Mapping recipes.
  4. Enter partners, group, channels, translations, routes and confirm rules in the test environment.
  5. Run each sample file through and compare the output with the guide.
  6. Work through the onboarding checklist (Part 10) with the partner.
  7. Make it production-ready: Running integrations in production.

Variations

  • EDIFACT instead of X12. The same design with ORDERS, ORDRSP, DESADV and INVOIC, CONTRL instead of 997 (send-edifact-CONTRL, ask-edifact-CONTRL), and the UNB IDs in the partner records.
  • A service provider (VAN) in between. One connection carries the files of many partners. Use one incoming route for the provider's connection; the partners come from the envelopes, and per-partner differences go into translations and partner syntax files.
  • Your system reads and writes a database. Replace the ERP file channels with db channels (see Database channels); the rest of the design stays.
  • Orders by mail from small customers. A pop3 or imap4 channel with one route; each customer is a partner with its mail address, so Bots knows who sent the file.
  • Two outputs from one order (the ERP file and a mail to sales): a chained translation, see How to make two outputs from one message.

Running integrations in production

An integration that works in a test is not yet ready for production. It is ready when errors reach a person, failed sending is retried, a dead partner connection is noticed before the partner's server locks your account, changes can be tested before they go live, and the daily checks take five minutes. This page shows how to get there with the tools of Bots 4, with the results of real test runs.

In plain words

In production something always goes wrong sooner or later: a partner sends a bad file, a server is down, a password expires. A good set-up tells you at once, repairs what it can by itself (sending again later), and lets you repair the rest without losing or doubling documents. This page is the list of things to set up for that, and what to look at every day.

Part 1: What happens to a bad file

Bots does not drop a file without a trace. Every received file gets a line in Incoming with its status; what happens next depends on where it fails:

Where it failsWhat Bots doesYour action
The file can not be read with the grammar (wrong format, a mandatory field missing)The whole file is in error; nothing of it is translated. For X12 a 997 with R (rejected) is made when a confirm rule asks for one and Bots could read the envelope.Read the error, ask the partner for a corrected file, or fix your grammar and rereceive.
One message fails in the mapping or when it is writtenThat message is in error; the other messages of the same file are translated and sent. The file shows status error.Fix the cause. Then send only the failed message again (see the warning below).
The mapping raises transform.KillWholeFileException, or the incoming grammar has 'KillWholeFile': TrueOne bad message makes the whole file fail; nothing of it is sent.Use this where a partial delivery is worse than none.
Sending fails (server down, login refused)The outgoing file gets status error in Outgoing, and a process error is written.See Part 3.
The file is larger than maxfilesizeincoming (5 MB by default)Error File size of … is too big; option "maxfilesizeincoming" in bots.ini is 5000000.Raise the setting in bots.ini if such files are normal.
Stop

A rereceive processes the whole file again. When some messages of the file were already sent, they are sent a second time. In the test run below, a file with orders PO3001 (good) and XPO3002 (bad) was rereceived: PO3001 went out twice, in interchange 4 and in interchange 5. For such files, ask the sender for a file with only the failed message, or put only that message in a new file, instead of a rereceive. Or use KillWholeFile for that format, so a file is either sent completely or not at all.

Part 2: Error report mails

After each run with a problem, Bots can mail a report to the managers in settings.py. It sends one when the run had files with errors, stuck files, system errors, or process errors (the last only when sendreportifprocesserror is True, the default). No mail is sent in acceptance tests.

  1. Switch the reports on in bots.ini: 
    [settings]
sendreportiferror = True
sendreportifprocesserror = True
  2. Set the receivers and the mail server in settings.py, as in How to get error reports by mail. Send the reports to a shared mailbox of the team, not to one person; put the environment in the subject: 
    MANAGERS = (
    ('EDI team', 'edi@mycompany.example'),
)
SERVER_EMAIL = 'edi@mycompany.example'
EMAIL_SUBJECT_PREFIX = '[Bots production] '
  3. Restart the web server and test: SysTasks → Send test report.

Part 3: When a connection fails: retries, resend and rereceive

Servers of partners are down now and then. Bots handles it in layers:

  1. Tries within a run. An incoming channel tries to connect up to maxconnectiontries times (3 when the setting is missing). An outgoing channel tries as often as its Max failures field says, or else maxconnectiontries; with neither set it tries once.
  2. Failures of incoming channels over several runs. With Max failures on an incoming channel (eg 3), a failed connection is only logged (Communication failure 1/3 …) until it failed in that many runs in a row; then it becomes a process error and the count starts again. Without it, every failed run is a process error. The incoming files simply wait on the server for the next run.
  3. Outgoing files that could not be sent get status Error in Outgoing. They are not lost: Bots keeps them and can send them again.
  4. Automatic retry. A run with --automaticretrycommunication (or Run → Retry failed out-communications) sends again every outgoing file whose sending failed since the previous retry run. Schedule it, eg every hour.
  5. By hand. Resend in Outgoing for one file, then Run → Run user-indicated resends; Rereceive in Incoming to process a received file again. See How to send an outgoing file again and How to process an incoming file again.
  6. Never again. No automatic retry on an outgoing line in error: the retry leaves it alone (for a file the partner does not want any more).
Watch out

The automatic retry first sets a starting point and sends nothing. In the test with Bots 4.0.0 the first two retry runs of a new environment only set that point; the third one sent. Files that failed before the starting point are never retried automatically: resend them by hand. Schedule the retry from the first day, and after go-live check once that a failed file is really sent again.

Check

In the practice runs, the two outgoing files that failed after the starting point were sent by the next retry run once the server was back; the file that failed before it was not:

Part 4: Partner logins that stop working

Passwords expire, keys are replaced, accounts are moved. Then every scheduled run tries to log in with the old details, and does so again and again:

  • An incoming channel tries maxconnectiontries times per run: 3 by default. With a run every 5 minutes that is 36 failed logins per hour from one channel. The practice run below shows the three tries of one run.
  • Many servers lock an account after a few failed logins. When the partner then fixes the password, the account is locked and has to be unlocked as well; some servers also block the IP address.
  • Max failures does not reduce the tries: it only delays the process error. With 3 and a run every 5 minutes, a dead login shows as a process error once every 15 minutes.

What to do:

  1. Lower the tries in bots.ini of production, so one run makes one login attempt: 
    [settings]
maxconnectiontries = 1
    This applies to all incoming channels, and to outgoing channels without their own Max failures. A short outage is then handled by the next run, not by tries within the run.
  2. Read the process errors every day (All runs → Process Errors). A login or authentication error that comes back in every run is a dead login, not an outage.
  3. Stop the route that fails in every run: Configuration → Routes, open the route and tick Not in default run (Bots sets it on all parts of the route). Scheduled runs leave it out, but you can still run it by name to test. To stop it completely, tick its parts and use the action activate/de-activate.
  4. Stop the retries of outgoing files to that server: they log in too. Set the waiting files to No automatic retry, and resend them by hand later.
  5. Contact the partner with the error text and the time of the first failure; ask them to check whether the account is locked.
  6. Test once when the partner reports the fix: bots-engine -c/srv/bots/env/production/config orders_in, then look at Process Errors. When it is clean, untick Not in default run and resend the files of step 4.
Tip

A channel is used by every route that names it. Before you change a channel, look at its Routes column in Configuration → Channels.

Part 5: A test environment next to production

Every change is tested before it reaches production. That needs a second environment on the same or another machine (see Environments):

  1. Make the test environment with its own folders and its own ports in bots.ini: [settings] port, [webserver] port, [jobqueue] port. Two environments with the same [settings] port block each other's runs.
  2. Make it look different: [webserver] environment_text = TEST and environment_text_color = #c00000 (see How to brand an environment), and EMAIL_SUBJECT_PREFIX = '[Bots test] ' in its settings.py.
  3. Keep it away from partners. Either connect its channels to the partners' test systems (other folders or hosts, ISA15 T), or set [settings] channels_use_testpath = True and give every channel an Acceptance test path: then it reads and writes local folders only, and a remote channel without a test path is not run.
  4. Keep a regression set: the accepted inputs and outputs of each integration. Run them as an acceptance test (runacceptancetest = True: frozen clock and counters, so the output can be compared byte for byte) after every change of a grammar or mapping.
Stop

A test environment that sends to a partner's production system with your production IDs uses its own counters. The partner then gets control numbers that production will use again later. Never let a test environment reach production systems of partners.

Part 6: Counters and control numbers when you move or restore

Partners check interchange control numbers (ISA13, UNB 0020) for gaps and duplicates. The numbers come from counters in the database (see Counters), so anything that replaces the database touches them:

  • Restore of a backup. The counters go back to the time of the backup. The next files get numbers that were already sent. After a restore, before the first run: SysTasks → View/edit counters, find isacounter_… / unbcounter_… and set each above the last number sent (look it up in Outgoing → column Reference of the newest files, in the archive, or ask the partner).
  • Moving to another machine or database. Copy the table uniek with the rest; check the first interchange per partner in Outgoing after the move.
  • Switching from another system (or back): set the counters of the system that takes over to the last numbers of the other one before its first run; see Part 11.
  • Changing interchangecontrolperpartner or your sender ID makes new counter names; set them to what the partners expect.
Watch out

Change counters only while no engine runs, and never lower an interchange counter that is in use.

Part 8: Cleanup, archives and backups

  • History. Reports, file lines and data files are removed after maxdays (30). Within that time you can view, resend and rereceive. Set it to the longest time in which you still want to resend from the web interface.
  • Archive. For longer periods (audits, disputes) use the Archive path of the partner channels, with Max days archive per channel or maxdaysarchive (180). Give each channel its own archive folder: the cleanup deletes everything in it that is older than the limit.
  • Backups. Back up config, usersys, the database, botssys/data, the archives, keys and the scheduler definitions, and make a backup plugin before every large change. See How to back up. Test a restore once, in the test environment, including the counters (Part 6).

Part 9: Monitoring: what to check every day

Error mails tell you about problems in runs. Two things they can not tell: that runs stopped, and that an acknowledgement never came. A small script that reads the Bots database closes that gap. Save it outside usersys, eg as /srv/bots/scripts/bots_healthcheck.py:

"""Health check of one Bots environment, for a scheduler or a monitoring tool.

Usage: python bots_healthcheck.py <config folder> [minutes]
Prints what needs attention; exit code 0 = all well, 1 = look at Bots.
"""
import datetime
import sys

from bots import botsinit

botsinit.generalinit(sys.argv[1])
from bots import models                                # noqa: E402  (after generalinit)
from bots.botsconfig import DONE, ERROR, EXTERNOUT, PROCESS   # noqa: E402

max_minutes = int(sys.argv[2]) if len(sys.argv) > 2 else 30
now = datetime.datetime.now()
day_ago = now - datetime.timedelta(days=1)
problems = []

# 1. Did the engine run lately? (no run = no error mail either)
last = models.report.objects.order_by('-idta').first()
if last is None or last.ts < now - datetime.timedelta(minutes=max_minutes):
    problems.append(f'no run in the last {max_minutes} minutes (last: {last.ts if last else "never"})')

# 2. Runs with errors in the last 24 hours
bad_runs = models.report.objects.filter(ts__gte=day_ago, status=True).count()
if bad_runs:
    problems.append(f'{bad_runs} run(s) with errors in the last 24 hours')

# 3. Outgoing files that are still in error (not resent, not set to "No retry")
out_errors = models.ta.objects.filter(ts__gte=day_ago, status=EXTERNOUT, statust=ERROR).count()
if out_errors:
    problems.append(f'{out_errors} outgoing file(s) not sent')

# 4. Process errors (connections, scripts) in the last 24 hours
proc_errors = models.ta.objects.filter(ts__gte=day_ago, status=PROCESS, statust=ERROR).count()
if proc_errors:
    problems.append(f'{proc_errors} process error(s)')

# 5. Acknowledgements asked more than a day ago and not received
pending = models.ta.objects.filter(ts__lt=day_ago, confirmasked=True, confirmed=False,
                                   confirmtype__startswith='ask', statust=DONE).count()
if pending:
    problems.append(f'{pending} file(s) wait more than a day for an acknowledgement')

for problem in problems:
    print('ATTENTION:', problem)
if not problems:
    print('OK')
sys.exit(1 if problems else 0)

Run it with the Python of Bots: /opt/bots4/bin/python /srv/bots/scripts/bots_healthcheck.py /srv/bots/env/production/config 30 (Windows: C:\bots4\Scripts\python.exe C:\bots\scripts\bots_healthcheck.py C:\bots\env\production\config 30). Most monitoring tools can run a command and alert on exit code 1. It reads the database through Bots, so it works with SQLite and with a database server. The check for a recent run needs runs that are kept: empty "new" runs are kept for hoursrunwithoutresultiskept hours (24 in the installed bots.ini), which is enough.

Check

On the practice environment after the runs below:

ATTENTION: 4 run(s) with errors in the last 24 hours
ATTENTION: 1 outgoing file(s) not sent
ATTENTION: 4 process error(s)

Exit code 1. The outgoing file not sent is the one of run 1, which the retry did not take. With 0 as minutes it also prints ATTENTION: no run in the last 0 minutes (last: 2026-10-15 21:18:46).

Part 10: Changes without downtime

Bots starts a new engine for every run, so a changed mapping, grammar or route is used from the next run on; you do not stop anything. That is also the risk: a mistake is live at the next run. Work like this:

  1. Change and test in the test environment, including the acceptance test of Part 5.
  2. Make a backup plugin of production: SysTasks → Plugins → Make backup plugin.
  3. Move only what changed. For a mapping or grammar, copy the file into usersys of production, or make a plugin in the test environment with Make translate plugin (mapping(s) without grammars) or Make grammar plugin (grammars only) in Translations. For new routes, a plugin with the selected routes (see How to make a plugin of a few routes).
  4. Choose a quiet moment, between two runs, outside the partner's busy hours. With the job queue, nothing overlaps a run that is going.
  5. After reading a plugin, check the channels it brought (they have the values of the test environment) and activate the routes: every route in a plugin is set inactive when it is read, also a route that was active in production.
  6. Watch the next runs of the changed flow in Incoming and Outgoing.
Stop

Reading a plugin overwrites channels with the same name. A plugin made in the test environment brings test hosts, folders and passwords into production. Use plugins with only translations and grammars for changes of existing flows, or correct the channels right after reading.

Tip

Keep usersys of production in version control, with the configuration index (bots-plugoutindex, see How to keep the configuration in version control). Every change of a route or channel is then visible, and you can see what changed when a flow breaks.

Part 11: Moving an integration from an old system

When an integration moves from another EDI system (or from Bots 3, see Upgrade from Bots 3), run both side by side before you switch:

  1. Collect real files of the old system: inputs and the outputs it made, for each document and partner.
  2. Parallel run. Give Bots a copy of the live input (a copy of the incoming folder, or the old system's archive) and let it write to local folders only (channels_use_testpath = True). The old system stays the one that sends.
  3. Compare the outputs file by file. Expect differences in dates, times, control numbers and file names; every other difference is a finding. An acceptance test with frozen clock and counters makes the comparison easier.
  4. Switch per partner, not all at once: stop the partner's flow in the old system, set the counters in Bots to the old system's last numbers (Part 6), activate the routes in Bots, and check the first files with the partner.
  5. Keep a way back for some days: do not delete the old configuration. When you go back, copy the counters of Bots to the old system first.

Variations

  • Error mails per partner. A mapping can mail a partner contact about a business problem in its document with transform.sendbotsemail() (the partner's Mail); see Mapping functions.
  • Fewer mails for short outages. Max failures on incoming channels of servers that are often down for a few minutes; keep the daily check of process errors.
  • Several production environments (eg per business unit): one job queue and directory monitor per environment, each with its own ports, and the health check per environment.
  • Bots behind a monitoring system. Use the exit codes of bots-engine (Part 7) and of the health check, and the log files in botssys/logging (see Logging).
  • Busy flows first. With the job queue, give the frequent receive run priority 1 and slow routes a higher number.
