bots.ini reference

bots.ini is the main settings file of a Bots environment. It sets how long Bots keeps data, how it logs, which ports it uses, how the web interface looks and how the job queue and the directory monitor work. Read this page when you want to change one of these, or to look up what a setting does.

In plain words

Bots has a small text file with switches and numbers in it. Each program of Bots reads it when it starts. You open it in a text editor, change a value, save, and restart the program that needs the new value. If a line is missing, Bots uses a built-in default.

How it works

  1. Where the file is. bots.ini is in the config directory of the environment, next to settings.py. In a standard installation that is ~/.bots/env/default/config/ (Windows: C:\Users\<you>\.bots\env\default\config\). You choose another config directory with the option -c<directory> of every command or with the environment variable BOTS_CONFIG_DIR; see Environments.
  2. Who reads it. Every program of Bots reads the file once, when it starts: bots-engine (so a change counts from the next run), bots-webserver, bots-jobqueueserver and bots-dirmonitor (restart these after a change).
  3. The format. The file has sections, each led by a header in square brackets such as [settings], followed by lines name = value (name: value works too). Lines that start with # or ; are comments. Names of settings are not case-sensitive; names of sections are. True/false settings accept True, False, yes, no, on, off, 1, 0.
  4. Missing lines. When a line is missing (or commented out), Bots uses the default of the program. That default is in the column "Default" below. In a few cases the default of the program differs from the value that is in the bots.ini that Bots installs; both are given.
  5. Relative paths in bots.ini are relative to the environment directory (the folder that holds config, botssys and usersys).
  6. A section or a setting twice is not an error: the last value counts, as in Bots 3.
  7. Old names. Bots accepts a bots.ini of Bots 3: log_file_number = daily is read as log_when = daily, use_email_address_validation as validate_email_address, log levels in lower case are accepted, and a file without section [dirmonitor] works. bots-portconfig carries a Bots 3 file over for you; see Command-line tools.

How to change a setting

  1. Open the file config/bots.ini of the environment in a text editor (Notepad, nano, vi). Use an editor that saves plain UTF-8 text.
  2. Find the section, for example [settings]. Find the line, or add it under the section header.
  3. Change the value and remove a leading # if the line was commented out. Do not leave a number or true/false setting empty: maxconnectiontries = with nothing after it stops the engine with a ValueError. Comment the line out instead.
  4. Save the file.
  5. Restart bots-webserver, bots-jobqueueserver and bots-dirmonitor if the setting is for them. The engine uses the new value in its next run.

How to make the common changes

Keep history longer or shorter

[settings]
# reports, incoming/outgoing views and the data files: 60 days
maxdays = 60
# the archive of channels with an "Archive path": 365 days
maxdaysarchive = 365

See Maintenance for what is removed and when.

Get an e-mail when a run has errors

[settings]
sendreportiferror = True
# also mail when only a process error (eg an ftp server that does not answer) occurred
sendreportifprocesserror = True

Then set the mail server and the receivers in settings.py; see settings.py. Test with SysTasks → Send test report.

Run the web interface on another port, or over HTTPS

[webserver]
port = 8090
ssl_certificate = /srv/bots/certs/edi.example.com.pem
ssl_private_key = /srv/bots/certs/edi.example.com.key

Restart bots-webserver; open https://edi.example.com:8090. See Security.

Show which environment you are in

[webserver]
environment_text = TEST
environment_text_color = #c00000

Run two environments on one machine at the same time

Give each environment its own ports, so they do not block each other:

[settings]
port = 28091        ; engine lock port (default 28081)
[webserver]
port = 8090         ; web interface (default 8080)
[jobqueue]
port = 28092        ; job queue (default 28082)

Find more detail when something goes wrong

[settings]
log_file_level = DEBUG
log_level = DEBUG
debug = True

Set these back after the problem is found: the log files grow fast. See Logging.

settings.py

settings.py is the second settings file of an environment. It holds the settings of Django, the framework under the web interface and the database: which database Bots uses, the time zone, the language, the mail server for error reports, and the login sessions. You need it to connect Bots to a database server, to get error mails, and to set the time zone.

In plain words

bots.ini is about how Bots works; settings.py is about where Bots keeps its data and how it talks to the outside world (mail, browser sessions). It is a small Python file: you change values between quotes and brackets, and keep the rest as it is.

How it works

  1. Where. settings.py is in the config directory, next to bots.ini. Every program of Bots imports it at start. Restart the web server, job queue server and directory monitor after a change; the engine reads it at its next run.
  2. It is Python. A typing error (a missing quote or comma) stops every program of Bots with a Python SyntaxError. Keep a copy before you change it.
  3. It reads bots.ini. The file reads [directories] botssys from bots.ini to find the SQLite database (botssys/sqlitedb/botsdb) and the folder for the static files of the web interface (botssys/static).
  4. A new environment gets a new secret key. When Bots makes a new environment (first start, or bots-configure), it copies bots/install/settings.py and writes a new random SECRET_KEY in it.
  5. Not the file of Bots 3. A settings.py of Bots 3 is refused at start; copy the new template and carry your values over (by hand, or with bots-portconfig). changed in 4.0

How to set the time zone

  1. Look up the name of your time zone in the tz database, eg Europe/Amsterdam, America/New_York, Asia/Kolkata.
  2. Open config/settings.py and set TIME_ZONE = 'America/New_York'.
  3. On Windows, use the same time zone as the system clock of the machine.
  4. Keep USE_TZ = False: the engine works with local time.
  5. Restart the web server. The times in All runs now match your clock.

How to get error reports by mail

  1. Switch the reports on in bots.ini: [settings] sendreportiferror = True.
  2. Set the receivers in settings.py: 
    MANAGERS = (
    ('EDI team', 'edi@mycompany.example'),
)
SERVER_EMAIL = 'edi@mycompany.example'     # sender of the reports
EMAIL_SUBJECT_PREFIX = '[Bots production] '
  3. Set the mail server. With Django 6.1 or newer (what a new installation gets), in MAILERS, the form of the template of this version: 
    MAILERS = {
    "default": {
        "BACKEND": "django.core.mail.backends.smtp.EmailBackend",
        "OPTIONS": {
            "host": "mail.example.org",
            "port": 587,
            "use_tls": True,
            "username": "edi@mycompany.example",
            "password": os.environ.get("BOTS_SMTP_PASSWORD", ""),
            "timeout": 10,
        },
    },
}
  4. Or, with Django 4.x to 6.0, set the classic names instead, and remove MAILERS (see the warning below): 
    EMAIL_HOST = 'mail.example.org'
EMAIL_PORT = 587
EMAIL_USE_TLS = True
EMAIL_HOST_USER = 'edi@mycompany.example'
EMAIL_HOST_PASSWORD = os.environ.get("BOTS_SMTP_PASSWORD", "")
  5. Restart the web server.
  6. Test: SysTasks → Send test report. Expect the message Sending test mail succeeded. and a mail with subject "testsubject" at the managers.
Watch out

Use exactly one of the two forms. Django 6.1 and newer read MAILERS, and refuse to start when settings.py also has one of the classic names: every Bots program then stops with Deprecated email settings are not allowed when MAILERS is defined: EMAIL_HOST. Django 4.x to 6.0 (Bots allows Django 4 to 6) do not know MAILERS; they read EMAIL_HOST, EMAIL_PORT, EMAIL_USE_TLS, EMAIL_USE_SSL, EMAIL_HOST_USER, EMAIL_HOST_PASSWORD and EMAIL_TIMEOUT, and use localhost port 25 when these are missing. See your version with python -c "import django; print(django.get_version())". Always check with Send test report.

Tip

Django puts [Django] in front of the subject of every report unless you set EMAIL_SUBJECT_PREFIX. Use it to say which environment sent the mail.

How to change how long users stay logged in

  1. Set the idle time: SESSION_COOKIE_AGE = 7200 (seconds; 2 hours).
  2. Keep SESSION_SAVE_EVERY_REQUEST = True so the time counts from the last click, not from the login.
  3. Choose SESSION_EXPIRE_AT_BROWSER_CLOSE = True (log in again after closing the browser) or False (stay logged in until the idle time is over).
  4. Restart the web server. Expired sessions are removed from the database by the daily cleanup of the engine.

Databases for Bots itself

Bots keeps its configuration (routes, channels, partners, users) and its history (runs, files, counters) in a database. By default this is one SQLite file; for larger volumes or for a company standard you can use MySQL/MariaDB, PostgreSQL or Microsoft SQL Server.

In plain words

Out of the box Bots stores everything in one file on disk, and that works for most installations. If you want Bots to use a database server, you install a driver, create an empty database, tell settings.py where it is, and run bots-updatedb to make the tables.

How it works

  1. Two kinds of tables. Django manages the tables of the configuration and the reports (routes, channel, partner, partnergroup, translate, chanpar, ccode, ccodetrigger, confirmrule, report, filereport) plus its own (auth_*, django_*). The engine has four tables of its own: ta (every step of every file), mutex (the database lock of a run), uniek (counters) and persist (values saved by mappings). Their definitions per database are in bots/sql/ (ta.mysql.sql, ta.postgresql.sql, ta.microsoft.sql, ta.sqlite.sql …).
  2. One command makes them. bots-updatedb applies the Django migrations and creates the engine tables from bots/sql. new in 4.0 (in Bots 3 the engine tables were made by hand.)
  3. The web interface uses Django's connection. The engine opens its own connection with the same settings: sqlite3, MySQLdb (package mysqlclient), psycopg (or psycopg2), or for SQL Server mssql-python or pyodbc.
  4. The same results everywhere. Bots sorts in its own code where the order matters, so routes, envelopes and counters come out the same on every database. Tested with PostgreSQL 17, MySQL 8.4, MariaDB 11.4 and SQL Server 2022.

How to use PostgreSQL

  1. Install the driver in the Python environment of Bots: pip install "bots-ediint[postgresql]".
  2. Create the user and the database on the server (as the postgres superuser): 
    CREATE USER bots WITH PASSWORD 'secret-example';
CREATE DATABASE botsdb OWNER bots ENCODING 'UTF8';
  3. Set DATABASES in config/settings.py (replace the SQLite block): 
    DATABASES = {
    'default': {
        'ENGINE': 'django.db.backends.postgresql',
        'NAME': 'botsdb',
        'USER': 'bots',
        'PASSWORD': 'secret-example',
        'HOST': 'db.example.com',
        'PORT': '5432',
        'OPTIONS': {'client_encoding': 'utf-8'},
    }
}
  4. Check: bots-updatedb --check. Expect This database is: empty (no bots tables). and To do: create the tables.
  5. Create the tables and a first user: bots-updatedb --createsuperuser. It asks for a user name and a password. Expect The database is up to date.
  6. Start bots-webserver and log in with that user.

How to use MySQL or MariaDB

  1. Install the driver: pip install "bots-ediint[mysql]".
  2. Create the database and the user: 
    CREATE DATABASE botsdb CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'bots'@'%' IDENTIFIED BY 'secret-example';
GRANT ALL PRIVILEGES ON botsdb.* TO 'bots'@'%';
  3. Set DATABASES: 
    DATABASES = {
    'default': {
        'ENGINE': 'django.db.backends.mysql',
        'NAME': 'botsdb',
        'USER': 'bots',
        'PASSWORD': 'secret-example',
        'HOST': 'db.example.com',
        'PORT': '3306',
        'OPTIONS': {
            'charset': 'utf8mb4',
            'init_command': 'SET default_storage_engine=INNODB',
        },
    }
}
  4. Create the tables: bots-updatedb --createsuperuser.
Watch out

PORT must be filled in for MySQL: the engine converts it to a number (int('') fails). Use the InnoDB engine: the database lock and the counters need transactions.

How to use Microsoft SQL Server

  1. Install pip install "bots-ediint[mssql]" and an ODBC driver for SQL Server on the machine (or the package mssql-python, which needs no ODBC driver; the engine uses it when it is installed).
  2. Create a database botsdb and a login bots that owns it (SQL Server Management Studio or sqlcmd).
  3. Set DATABASES: 
    DATABASES = {
    'default': {
        'ENGINE': 'mssql',
        'NAME': 'botsdb',
        'USER': 'bots',
        'PASSWORD': 'secret-example',
        'HOST': 'db.example.com',
        'PORT': '1433',
        'OPTIONS': {
            'driver': 'ODBC Driver 18 for SQL Server',
            # for a server with its own (self-signed) certificate:
            'extra_params': 'TrustServerCertificate=yes',
        },
    }
}
  4. Create the tables: bots-updatedb --createsuperuser.

Without USER the engine logs in with the Windows account (Trusted_Connection=yes). OPTIONS may also have python_driver to choose the driver: 'mssql_python' (with an underscore; no ODBC driver needed) or 'pyodbc'.

How to move from SQLite to a database server

Move the configuration with a plugin and start the history fresh:

  1. Note the counters: SysTasks → View/edit counters. Write down the current numbers (interchange control references and the like). Partners check these numbers.
  2. Make a plugin: SysTasks → Plugins → Make plugin. Tick Database configuration, User code lists and Script files. Save the zip file.
  3. Stop the scheduler, the job queue server, the directory monitor and the web server.
  4. Set up the server database as described above and run bots-updatedb --createsuperuser.
  5. Start the web server, log in, and read the plugin: SysTasks → Plugins → Read plugin.
  6. Set the counters to the noted values in View/edit counters.
  7. Create the users again (Users and rights); users are not in a plugin.
  8. Keep the SQLite file (botssys/sqlitedb/botsdb) until you are sure; with the old settings.py you can look at the old history.
Note

A plugin can also hold Database transactions (the history and all counters). That plugin can be very large; use it only when you need the history in the new database.

How to back up the database

  • SQLite: stop the engine (no run may be going), then copy botssys/sqlitedb/botsdb. A copy made during a run can be damaged.
  • PostgreSQL: pg_dump -h db.example.com -U bots -F c -f botsdb.dump botsdb.
  • MySQL/MariaDB: mysqldump -h db.example.com -u bots -p --single-transaction botsdb > botsdb.sql.
  • SQL Server: BACKUP DATABASE botsdb TO DISK = 'D:\backup\botsdb.bak'.

Back up the files too; see Maintenance.

Command-line tools

Bots is a set of programs you start from a command prompt, a scheduler or a service manager. This page lists every program that the Bots package installs, with every option, its exit codes and examples for Windows and Linux.

In plain words

The web interface is for looking and configuring. The real work is done by small programs: bots-engine translates and sends, bots-webserver shows the web interface, and a few helpers queue jobs, watch folders, check grammars and move old installations over. You type their names in a terminal, with options behind them.

How it works

  1. Where the programs are. pip installs them in the Scripts folder (Windows, eg C:\bots4\Scripts\bots-engine.exe) or the bin folder (Linux, eg /opt/bots4/bin/bots-engine) of the Python environment where you installed Bots. Activate that environment, or use the full path.
  2. Which environment. Every program that works on an environment takes -c<config directory>, written without a space: -cC:\bots\env\production\config or -c/srv/bots/env/production/config. Without -c, Bots uses the environment variable BOTS_CONFIG_DIR; without that, ~/.bots/env/<BOTSENV>/config, where BOTSENV is an environment variable (default default). That last environment is created the first time it is needed. The help texts still say "default: config"; this is what the program does.
  3. One environment per process. Each program works on one environment. To work on two environments, start the program twice, each with its own -c.
  4. Help. -h, --help, ? or /? prints the usage text. For most programs an unknown option starting with - also prints the usage text and does nothing.

How to run the engine by hand

  1. Open a terminal (Windows: Command Prompt or PowerShell; Linux: a shell) as the user that runs Bots.
  2. Run a normal run for the environment: 
    C:\bots4\Scripts\bots-engine.exe -cC:\bots\env\production\config

    /opt/bots4/bin/bots-engine -c/srv/bots/env/production/config
  3. Read the result. The log is shown on the screen. The last lines say how many files were received, had errors and were sent. The run also appears in All runs.
  4. Check the exit code when a script runs the engine: Windows echo %ERRORLEVEL% (cmd) or $LASTEXITCODE (PowerShell); Linux echo $?. 0 is OK, 2 means errors in the run.

How to run one route, or resend

  • Only the routes orders_in and invoices_out: bots-engine orders_in invoices_out. Named routes run even when they are marked "not in default run"; they must be active.
  • Files you marked for resend in Outgoing: bots-engine --resend.
  • Files you marked for rereceive in Incoming: bots-engine --rereceive.
  • Retry outgoing files whose sending failed: bots-engine --automaticretrycommunication. The very first time this runs it only notes the moment and sends nothing, so that old files are not sent.
  • Only the cleanup: bots-engine --cleanup. With --new also: bots-engine --new --cleanup.
  • Several run types at once: bots-engine --automaticretrycommunication --resend --rereceive --new. They always run in this order, one second apart.

Scheduling runs

The engine runs when something starts it. This page shows how to start it regularly with cron or the Windows Task Scheduler, how the job queue makes runs wait for each other, and how the directory monitor starts a route as soon as a file arrives.

In plain words

You decide when Bots looks for new files: every few minutes, every hour, or the moment a file lands in a folder. The operating system's scheduler starts Bots at those times. If runs could overlap, put them in the job queue: it lines them up and starts the next one when the previous one is done.

How it works

  1. Without the job queue the scheduler starts bots-engine directly. When a run is still going, the new engine cannot get the lock port ([settings] port) and stops at once with exit code 3: that run is skipped, not delayed. The next scheduled run picks up the files.
  2. With the job queue ([jobqueue] enabled = True and bots-jobqueueserver running), the scheduler starts bots-job2queue bots-engine …. The job queue server keeps a list of jobs and starts the next one when the previous one has ended. Priority 1 runs first, 9 last; with the same priority, the oldest job first. A job equal to one that is waiting is not added twice (only its priority is updated). The Run menu of the web interface also uses the queue, with priority 5.
  3. The directory monitor (bots-dirmonitor) watches folders. When a file arrives it waits until no new events come for 2 seconds, then sends one job per route to the queue. It needs the job queue.
  4. The database lock. Besides the port, each run sets a lock row in the database (table mutex). If a run ends abnormally, the next run finds the lock, logs !Bots database is locked!, mails it (when reports are on) and first does a crash recovery of the broken run.

How to schedule with cron (Linux)

  1. Log in as the user that runs Bots and open its crontab: crontab -e.
  2. Add the lines (full paths; cron has a short PATH): 
    # every 5 minutes: new files
*/5 * * * * /opt/bots4/bin/bots-engine --new -c/srv/bots/env/production/config >/dev/null 2>&1
# every hour at :30: retry failed sending
30 * * * * /opt/bots4/bin/bots-engine --automaticretrycommunication -c/srv/bots/env/production/config >/dev/null 2>&1
# a route that is not in the default run, every day at 06:00
0 6 * * * /opt/bots4/bin/bots-engine invoices_out -c/srv/bots/env/production/config >/dev/null 2>&1
  3. Save. The output goes to the log files of Bots, so it is discarded here.
  4. Check after a few minutes in All runs that runs appear.

With the job queue, put /opt/bots4/bin/bots-job2queue -p1 in front: */5 * * * * /opt/bots4/bin/bots-job2queue -p1 bots-engine --new -c/srv/bots/env/production/config.

How to schedule with the Windows Task Scheduler

  1. Open Task Scheduler → Create Task.
  2. General: name Bots production new; choose the user that runs Bots; tick Run whether user is logged on or not.
  3. Triggers → New: daily, Repeat task every 5 minutes for Indefinitely.
  4. Actions → New: program C:\bots4\Scripts\bots-engine.exe, arguments --new -cC:\bots\env\production\config.
  5. Settings: If the task is already running: Do not start a new instance.
  6. Save and give the password. Check All runs after a few minutes.

The same from a command prompt (as administrator):

schtasks /Create /TN "Bots production new" /SC MINUTE /MO 5 /RU edisvc /RP * ^
  /TR "C:\bots4\Scripts\bots-engine.exe --new -cC:\bots\env\production\config"

How to use the job queue

  1. Switch it on in bots.ini: [jobqueue] enabled = True. Restart the web server.
  2. Start the server: bots-jobqueueserver -c/srv/bots/env/production/config. Expect in its log Listening xmlrpc request on port: "28082". and bots-engine is run from: …. In production run it as a service (see below).
  3. Send jobs from the scheduler: 
    bots-job2queue -p1 bots-engine --new -c/srv/bots/env/production/config
bots-job2queue -p7 bots-engine --automaticretrycommunication -c/srv/bots/env/production/config
    Expect OK, job added to queue.
  4. Check SysTasks → Logs → Jobqueue logs: Starting job 1: … and Finished job 1, elapsed time: …, exit code 0.
Tip

Give the frequent "new" run priority 1 and slow, less urgent routes a higher number. When the machine is busy, the urgent runs go first.

How to start a route when a file arrives

  1. Set up and start the job queue (above).
  2. Choose the folder. Either tick Dirmonitor in the route (the folder and file name of its incoming file channel are watched), or add a section to bots.ini: 
    [dirmonitor1]
path = /srv/edi/in
filemask = *.csv
route = orders_in
recursive = False
  3. Start the monitor: bots-dirmonitor -c/srv/bots/env/production/config. Its log shows Watched path added for route "orders_in": /srv/edi/in/*.csv and Started.
  4. Drop a test file in the folder. Expect Sending job to queue: "bots-engine -c… orders_in". in the monitor log, then the run in All runs.
  5. After a change of the folders: bots-dirmonitor -c… --reload. Changing the path or file name of a monitored channel, or the Dirmonitor tick of a route, in the web interface reloads it by itself.
Watch out

The monitor sees local folders only. For files on an ftp or sftp server, schedule the route instead. Keep a scheduled run as well: a file that arrives while the monitor is stopped is only seen at its next start (with process_existing = True).

How to run the servers as services

bots-webserver, bots-jobqueueserver and bots-dirmonitor keep running; start them when the machine starts. bots-engine is never a service: it is started per run.

Linux (systemd), file /etc/systemd/system/bots-jobqueue@.service:

[Unit]
Description=Bots job queue server (%i)
After=network.target

[Service]
User=edi
ExecStart=/opt/bots4/bin/bots-jobqueueserver -c/srv/bots/env/%i/config
Restart=on-failure

[Install]
WantedBy=multi-user.target

Then systemctl enable --now bots-jobqueue@production. Make the same for bots-webserver and bots-dirmonitor (with After=bots-jobqueue@%i.service). Stop with systemctl stop: the job queue lets the running job finish.

Windows: use a service wrapper (such as NSSM) or a Task Scheduler task with the trigger At startup, program C:\bots4\Scripts\bots-jobqueueserver.exe, arguments -cC:\bots\env\production\config, and in Settings no time limit.

How to run several environments

  1. Give each environment its own ports in its bots.ini: [settings] port, [webserver] port, [jobqueue] port.
  2. Schedule each environment with its own -c. Runs of different environments may run at the same time.
  3. Start one job queue server and one directory monitor per environment, each with its own -c.

Acceptance testing

An acceptance test runs your routes on test files without touching your partners: files are read from and written to local folders, and the clock and the counters are frozen so every test run gives the same output. Use it to check a change before it goes to production, and to prove that existing flows still work.

In plain words

You give each channel a "practice folder". In test mode Bots reads from and writes to those folders instead of the real servers, and pretends it is always the same date and time. Then the output of today's test can be compared, byte for byte, with the output you know is right.

How to set up a test environment

  1. Make a separate environment (see Environments): its own config, botssys, usersys and ports. Copy usersys and read a plugin of production, or use bots-portenv --local-folders for an environment that comes from Bots 3.
  2. Give every channel a testpath: Configuration → Channels → open the channel → Acceptance test path, eg botssys/infile/orders for partnera_sftp_in and botssys/outfile/invoices for partnera_sftp_out. Relative paths are relative to the environment folder.
  3. Put test files in the incoming test folders: one or more X12 850 files of PartnerA in botssys/infile/orders/.
  4. Put the expected results in a folder of their own, eg botssys/infile/outfile/, made from a run you checked by hand.
  5. Switch the test mode on: [acceptance] runacceptancetest = True in bots.ini of the test environment.
Stop

A channel without a testpath still connects to the real server in a test run, and sends real files. Give every remote channel a testpath before you switch the mode on, or use channels_use_testpath, which refuses such channels.

How to run a test and compare the results

  1. Write the check script usersys/routescripts/bots_acceptancetest.py: 
    import filecmp
import os
import shutil

    return os.path.join(botsglobal.ini.get('directories', 'botssys'), *parts)

    """before the run: empty the output folder"""
    shutil.rmtree(_botssys('outfile'), ignore_errors=True)
    os.makedirs(_botssys('outfile'))

    """after the run: compare output with the expected files"""
    result = filecmp.dircmp(_botssys('outfile'), _botssys('infile', 'outfile'))
    print('different:', result.diff_files)
    print('missing:', result.right_only)
    print('unexpected:', result.left_only)
    Both functions may also be left out. They receive the routes given on the command line (an empty list for a normal run).
  2. Run the engine from a terminal: bots-engine -c/srv/bots/env/test/config. The log says This run is an acceptance test - as indicated in option "runacceptancetest" in bots.ini.
  3. Read the comparison on the screen (the output of posttest is printed there, not in the web interface).
  4. Look at the run in All runs, Incoming and Outgoing as usual.
  5. Remove the test runs: SysTasks → Configuration → Bulk delete; tick only Delete transactions in acceptance testing and untick Delete transactions.
  6. Switch the mode off (runacceptancetest = False) when the environment is used for normal work again.
Watch out

In Bulk delete both Delete transactions in acceptance testing and Delete transactions are ticked when the page opens. With both ticked, Bots deletes all runs and files, not only the test runs.

Logging

Every program of Bots writes what it does to a log file: the engine per run, the web server, the job queue and the directory monitor per day. The log is where you look when the screens of the web interface do not explain a problem, or when a program does not start.

In plain words

A log is a diary that Bots keeps while it works: one line per step, with the time and how important it is. Normally it notes only the main steps. When you hunt a problem, you turn the detail up, run again, read, and turn it down.

Maintenance

Bots cleans up after itself: old runs, data files, archives and log files are removed after a set number of days. This page explains that cleanup, what you should back up, how to move Bots to another machine and how to upgrade to a newer version.

In plain words

Every file Bots handles leaves copies and notes behind. Once a day Bots throws away what is older than the limits you set, so the disk and the database do not fill up. Your part is to make backups, and to follow a few steps when you move or upgrade.

How the cleanup works

After every run (not in acceptance tests):

  1. A "new" run that received nothing and had no process error has its step records (ta) deleted at once; its report is deleted when it is older than hoursrunwithoutresultiskept hours (runs of the last 25 hours are checked), together with its engine log file.

The full cleanup runs at the end of the first run of the day (whencleanup = daily), or when the engine is started with --cleanup (also from Run → Run cleanup when menu_cleanup is on). In this order:

  1. Data files: files in botssys/data/ older than maxdays; empty folders there are removed.
  2. Archives: in every channel with an Archive path, day folders and day zip files older than maxdaysarchive days (or the channel's Max days archive). Only entries named by date directly in the archive path are removed.
  3. Sessions: expired logins of the web interface.
  4. Persist: values saved by mappings older than maxdayspersist days.
  5. History: reports, file reports and step records older than maxdays days (the most recent run older than that is kept), with the engine log files of those runs; in parts of 1000.
  6. SQLite: VACUUM to give the space back.
  7. Your exit: the function postcleanup(whencleanup) in usersys/routescripts/botsengine.py, if it exists.

Errors in the cleanup are logged (Cleanup error.) and do not change the result of the run. The cleanup does not touch botssys/infile, botssys/outfile, botssys/backup and the folders of file channels. Daily log files are removed by the logging itself: it keeps log_file_number old files.

How to run the cleanup by hand

  1. From a terminal: bots-engine --cleanup -c/srv/bots/env/production/config. Expect in the log Cleanup files, Cleanup database, Done full cleanup.
  2. Or from the web interface: set [webserver] menu_cleanup = True, restart the web server, then Run → Run cleanup.
  3. To clean only at night: set whencleanup = never and schedule bots-engine --cleanup at 02:00.

Security

Bots handles business documents and holds the passwords of your partners' servers. This page lists what to protect and how: user accounts, HTTPS for the web interface, running behind a reverse proxy, file rights, the secrets in channels, and checking the identity of the servers Bots connects to.

In plain words

Three things matter: only the right people can log in, nobody can listen in on the connections, and the files on the server (with passwords and orders in them) can only be read by Bots and its administrators.

How it works

  1. Login. Every page of the web interface except the login page needs a logged-in user. What a user may see and change depends on the rights of the user and its groups; some pages (plugins, bulk delete, test mail, users) are for superusers only; running the engine needs the right "change mutex". See Users and rights.
  2. Sessions end after SESSION_COOKIE_AGE seconds without activity and, by default, when the browser closes.
  3. Protection in the pages: forms carry a CSRF token; the pages may not be shown inside a frame of another site; values from files and the database are escaped; an incoming HTML file is shown in a sandbox without scripts; the log viewer only opens files in the log folder and the source viewer only .py files in usersys.
  4. Internal ports: the engine lock port and the job queue listen on 127.0.0.1 only; the job queue only runs bots-engine and the programs in authorized_tasks.
  5. The web server listens on all network addresses of the machine, on [webserver] port. Without ssl_certificate/ssl_private_key it uses plain HTTP: passwords cross the network readable.
  6. Secrets: channel passwords are stored as plain text in the database (shown as ******** in lists). The database password and SECRET_KEY are in settings.py.

How to secure the accounts

  1. Change the password of the standard superuser bots at the first login (Home → Change password), or create your own superuser admin and deactivate bots.
  2. Give each person an own account: operator with rights to view and to run, viewer with view rights only. Make only administrators superuser.
  3. Keep the password rules of AUTH_PASSWORD_VALIDATORS in settings.py.
  4. Deactivate accounts of people who leave.

How to switch on HTTPS

  1. Get a certificate for the name users type (eg edi.example.com), in PEM form: a certificate file (with the intermediate certificates after it) and a private key file. A self-signed certificate works but browsers warn.
  2. Store the files where only the Bots account can read the key, eg /srv/bots/certs/.
  3. Set in bots.ini: 
    [webserver]
port = 8443
ssl_certificate = /srv/bots/certs/edi.example.com.pem
ssl_private_key = /srv/bots/certs/edi.example.com.key
  4. Set in settings.py: SESSION_COOKIE_SECURE = True, CSRF_COOKIE_SECURE = True, ALLOWED_HOSTS = ['edi.example.com'].
  5. Restart the web server. Its log says using ssl (https). Open https://edi.example.com:8443.

How to run behind a reverse proxy

  1. Keep Bots on HTTP on its port, and let the proxy (nginx, Apache, IIS) handle HTTPS. Serve Bots at the root of a host name (https://edi.example.com/): its pages use /bots/…, /admin/… and /static/….
  2. Block the Bots port for other machines with the firewall: the Bots web server listens on all addresses of the machine.
  3. Configure the proxy, eg nginx: 
    server {
    listen 443 ssl;
    server_name edi.example.com;
    ssl_certificate     /etc/ssl/edi.example.com.pem;
    ssl_certificate_key /etc/ssl/edi.example.com.key;
    client_max_body_size 50m;              # plugins are uploaded
    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto https;
    }
}
  4. Tell Django in settings.py: 
    ALLOWED_HOSTS = ['edi.example.com']
CSRF_TRUSTED_ORIGINS = ['https://edi.example.com']
SECURE_PROXY_SSL_HEADER = ('HTTP_X_FORWARDED_PROTO', 'https')
SESSION_COOKIE_SECURE = True
CSRF_COOKIE_SECURE = True
  5. Restart the web server and log in through the proxy.

How to protect the files

  1. Run all programs of an environment under one dedicated account (eg edi), not as root or Administrator.
  2. Restrict the config folder to that account and the administrators: chmod 700 /srv/bots/env/production/config (Linux) or remove "Users" from its permissions (Windows).
  3. Restrict botssys (business documents, the SQLite database, logs) and the key files the same way: chmod 600 /srv/bots/keys/*.
  4. Keep secrets out of files where you can: in settings.py, read passwords from environment variables, eg 'PASSWORD': os.environ.get('BOTS_DB_PASSWORD', ''), set for the service.
  5. Treat plugins and configuration indexes as secret: they contain the channels with their passwords.

How to check the host key of an SFTP server

By itself Bots accepts any host key of an SFTP server, as Bots 3 did. To check it, give the channel a communication script with a hostkey function.

  1. Get the key of the server and check its fingerprint with the partner: ssh-keyscan sftp.example.net >> /srv/bots/keys/known_hosts.
  2. Write usersys/communicationscripts/partnera_sftp_out.py (the name of the channel): 
    import paramiko


def hostkey(channeldict):
    """the key the server must have"""
    keys = paramiko.hostkeys.HostKeys('/srv/bots/keys/known_hosts')
    return keys.lookup(channeldict['host'])['ssh-ed25519']
  3. Run the route. A server with another key is refused with Bad host key from server.

For login with a key instead of a password, set the channel field Private key file; the password field is then the passphrase of the key. RSA, ECDSA and Ed25519 keys work.

How to check certificates of TLS channels

  1. Leave Verify server certificate ticked (the default for new channels of type pop3s, imap4s, smtps, smtpstarttls, ftps, ftpis, https). new in 4.0
  2. For a server with a private CA or a self-signed certificate, put the CA certificate (or the server certificate) in a PEM file and set CA certificate file to its path.
  3. For a client certificate, set Certificate chain file and Private key file; this works together with a CA certificate file.
  4. Channels from a Bots 3 database have the tick off (Bots 3 never checked); bots-updatedb lists them. Switch it on per channel when the server has a valid certificate.
