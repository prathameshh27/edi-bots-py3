Grammars

A grammar is a small Python file that describes one kind of EDI file or message: which records it has, in which order, and which fields each record has. Bots needs a grammar to read an incoming file and to write an outgoing file. You need this page as soon as you translate anything.

In plain words

A grammar is the "form layout" of a document. It tells Bots: "an order starts with a header line, then has one or more item lines; the header has an order number of at most 35 characters and a date". With that layout Bots can take a file apart into named pieces, check it, and put a new file together.

How it works

Bots never works on the raw text of an EDI file. It works on a tree of records (a node tree). The grammar is the bridge between the file and the tree:

  1. Read. Bots reads the incoming file with the grammar of the incoming editype and message type. It cuts the file into records and fields (this is called lexing and parsing) and builds the tree.
  2. Check. Bots checks the tree against the grammar: are mandatory records and fields there, do records occur not too often, do numbers and dates have the right format and length. Errors are reported for the file.
  3. Split. If the grammar says how (nextmessage), the file is split into messages; each message goes to the mapping on its own.
  4. Map. Your mapping script reads the incoming tree and fills an outgoing tree.
  5. Write. Bots checks the outgoing tree against the grammar of the outgoing message type, puts the records in the order of that grammar, formats the fields and writes the file. An envelope is added later, also with a grammar.

Where grammar files live

Grammars are Python files in the usersys folder of your environment:

usersys/grammars/<editype>/<messagetype>.py

usersys/grammars/x12/850004010.py          editype x12, message type 850004010
usersys/grammars/edifact/ORDERSD96AUNEAN008.py
usersys/grammars/csv/orders_erp.py         editype csv, message type orders_erp
usersys/partners/x12/PARTNERA.py           partner-specific syntax (only a syntax dict)

The folder name is the editype, the file name (without .py) is the message type. Every folder needs an __init__.py (an empty file); the folders for all editypes come with Bots. Bots 4.0 itself ships no message grammars: you get them from a plugin (the plugins on the Bots website contain grammars for many EDIFACT, X12 and other messages), from a colleague, or you write them.

Note

A grammar may be in a sub-folder, for example usersys/grammars/csv/erp/orders_erp.py. Its message type is then erp.orders_erp (folder and name joined with a dot). Put an empty __init__.py in the sub-folder too. new in 4.0 the web interface lists grammars in sub-folders.

A complete small grammar

This csv grammar describes a file with order headers (HEA) and order lines (LIN), separated by commas:

# usersys/grammars/csv/orders_erp.py
from bots.botsconfig import *

syntax = {
    'field_sep': ',',
    'quote_char': '"',
    'forcequote': 0,
    'charset': 'utf-8',
}

structure = [
    {ID: 'HEA', MIN: 1, MAX: 9999, LEVEL: [
        {ID: 'LIN', MIN: 1, MAX: 9999},
    ]},
]

recorddefs = {
    'HEA': [
        ['BOTSID', 'M', 3, 'A'],
        ['ORDERNUMBER', 'M', 35, 'AN'],
        ['ORDERDATE', 'M', 8, 'D'],
        ['BUYER', 'C', 13, 'AN'],
    ],
    'LIN': [
        ['BOTSID', 'M', 3, 'A'],
        ['LINENUMBER', 'M', 6, 'N'],
        ['ARTICLE', 'M', 14, 'AN'],
        ['QUANTITY', 'M', 10, 'R'],
    ],
}

Using parts of other grammars (imports)

Many message types share records. For example all EDIFACT D96A messages use the same segment definitions. Instead of copying, put the shared part in one file and import it. In Bots 4.0 (Python 3) the import of a file next to the grammar is written with a dot:

# usersys/grammars/edifact/ORDERSD96AUNEAN008.py
from bots.botsconfig import *
from .recordsD96AUN import recorddefs      # shared segment definitions
from .edifactsyntax3 import syntax         # optional: shared syntax

structure = [
    {ID: 'UNH', MIN: 1, MAX: 1, LEVEL: [
        {ID: 'BGM', MIN: 1, MAX: 1},
        {ID: 'DTM', MIN: 1, MAX: 35},
        {ID: 'UNT', MIN: 1, MAX: 1},
    ]},
]

A file that only holds shared parts (like recordsD96AUN.py) is not a grammar on its own; it has no structure. Bots 3 grammars wrote from recordsD96AUN import recorddefs without the dot; that does not work in Python 3. The tool bots-portusersys converts such imports for you (see Upgrade from Bots 3).

Watch out

Bots changes structure and recorddefs in memory when it reads them (it adds internal keys). Two grammars that import the same recorddefs share that changed object. This is normal and works, but do not change the imported objects yourself in a grammar file.

How Bots finds the grammar

  1. Incoming. The editype and message type come from the route (fields Fromeditype / Frommessagetype) or, for EDIFACT, X12 and TRADACOMS, from the mailbag step, which sets message type edifact, x12 or tradacoms. Bots imports usersys/grammars/<editype>/<messagetype>.py.
  2. Envelope grammar. For EDIFACT, X12 and TRADACOMS the first grammar read is the envelope grammar (edifact.py, x12.py, tradacoms.py). It describes the envelope (UNB…UNZ, ISA…IEA, STX…END). One record in it has SUBTRANSLATION: there Bots reads the real message type from the file (for example ORDERSD96AUNEAN008 from the UNH segment, or 850 plus the version 004010 from ST and GS) and continues with that grammar.
  3. Syntax is combined. The syntax that is used is built in layers: the defaults of the editype, then the syntax of the envelope grammar (named in syntax['envelope']), then the syntax of the message grammar. Details: Grammar syntax options.
  4. Outgoing. The translation (Configuration → Translations) or the mapping gives the outgoing editype and message type. Bots reads that grammar when it writes the file, and also looks for a partner-specific syntax: usersys/partners/<editype>/<frompartner>.py and then usersys/partners/<editype>/<topartner>.py. Values in these files overrule the grammar (the topartner file wins over the frompartner file). A partner file contains only a syntax dict. It is used for outgoing files and their envelopes, not for reading.
# usersys/partners/x12/PARTNERA.py   -- only for files sent to (or from) PARTNERA
syntax = {
    'ISA05': 'ZZ',
    'ISA07': 'ZZ',
    'field_sep': '|',
    'merge': False,
}

In the web interface, where a message type is shown (for example in Configuration → Translations and in the reports), it is a link with a Python icon: move the mouse over it or click it to see the source of the grammar.

How to add a grammar

  1. Choose the editype and a message type name. For a csv file from your ERP system for example editype csv, message type orders_erp.
  2. Create the file usersys/grammars/csv/orders_erp.py with a text editor. Save it as UTF-8.
  3. Write syntax, structure and recorddefs as in the example above.
  4. Check the grammar with bots-grammarcheck (next task). Expected result: OK - no error found in grammar.
  5. Use it in a route (incoming) or a translation (Configuration → Translations → Add; the message type field offers the grammars it finds).

How to check a grammar (bots-grammarcheck)

bots-grammarcheck reads a grammar with exactly the checks Bots uses in a translation. It does not need a file to translate.

  1. Open a command prompt (Windows) or a terminal (Linux) where Bots is installed (activate the virtual environment if you use one).
  2. Run the check with the editype and message type, and the config folder of your environment with -c: 
    bots-grammarcheck -cC:\edi\config x12 850004010
    bots-grammarcheck -c/srv/edi/config x12 850004010
    You can also give the path of the grammar file instead of editype and message type; Bots then takes the editype from the folder name and the message type from the file name, but still reads the grammar from the usersys of the environment: 
    bots-grammarcheck -c/srv/edi/config /srv/edi/usersys/grammars/x12/850004010.py
  3. Read the result. OK - no error found in grammar (exit code 0) or Found error in grammar: followed by the error (exit code 1).

To check all grammars, mappings and scripts of an environment at once, use bots-checkusersys -c<config> (options --processes=<number> and --json=<file>). It compiles every Python file, reads every grammar with the checks of a translation and imports every script; exit code 1 if anything failed. new in 4.0

How to make an XML grammar from a sample file (bots-xml2botsgrammar)

Writing an XML grammar by hand is a lot of work. bots-xml2botsgrammar makes a first version from a sample XML file.

  1. Get a complete sample. Use an XML file in which every element and attribute you will ever need is present (a "completely filled" file). Elements that are not in the sample are not in the grammar.
  2. Run the tool: 
    bots-xml2botsgrammar -c/srv/edi/config botssys/infile/orders/sample.xml usersys/grammars/xml/orders_partnera.py
    Add -a to make every XML element a record (by default an element without child elements becomes a field of its parent).
  3. Expect the message grammar file is written: …. The new file has structure and recorddefs; every record has MIN: 0, MAX: 99999; every field is conditional ('C'), length 256, format 'AN'; BOTSID and BOTSCONTENT are mandatory; attributes are fields named element__attribute.
  4. Edit the result. Set real MIN/MAX values (the root record MIN: 1, MAX: 1), mark mandatory fields 'M', set lengths and formats, add a syntax dict if needed.
  5. Check it with bots-grammarcheck … xml orders_partnera.
Note

The tool does not write namespaces into the grammar; an XML file with namespaces gives tags in the form {uri}name. See XML and JSON for namespaces.

Grammar syntax options

The syntax dict of a grammar holds the settings of the file format: separators, character set, envelope values, how to write XML or JSON, and more. This page lists every option Bots 4.0 reads, with its default for each editype. Look up an option here when you write a grammar or a partner-specific syntax.

In plain words

The structure of a grammar says what is in a file; the syntax says how it is written down: which character separates two fields, which ends a line, which alphabet is used. Every editype has sensible defaults, so a grammar only lists the settings that differ.

How it works

Bots builds the syntax that is used for a file from several layers. A later layer overrules an earlier one:

  1. Defaults of the editype (the tables below; in the program: defaultsyntax of the editype class in bots/grammar.py).
  2. The envelope grammar: the grammar named in syntax['envelope'] (for example usersys/grammars/x12/x12.py), if that file exists. Its syntax is used for all messages of that editype.
  3. The message grammar: the syntax of the grammar itself.
  4. Outgoing only: partner-specific syntax: usersys/partners/<editype>/<frompartner>.py, then usersys/partners/<editype>/<topartner>.py.
  5. Values already in the transaction. A value that is already set and not empty is not overwritten by the grammar. Outgoing: a value your mapping put in out.ta_info (for example out.ta_info['charset'] = 'iso-8859-1') wins. Incoming: a character set that came with the file (for example from the mail header of an attachment) wins over the grammar.
  6. Incoming EDIFACT and X12: separators, character set (EDIFACT) and version are read from the file itself (UNA/UNB, ISA). The grammar values are only a fallback.

So a setting that is the same for all your X12 messages goes into the envelope grammar x12.py; a setting for one message type into that grammar; a setting for one partner into a partner file.

Note

A mapping can change syntax for the message it writes by setting out.ta_info[...]. See Mappings. advanced Values in the dict out.syntax overrule everything for writing that message.

How to change a syntax option

  1. Find the option in the tables below and decide on which layer it belongs (all messages of the editype, one message type, one partner).
  2. Open the file: the envelope grammar (for example usersys/grammars/edifact/edifact.py), the message grammar, or create usersys/partners/<editype>/<partnerid>.py.
  3. Add the key to the syntax dict, for example 'merge': False,. Keys are case-sensitive and written exactly as in the tables.
  4. Check the grammar with bots-grammarcheck (see Grammars) and run a test file. Open the result in Outgoing and look at the file.
# usersys/partners/edifact/PARTNERB.py -- outgoing EDIFACT for PartnerB
syntax = {
    'merge': False,            # one interchange per message
    'forceUNA': True,          # always write UNA
    'UNB.S002.0007': 'ZZ',     # qualifier of the sender in UNB
    'UNB.S003.0007': 'ZZ',     # qualifier of the receiver in UNB
}

Records, fields and structure

This page explains the two main parts of every grammar: recorddefs (the fields of each record, with their length and format) and structure (which records come in which order, how often, and nested in which other record). It also covers splitting a file into messages and how Bots reports errors it finds in a file.

In plain words

Think of an order on paper. It has a header block (order number, date, buyer) and a number of item lines (article, quantity). Each block is a record; each box on the block is a field. recorddefs describes the boxes of each block; structure describes that the item lines belong under the header, at least one and at most 9999 of them.

How it works

Every line or segment of an EDI file is a record. Each record starts with a record ID (in EDIFACT and X12 the segment tag, like UNH or BEG; in your own csv files you choose it, like HEA). Bots stores the record ID in the field BOTSID. In the tree every record is a node; records that belong to another record (the lines of a header) are its children.

  1. Reading a file, Bots takes each record, looks up its ID in the structure at the current place, and checks that mandatory records are not skipped.
  2. For the record it finds, it uses recorddefs to name the fields (by position in separated formats, by position and length in fixed files, by tag in XML and JSON).
  3. After the whole file is read, every record and field is checked: counts (MIN/MAX), mandatory fields, lengths and formats.
  4. Writing, the same checks are made on the tree your mapping made; then records are sorted in the order of the structure, fields in the order of recorddefs.

recorddefs: fields

recorddefs is a dict. The key is the record ID; the value is a list of field definitions. Every record must have a field BOTSID (normally the first). Field names must be unique within a record.

A field is a list of 4 items: [name, mandatory, length, format]:

['ORDERNUMBER', 'M', 35, 'AN']          # mandatory, max 35, alphanumeric
['BUYER', 'C', (13, 13), 'AN']           # conditional, exactly 13 long
['AMOUNT', 'C', 12.2, 'N']               # number, max 12 digits, exactly 2 decimals
['REFERENCE', ('C', 5), 35, 'AN']        # repeating field: up to 5 times

A composite (a field made of sub-fields, like C507 in EDIFACT) is a list of 3 items: [name, mandatory, [sub-fields]], with at least 2 sub-fields. Sub-fields are fields as above. The name of the composite itself is not a field in the tree: in a mapping you use the names of the sub-fields.

['C507', 'M', [
    ['C507.2005', 'M', 3, 'AN'],     # date/time qualifier
    ['C507.2380', 'C', 35, 'AN'],    # the date
    ['C507.2379', 'C', 3, 'AN'],     # format code
]],
['C212', ('C', 9), [                 # repeating composite: up to 9 times
    ['C212.7140', 'C', 35, 'AN'],
    ['C212.7143', 'C', 3, 'AN'],
]],

SUBTRANSLATION

In an envelope grammar, the record where a message starts (UNH in EDIFACT, ST in X12, MHD in TRADACOMS) has SUBTRANSLATION. Its value is looked up as above and gives the message type. Then:

  1. EDIFACT: dots are replaced by underscores (90.1 becomes 90_1). X12: the version from GS08 of the group is added (850 + 004010 = 850004010).

Collision checks

For csv, fixed, idoc, EDIFACT, X12 and TRADACOMS Bots checks that the structure can be read in only one way. Two problems are refused:

  • Back-collision: an optional record can be followed by a record with the same ID at the same place, so Bots cannot tell which one it is reading. Example: AAA (optional), BBB (optional), AAA.
  • Nesting collision: a record inside a group has the same ID as a record that can follow the group at a higher level.

Records with MIN equal to MAX (for example 1 and 1) are never ambiguous. To fix a collision, make a record in between mandatory (MIN: 1) or leave out a group you do not use. Some UN/EDIFACT messages (for example INVRPT D96A) have this problem in the standard; message implementation guides (like EANCOM) make the needed choices.

How errors in a file are reported

  1. Fatal errors stop reading at once: errors in separators or envelope ([A..]), a record that is not allowed at that place ([S50]), a missing mandatory record at the end ([S51]), fixed records with a wrong length ([S52], [S53]), invalid JSON ([J..]). The file gets one error.
  2. Other errors are collected: Bots goes on reading and reports up to max_number_errors (in bots.ini, default 10) errors, then adds Found at least 10 errors.
  3. Each error starts with its code and, when known, the place: line 12 pos 4, and the record path (ST-PO1). In EDIFACT and X12, errors inside a message start with Message nr 3, type 850004010, .
  4. A file with errors is not translated (no message of it), and gets status error. You see the error text in Incoming (click the file, or the error icon) and in Process Errors. For EDIFACT and X12 a negative acknowledgement can be sent (see Acknowledgements).
  5. Errors when writing (in the outgoing message made by the mapping) have the codes [F20]-[F35], [F50], [F51] and the same [S..]/[F0..] codes without line and position. The message is in error; other messages of the same file are translated (unless KillWholeFile).

EDIFACT

EDIFACT is the United Nations standard for EDI, used mostly in Europe and in retail (with the EANCOM guidelines). This page shows how Bots reads and writes EDIFACT files (editype edifact), which grammars you need, and how to solve the usual problems.

In plain words

An EDIFACT file is one long text of segments like BGM+220+PO-1001+9'. A segment starts with a three-letter tag, + separates fields, : separates parts of a field and ' ends the segment. Several messages (orders, invoices) travel together in one "interchange", wrapped in an envelope: UNB at the start and UNZ at the end.

How it works

UNA:+.? '                                                   service string advice (optional): the separators
UNB+UNOA:3+PARTNERA:ZZ+5412345000013:14+260115:1030+1++ORDERS'   interchange header
UNH+1+ORDERS:D:96A:UN:EAN008'                                message header: type ORDERS, version D96A
BGM+220+PO-1001+9'
DTM+137:20260115:102'
NAD+BY+5412345000099::9'
LIN+1++8712345678906:SRV'
QTY+21:12'
UNS+S'
UNT+8+1'                                                     message trailer: 8 segments, reference 1
UNZ+1+1'                                                     interchange trailer: 1 message, reference 1

Reading:

  1. The route has incoming editype edifact. The mailbag step splits the file into interchanges (one UNB…UNZ each) and gives each the message type edifact (unless the route names a specific message type).
  2. Bots reads the start of the interchange: UNA (if present) gives the separators, decimal sign, escape and repetition character; UNB gives the character set (UNOA, UNOC, …) and the syntax version. Without UNA the standard separators + : ? ' are assumed (or the UNOB set 0x1D 0x1F 0x1C).
  3. The envelope grammar usersys/grammars/edifact/edifact.py describes UNB, UNG, UNH, UNE, UNZ. At UNH its SUBTRANSLATION builds the message type from UNH: S009.0065 + 0052 + 0054 + 0051 + 0057, for example ORDERS+D+96A+UN+EAN008 = ORDERSD96AUNEAN008. Bots reads that grammar for the segments of the message.
  4. Bots checks the envelope: UNB/UNZ references and message count, UNH/UNT references and segment count, UNG/UNE ([E01]-[E12]).
  5. nextmessage splits the interchange into messages (also inside UNG groups with nextmessage2); each message goes to the mapping. QUERIES give partners and references.
  6. If a confirm rule asks for it, Bots sends a CONTRL message back (see Acknowledgements).

Writing:

  1. Your mapping writes the message from UNH to UNT, including the segment count in UNT.
  2. Bots checks it with the message grammar and writes it with the separators of the syntax. Separators in the data get the escape character ? in front.
  3. The envelope step adds UNA (when the charset is not UNOA or forceUNA is set), UNB and UNZ. The interchange reference is a counter per sender (or per sender and receiver with interchangecontrolperpartner in bots.ini). With merge: True (default) all messages for the same partners of one run go in one interchange.

  1. Install the grammars: the envelope grammar edifact.py and the message grammars (for example from a plugin: Plugins → Read plugin), in usersys/grammars/edifact/.

X12

X12 (ANSI ASC X12) is the EDI standard used mostly in North America. This page shows how Bots reads and writes X12 files (editype x12), which grammars you need, and how to solve the usual problems.

In plain words

An X12 file is a series of segments like BEG*00*SA*PO-1001**20260115~: a tag, fields separated by *, and ~ at the end. The file starts with a fixed-length ISA segment that also tells which separators are used. Messages (called transaction sets, ST…SE) are grouped in functional groups (GS…GE) inside the interchange (ISA…IEA).

How it works

ISA*00*          *00*          *ZZ*PARTNERA       *ZZ*MYCOMPANY      *260115*1030*U*00401*000000001*0*P*>~
GS*PO*PARTNERA*MYCOMPANY*20260115*1030*1*X*004010~
ST*850*0001~
BEG*00*SA*PO-1001**20260115~
N1*ST*MyCompany Warehouse*92*WH01~
PO1*1*12*EA*9.95**VP*ART-100~
PID*F****Blue widget~
CTT*1~
SE*7*0001~
GE*1*1~
IEA*1*000000001~

Reading:

  1. The route has incoming editype x12, message type x12. The mailbag step splits the file into interchanges.
  2. Bots reads the ISA segment by position: character 4 is the element separator, 105 the sub-element separator, 106 the segment terminator, 83 the repetition separator (ISA11, only for version 00403 and later and only if it is not a letter or digit), 85-89 the version. A CR or LF used as segment terminator is not skipped.
  3. The envelope grammar usersys/grammars/x12/x12.py describes ISA, GS, ST, GE, IEA. At ST its SUBTRANSLATION gives ST01 (for example 850); Bots adds GS08 of the group (004010) and reads grammar 850004010.
  4. Bots checks the envelope: ISA13/IEA02, the group count in IEA01, GS06/GE02, the message count in GE01, ST02/SE02 and the segment count in SE01 ([E13]-[E21]).
  5. Each ST…SE goes to the mapping. With a confirm rule, Bots sends a 997 back (see Acknowledgements).

Writing:

  1. Your mapping writes ST to SE, including the segment count in SE01.
  2. Bots writes the message. X12 has no escape character: a separator in the data gives error [F51], unless replacechar is set.
  3. The envelope step writes ISA, GS, GE and IEA. ISA06/ISA08 are padded to 15 characters; ISA13 is a counter per sender; GS01 comes from functionalgroup; GS08 is the message type without its first 3 characters (850004010 gives 004010; 850004010VICS gives 004010VICS); GS04 has 8 digits from version 004010 on, else 6.

CSV and fixed files

Most in-house systems (ERP, warehouse, accounting) exchange data with Bots as csv files (fields separated by a character) or fixed files (each field at a fixed position). This page shows how Bots reads and writes them (editypes csv and fixed), with complete example grammars.

In plain words

A csv file is like a spreadsheet saved as text: one line per record, values separated by commas or semicolons. A fixed file has no separators at all: the order number is always in columns 4 to 23, the date in columns 24 to 31, and so on. In both, the grammar tells Bots which value is which.

How it works

csv

  1. Lexing. Bots reads the file with the grammar's charset. Each character of record_sep ends a record (the default '\r\n' accepts Windows and Linux line ends; empty lines are skipped). Each character of field_sep ends a field. A value that starts with quote_char runs to the next quote character; two quote characters inside it are one. A character after escape is taken as data.
  2. Skipping. With skip_firstline the first line(s) are dropped (column names).
  3. Record ID. The first field of each line is the record ID (BOTSID). With noBOTSID: True the lines have no record ID and Bots uses the ID of the root record of the grammar; with noBOTSID: 2 the third field is the record ID.
  4. Parsing. Each line is matched with the structure and its fields are named by position with recorddefs. Spaces around values are removed (strip_value).
  5. Messages. By default the whole file is one message for the mapping (pass_all: True). With nextmessageblock consecutive lines with the same value in a field (for example the order number) form one message. With pass_all: False each root record (with its lines) is a message.
  6. Writing is the reverse: each record is written with all its fields (empty text fields as empty values, empty number fields as 0), quoted according to forcequote, followed by record_sep. The envelope csvheader adds a first line with the field names.

fixed

  1. Lines. Bots reads the file line by line (empty lines are skipped).
  2. Record ID. BOTSID must be at the same position and with the same length in every record; Bots takes that position from the grammar. The record ID is cut from each line and stripped. With noBOTSID: True every line is the root record.
  3. Length check. The record length is the sum of the field lengths. A longer line is an error ([S53], checkfixedrecordtoolong, default on); a shorter line is accepted unless checkfixedrecordtooshort is set ([S52]).
  4. Fields. Each field is cut by its length and stripped of spaces; empty fields are left out. Text fields are not checked for length; numbers, dates and times are checked.
  5. Messages. Without nextmessage/nextmessageblock each root record with its sub-records is one message.
  6. Writing. Every field is written with exactly its length: text padded with spaces on the right (AR: on the left), numbers with leading zeros (NL/RL: left aligned, NR/RR: right aligned with spaces), empty dates and times as spaces, empty numbers as zeros. Then record_sep (default CR LF).

  1. Look at the file in a text editor: which separator, quotes, a header line, a record ID in the first column or not, the character set (UTF-8 or Windows/latin-1).

How to describe a fixed file from a specification

XML and JSON

XML and JSON are used by web shops, portals, APIs and many modern ERP systems. Bots reads and writes them with the editypes xml and json (checked against a grammar) and xmlnocheck and jsonnocheck (no checks). This page shows how elements, attributes, objects and lists become records and fields.

In plain words

In XML and JSON the data already has names: <OrderNumber>PO-1001</OrderNumber> or "OrderNumber": "PO-1001". Bots turns every element (or object) that has child elements into a record, and every element (or value) without children into a field of its parent. The grammar says which records and fields are allowed.

How it works

XML, reading

  1. Bots parses the file with Python's ElementTree (the encoding comes from the XML declaration of the file). Extra named entities can be given in extra_character_entity.
  2. The root element must be the root record of the grammar ([G50] otherwise).
  3. For each child element of a record: if it is a record in the LEVEL of that record in the structure, it becomes a child record; if it has no child elements, it is a field of the record (its text is the value); if it has child elements but is not in the structure, it is reported as [S02] Unknown xml-tag and skipped (with checkunknownentities: True).
  4. Attributes become fields with the attributemarker ('__'): attribute unit of field element Quantity is field Quantity__unit; attribute type of record element Order is field Order__type in the record Order. Attributes with an empty value are ignored.
  5. Text directly in a record element (next to its child elements) is the field BOTSCONTENT. Spaces around texts and attribute values are removed.
  6. All fields must be in recorddefs ([F01] otherwise), then the normal checks run. The whole file is one message.

XML, writing

  1. Every record becomes an element; its fields become child elements in the order of recorddefs; child records follow in the order of the structure.
  2. Fields with the attribute marker become attributes (sorted alphabetically, as in Bots 3); BOTSCONTENT becomes the text of the record element.
  3. Bots writes the declaration <?xml version="1.0" encoding="utf-8" ?> (from version, charset, standalone), then DOCTYPE and processing_instructions if set, then the elements, on one line or indented.
  4. One file per message (merge: False). Several XML messages in one file need an envelope script that makes a valid XML file (see Envelope scripts).

JSON, reading

Bots accepts five shapes; ROOT is the ID of the root record of the grammar:

ShapeExampleMessages

Inside an object: a string, number or boolean is a field (numbers and booleans become text, true becomes 'True'); an object is a child record named by its key; a list of objects is a repeated child record; a list of strings or numbers is a repeating field. null and empty strings are ignored.

JSON, writing

Each record is an object with its fields in the order of recorddefs; child records are lists under the record ID as key (with max1_as_object: an object for records with MAX: 1). The root is written as {"Order": {...}} (named_root_object: True) or as {...}. Several messages in one write give a list, one message an object (force_list always gives a list). Values are strings, except booleans (format B) and, with json_write_numericals, numbers.

How to read and write XML with namespaces

  1. Know how Bots sees namespaced names: ElementTree writes them as {uri}name, for example {http://www.example.com/orders}Order. Record IDs and field names in the grammar must use this form.
  2. Use a variable in the grammar to keep it readable: 
    NS = '{http://www.example.com/orders}'
structure = [{ID: NS + 'Order', MIN: 1, MAX: 1, LEVEL: [{ID: NS + 'Line', MIN: 1, MAX: 9999}]}]
recorddefs = {
    NS + 'Order': [['BOTSID', 'M', 256, 'AN'], [NS + 'OrderNumber', 'M', 35, 'AN']],
    NS + 'Line':  [['BOTSID', 'M', 256, 'AN'], [NS + 'Article', 'M', 14, 'AN']],
}
  3. In the mapping use the same names: inn.get({'BOTSID': NS + 'Order', NS + 'OrderNumber': None}).
  4. Writing: Bots writes prefixes ns0, ns1; to get your own prefix set 'namespace_prefixes': [('ord', 'http://www.example.com/orders')].

How to recognise different XML messages on one channel

  1. Set the route to incoming editype mailbag (or xml with message type mailbag).
  2. Create usersys/grammars/xml/mailbag.py with a list mailbagsearch. Each entry has an xpath (ElementTree path searched in the file) and a messagetype, and optionally content (the text must be equal) or tag (the found element must have this tag). The first entry that matches gives the message type: 
    # usersys/grammars/xml/mailbag.py
mailbagsearch = [
    {'xpath': './/DocumentType', 'content': 'INVOICE', 'messagetype': 'invoice_partnerb'},
    {'xpath': './/OrderNumber', 'messagetype': 'orders_partnera'},
]
# optional: extra_character_entity = {'nbsp': ' '}
  3. Run. Expected: in Incoming each file has the found message type.

How to pass XML or JSON without a full grammar

  1. Use editype xmlnocheck or jsonnocheck. A grammar file is still needed (usersys/grammars/xmlnocheck/<name>.py), but it may contain only a syntax dict or nothing at all; no structure, no recorddefs.
  2. Expect: reading, every element with children is a record and every element without children a field; nothing is checked. jsonnocheck: the root record is ROOT (defaultBOTSIDroot), or the key of a JSON {"order": {...}}.
  3. Writing xmlnocheck: fields of a record are written in alphabetical order; records in the order the mapping made them. jsonnocheck: fields sorted alphabetically, child records always lists.

Other formats

Besides EDIFACT, X12, csv, fixed, XML and JSON, Bots knows the editypes tradacoms, idoc, excel, templatehtml, raw and db, and a few special values (mailbag, database, email-confirmation). This page explains each of them: what it is for, how it is read or written, and what can go wrong.

In plain words

Not every file is a classic EDI message. Some partners still send the older UK standard TRADACOMS, SAP systems use IDocs, a customer may send an Excel sheet, and sometimes you want a readable HTML page, a file passed on untouched, or data for a database. Each of these has its own editype.

TRADACOMS

Reading. The mailbag step finds each interchange (STX … END). Separators are fixed: = after the tag (record_tag_sep), + between fields, : between sub-fields, ' at the end, ? as escape. The envelope grammar usersys/grammars/tradacoms/tradacoms.py describes STX, MHD and END; at MHD its SUBTRANSLATION gives the message type (for example TYPE.01 + TYPE.02 = ORDHDR9). Bots checks the message count in END ([E22], [E23]) and the segment count in MTR ([E24], [E25]).

Writing. The mapping builds a tree with STX at the top and the messages (MHD … MTR) under it. Bots writes each MHD message with the grammar named by its TYPE.01 + TYPE.02; the envelope step writes STX and END (values from STX.* syntax options, sender and receiver from the partners). merge is False by default.

Format codes in TRADACOMS grammars are X (text), 9 (number) and 9V9 (number with implied decimals).

idoc (SAP IDoc flat files)

An IDoc flat file is a fixed file: every record (segment) starts with the segment name, followed by SAP administration fields and the data. Bots reads it exactly like a fixed file, but longer lines are accepted (checkfixedrecordtoolong: False, because SAP cuts empty fields at the end). When writing, Bots fills in every record: MANDT and DOCNUM from the syntax, and (with automaticcount: True) SEGNUM (the number of the record), PSGNUM (the number of the parent record) and HLEVEL (the level). The grammar must have these fields; take the record layout from the IDoc documentation of your SAP system.

# usersys/grammars/idoc/orders_sap.py
from bots.botsconfig import *

syntax = {
    'MANDT': '100',
    'charset': 'iso-8859-1',
}

def sapfields():
    # a new list of new field lists for every record (see the warning below)
    return [
        ['MANDT', 'C', 3, 'AN'],
        ['DOCNUM', 'C', 16, 'AN'],
        ['SEGNUM', 'C', 6, 'AN'],
        ['PSGNUM', 'C', 6, 'AN'],
        ['HLEVEL', 'C', 2, 'AN'],
    ]

structure = [
    {ID: 'E1HEAD', MIN: 1, MAX: 1, LEVEL: [
        {ID: 'E1LINE', MIN: 1, MAX: 9999},
    ]},
]

recorddefs = {
    'E1HEAD': [['BOTSID', 'M', 30, 'AN']] + sapfields() + [
        ['ORDERNUMBER', 'M', 35, 'AN'],
        ['ORDERDATE', 'M', 8, 'D'],
    ],
    'E1LINE': [['BOTSID', 'M', 30, 'AN']] + sapfields() + [
        ['ARTICLE', 'M', 18, 'AN'],
        ['QUANTITY', 'M', 15.3, 'N'],
    ],
}
Watch out

Bots extends every field list of recorddefs when it reads the grammar. The same field list object may therefore be used only once: if two records share one list (for example SAPFIELDS = [...] added to both), reading the second record fails with list has invalid number of arguments. Use a function that returns new lists, as in the example.

excel (incoming only)

  1. Install the libraries: pip install bots-ediint[excel] (openpyxl for .xlsx/.xlsm, xlrd for .xls). changed in 4.0 .xlsx works; the type is recognised from the content, not the file name.
  2. Bots reads the first sheet only and turns it into csv text with the separators of the grammar (field_sep, quote_char, escape), then reads that as a csv file with the same grammar. The grammar is a csv grammar in usersys/grammars/excel/.
  3. Values: whole numbers without decimals (12.0 becomes 12); dates as ISO text (2026-01-15, 2026-01-15T13:45:00, a time alone as T13:45:00); booleans as 1/0; a cell error as its text (#DIV/0!); a formula as the value Excel calculated last. Empty rows at the end and empty columns at the right are dropped.

templatehtml (outgoing only)

templatehtml writes a file from a template: for example an invoice as an HTML page to mail to a partner without EDI. Install Genshi with pip install bots-ediint[templatehtml]. Templates are in usersys/grammars/templatehtml/templates/. There are two ways of working:

  1. Data object (default, has_structure: False): the grammar has only a syntax. The mapping puts what it wants in out.data (an empty object: out.data.invoicenumber = ...). The template gets data and ta_info.
  2. Tree (has_structure: True with structure and recorddefs): the mapping uses out.put() as usual; Bots checks the tree; the template gets node (the root of the tree) and ta_info. print_as_row collects repeated records into lists for table rows.

The envelope (envelope: 'templatehtml', the default) puts the messages of one file together with envelope-template; that template gets data (the list of message files) and ta_info. With template_engine: 'django' new in 4.0 Django templates are used instead of Genshi.

raw

No grammar and no checks. Incoming: inn.root in the mapping is the content of the file as bytes. Outgoing: the mapping puts bytes in out.root; Bots writes them as they are, without envelope and without merging. Mappings are in usersys/mappings/raw/. Use it to pass a file on with a few changes, or to wrap a PDF, for example.

def main(inn, out):
    out.root = inn.root.replace(b'\r\n', b'\n')    # raw to raw: change line ends

db

For database channels. Incoming: the communication script of the channel reads from the database and returns a Python object (for example a list of dicts); Bots stores it, and in the mapping inn.root is that object. Outgoing: the mapping puts any Python object (dict, list) in out.root; the outgoing database channel's script writes it to the database. No grammar, no envelope, no merging. Mappings are in usersys/mappings/db/.

mailbag, database (old), email-confirmation, test

  • mailbag: only as incoming editype of a route. The mailbag step looks at each file, splits it into EDIFACT, X12 and TRADACOMS interchanges and gives each its editype; an XML file gets editype xml with message type mailbag (see XML and JSON and Preprocessing).
  • database (old): in the list so that configurations from older Bots versions can be opened. Bots 4.0 cannot read or write it: use db.
  • email-confirmation: Bots gives this editype to the MDN mails it makes as receipt for incoming mails (see Acknowledgements). Do not use it in routes or translations.
  • test: a grammar type for the tests of Bots itself; it has a usersys/grammars/test/ folder but is not in the web interface lists.
