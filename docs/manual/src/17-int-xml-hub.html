Tutorial: an XML hub

MyCompany's web shop puts all its XML documents in one folder: new orders, cancellations and status updates. In this tutorial Bots recognises each kind of document by itself and translates each with its own mapping: orders become a pick list for the warehouse, rows in a database and an order confirmation for the customer; cancellations and status updates go into the database; and what the warehouse does goes back to the web shop as XML. At the end you add a new kind of document to the hub and handle broken files.

In plain words

One folder, many kinds of letters. Bots opens each letter, looks at what kind it is (an order, a cancellation, a status update), and sends it to the right desk. Each desk has its own form to fill in. One order is copied three times: a pick list for the warehouse, a line in the order book (a database table), and a thank-you letter for the customer. When the warehouse marks something in the order book, Bots writes a note back to the web shop.

What you will build

The web shop (id SHOP01) and MyCompany exchange XML documents that share one envelope: a root element SHOPMSG with a header MSGHEADER, and then one body element that says what the document is. Bots must find out the kind of each file itself, because they all arrive in the same folder with the same kind of name.

  1. Orders (SHOPORDERS, one or more orders per file): each order becomes lines in a csv pick list for the warehouse, rows in the table edi_order_lines, and an HTML order confirmation that is mailed to the customer.
  2. Cancellations (SHOPCANCEL): the cancelled order lines are marked CANCELLED in the table, and flagged so that MyCompany confirms the cancellation to the web shop.
  3. Status updates from the web shop (SHOPSTATUS, in an XML namespace): the payment status of an order (PAID, HOLD) is stored in the column shop_status.
  4. Status updates to the web shop: when the warehouse ships, back-orders, or a line is cancelled, the row gets send_flag = 'Y'. A second route reads these rows and writes one status document per order, in the same XML format and namespace as the web shop's own status updates.

You learn: the XML mailbag (mailbag.py), XML grammars with attributes and namespaces, several documents in one file (nextmessage), chained translations (one order, three results), the database channel in both directions, templatehtml with Genshi, xmlnocheck, how to add a document type, and what Bots does with unknown and broken files.

  3. Read a status update. The web shop tells whether an order is paid or on hold. This document is in an XML namespace: xmlns="http://shop.example.com/ns/status" on the root means that every element in the file belongs to that namespace, also when no prefix is written: 
    <?xml version="1.0" encoding="utf-8"?>
<SHOPMSG xmlns="http://shop.example.com/ns/status">
  <MSGHEADER MSGID="SHOP01.20261015.114511.000440" MSGTYPE="STS" VERSION="2.1">
    <MH_FROM ID="SHOP01" NAME="Web shop"/>
    <MH_TO ID="MYCOMPANY" NAME="MyCompany"/>
  </MSGHEADER>
  <SHOPSTATUS>
    <SS_ORDERSTATUS REQNO="7700012345601" CODE="PAID"/>
    <SS_ORDERSTATUS REQNO="7700012345602" CODE="HOLD" NOTE="Payment check"/>
  </SHOPSTATUS>
</SHOPMSG>
  4. See how Bots will read them. Bots turns every element that is a record in the grammar into a record, and every other element into fields of its parent:
    • An attribute of a record element is a field element__attribute: REQNO of <SO_ORDER> is SO_ORDER__REQNO.
    • An element without children (a "field element") gives one field for its text and one per attribute, all in the parent record: <SO_ADDRESS NAME="…" ZIP="…"/> inside SO_SHIPTO gives the fields SO_ADDRESS__NAME and SO_ADDRESS__ZIP of the record SO_SHIPTO; <SO_NOTE>text</SO_NOTE> gives the field SO_NOTE.
    • In a namespace, Bots sees the names as {http://shop.example.com/ns/status}SHOPMSG. Attributes without a prefix have no namespace, so the field is {http://shop.example.com/ns/status}SS_ORDERSTATUS__REQNO.

Part 2: Recognise the kind of document

The route that reads the drop folder gets Fromeditype mailbag and Frommessagetype mailbag. The mailbag step sees that a file starts with < and gives it editype xml and messagetype mailbag. When Bots then reads the file, it opens usersys/grammars/xml/mailbag.py and tries the rules of mailbagsearch one by one; the first rule that matches gives the messagetype, and that is the name of the grammar Bots reads the file with. See XML and JSON.

  1. Write usersys/grammars/xml/mailbag.py: 
    # Rules to recognise the document type of an XML file from the web shop.
# Bots tries the rules from top to bottom; the first rule that matches
# gives the messagetype (= the grammar usersys/grammars/xml/<messagetype>.py).
STATUS_NS = '{http://shop.example.com/ns/status}'

mailbagsearch = [
    # orders: the root element has a child element SHOPORDERS
    {'xpath': 'SHOPORDERS', 'messagetype': 'shoporders'},
    # cancellations: the root element has a child element SHOPCANCEL
    {'xpath': 'SHOPCANCEL', 'messagetype': 'shopcancel'},
    # status updates: the root element is SHOPMSG in the status namespace
    {'xpath': '.', 'tag': STATUS_NS + 'SHOPMSG', 'messagetype': 'shopstatus'},
]
  2. Understand the rules. xpath is searched from the root element with ElementTree's find():
    • 'SHOPORDERS' finds a child element SHOPORDERS of the root. Use './/SHOPORDERS' to search at any depth.
    • '.' is the root element itself. With 'tag' the found element must have exactly this name; here the root must be SHOPMSG in the status namespace. An orders file has the root SHOPMSG without namespace, so this rule does not match it.
    • With 'content' the text of the found element must be equal, eg {'xpath': './/DocType', 'content': 'CANCEL', 'messagetype': 'shopcancel'}.
    • To look at an attribute, use an ElementTree predicate in the path: {'xpath': "MSGHEADER[@MSGTYPE='CAN']", 'messagetype': 'shopcancel'}.
  3. Put specific rules first. Bots stops at the first match. If one document type contains the element another rule looks for, put the stricter rule above.
Watch out

A file that matches no rule is not translated. It gets the error Could not find right xml messagetype for mailbag.; see part 9. A file that is not well-formed XML fails before the rules are tried.

Part 3: The XML grammars

Each kind of document gets its own grammar in usersys/grammars/xml/, named as the messagetype that the mailbag gives. Editype xml checks the file against the grammar: every element must be known, mandatory fields must be there, lengths and formats must fit. (Editype xmlnocheck checks nothing and needs no structure; part 10 uses it. For documents you translate, use xml: errors then show up in Bots and not in the warehouse.)

Part 4: The hub database

The database is the "order book" between the web shop and the warehouse: one row per order line. In the test it is a SQLite file in the environment; in production it is often MySQL/MariaDB or PostgreSQL on db.example.com (see the variant at the end of this part).

  1. Make the table. Save this as shopdb_create.sql and run it, for SQLite with sqlite3 botssys/shopdb.sqlite3 < shopdb_create.sql in the environment folder (or with any SQLite tool). The same statement works on MySQL/MariaDB and PostgreSQL. 
    CREATE TABLE edi_order_lines (
    req_no        VARCHAR(20)   NOT NULL,
    line_seq      INTEGER       NOT NULL,
    order_no      VARCHAR(20)   NOT NULL,
    ordered_on    VARCHAR(8)    NOT NULL,
    article_no       VARCHAR(20)   NOT NULL,
    qty           DECIMAL(10,2) NOT NULL,
    line_price    DECIMAL(10,2),
    shipto_email  VARCHAR(80),
    line_status   VARCHAR(10)   NOT NULL DEFAULT 'NEW',
    shop_status   VARCHAR(10),
    carrier       VARCHAR(10),
    tracking_no   VARCHAR(40),
    shipped_on    VARCHAR(10),
    send_flag     CHAR(1)       NOT NULL DEFAULT 'N',
    PRIMARY KEY (req_no, line_seq)

    send_flag: N nothing to send, Y news for the web shop, S sent. line_status: NEW, CANCELLED, SHIPPED, BACKORDER (and RETURNED from part 10).
  2. Write the script of the outgoing database channel usersys/communicationscripts/shop_db_out.py. The file name must be the channel name. Every mapping that writes to the database puts a dict {'action': …, 'rows': […]} in out.root; one channel then serves all document types: 
    # Outgoing database channel shop_db_out: writes what the mappings put in out.root.
# Bots makes the connection (field Database of the channel) and commits after each call.
# db_object is {'action': ..., 'rows': [...]}; one call per translated message.


def outcommunicate(channeldict, dbconnection, db_object):
    cursor = dbconnection.cursor()
    action = db_object['action']
    for row in db_object['rows']:
        if action == 'new_order':
            # the same order sent twice by the web shop: update instead of a second insert
            cursor.execute('SELECT 1 FROM edi_order_lines WHERE req_no = %(req_no)s AND line_seq = %(line_seq)s',
                           row)
            if cursor.fetchone():
                cursor.execute('UPDATE edi_order_lines SET qty = %(qty)s, line_price = %(line_price)s '
                               'WHERE req_no = %(req_no)s AND line_seq = %(line_seq)s', row)
            else:
                cursor.execute('INSERT INTO edi_order_lines '
                               '(req_no, line_seq, order_no, ordered_on, article_no, qty, line_price, '
                               ' shipto_email, line_status, send_flag) '
                               'VALUES (%(req_no)s, %(line_seq)s, %(order_no)s, %(ordered_on)s, %(article_no)s, '
                               ' %(qty)s, %(line_price)s, %(shipto_email)s, \'NEW\', \'N\')', row)
        elif action == 'cancel':
            # cancelled by the customer: confirm it to the web shop with the next status run
            cursor.execute('UPDATE edi_order_lines SET line_status = \'CANCELLED\', send_flag = \'Y\' '
                           'WHERE req_no = %(req_no)s AND line_seq = %(line_seq)s', row)
        elif action == 'shop_status':
            cursor.execute('UPDATE edi_order_lines SET shop_status = %(shop_status)s '
                           'WHERE req_no = %(req_no)s', row)
        else:
            raise ValueError('shop_db_out: unknown action "%s"' % action)
    Bots makes the connection (the channel's Database field), so the script has no connect, does not commit, and uses %(name)s placeholders on every database. A new order that comes twice is updated, not inserted twice.

def ordered_on(inn):
    """Make YYYYMMDD from <SO_PLACED YEAR="2026" MONTH="10" DAY="15"/>."""
    year = inn.get({'BOTSID': 'SO_ORDER', 'SO_PLACED__YEAR': None})
    month = inn.get({'BOTSID': 'SO_ORDER', 'SO_PLACED__MONTH': None})
    day = inn.get({'BOTSID': 'SO_ORDER', 'SO_PLACED__DAY': None})
    return year + month.zfill(2) + day.zfill(2)


def main(inn, out):
    # Safety net: Bots uses the translation without alt when it finds none for an alt.
    # Then this mapping runs again, returns 'to_db' again, and the chain never ends.
    if inn.ta_info['alt']:
        raise ValueError('No translation for xml/shoporders with alt "%s".' % inn.ta_info['alt'])
    shipto = {'BOTSID': 'SO_SHIPTO'}

    def ship(field):
        return inn.get({'BOTSID': 'SO_ORDER'}, dict(shipto, **{field: None}))

    # the values that are the same for every line of the order
    order = {
        'order_no': inn.get({'BOTSID': 'SO_ORDER', 'SO_ORDER__ORDERNO': None}),
        'ordered_on': ordered_on(inn),
        'ship_method': ship('SO_SHIPTO__METHOD'),
        'recipient_name': ship('SO_ADDRESS__NAME'),
        'shipto_street': ship('SO_ADDRESS__STREET'),
        'recipient_city': ship('SO_ADDRESS__CITY'),
        'recipient_state': ship('SO_ADDRESS__STATE'),
        'shipto_zip': ship('SO_ADDRESS__ZIP'),
        'recipient_country': ship('SO_ADDRESS__COUNTRY'),
        'note': inn.get({'BOTSID': 'SO_ORDER', 'SO_NOTE': None}),
    }

    for line in inn.getloop({'BOTSID': 'SO_ORDER'}, {'BOTSID': 'SO_LINE'}):
        values = dict(order)
        values.update({
            'line_seq': line.get({'BOTSID': 'SO_LINE', 'SO_LINE__LINENO': None}),
            'article_no': line.get({'BOTSID': 'SO_LINE', 'SO_ITEM__ITEMNO': None}),
            'sku': line.get({'BOTSID': 'SO_LINE', 'SO_ITEM__SKU': None}),
            'qty': line.get({'BOTSID': 'SO_LINE', 'SO_ITEM__QTY': None}),
            'description': line.get({'BOTSID': 'SO_LINE', 'SO_ITEM__DESC': None}),
        })
        # put() writes nothing at all when one of the values is None: leave out the empty ones
        values = {key: value for key, value in values.items() if value is not None}
        csv_line = out.putloop({'BOTSID': 'LINE'})
        csv_line.put(dict(values, BOTSID='LINE'))

    # next translation in the chain: the same order into the database
    return 'to_db'

Watch out

When Bots finds no translation for an alt, it uses the translation without alt. If the translation to_mail is missing or not active, Bots runs shoporders_to_csv again, which returns to_db again, and so on: the run never ends (the loop check of Bots only stops a mapping that returns the same alt over and over). The check at the top of shoporders_to_csv turns this into a clear error instead: ValueError: No translation for xml/shoporders with alt "to_mail". Put such a check in the first mapping of every chain.

from bots.botsconfig import *        # for DONE
import bots.transform as transform

NS = '{http://shop.example.com/ns/status}'     # the same namespace as in the grammar
LINE_CODES = {'CANCELLED': 'CXL', 'BACKORDER': 'BO'}


def rec(name, **fields):
    """A new dict for put(): record NS+name with fields NS+field.
    Make a new dict for every put: Bots changes the dicts you give to put()."""
    record = {'BOTSID': NS + name}
    record.update((NS + key, value) for key, value in fields.items())
    return record


def main(inn, out):
    rows = inn.root                      # the list of rows that shop_db_in returned for one order
    req_no = rows[0]['req_no']
    inn.ta_info['botskey'] = out.ta_info['botskey'] = 'STATUS_' + req_no   # used in the file name

    # header: who sends, who receives, a unique id
    msg_id = 'MYCOMPANY.%s.%s' % (transform.strftime('%Y%m%d.%H%M%S'),
                                  transform.unique('shopstatus_msgid').zfill(6))
    out.put(rec('SHOPMSG'), rec('MSGHEADER', MSGHEADER__MSGID=msg_id,
                                MSGHEADER__MSGTYPE='STS', MSGHEADER__VERSION='2.1'))
    out.put(rec('SHOPMSG'), rec('MSGHEADER'),
            rec('MH_FROM', MH_FROM__ID='MYCOMPANY', MH_FROM__NAME='MyCompany'))
    out.put(rec('SHOPMSG'), rec('MSGHEADER'),
            rec('MH_TO', MH_TO__ID='SHOP01', MH_TO__NAME='Web shop'))
    out.put(rec('SHOPMSG'), rec('SHOPSTATUS'))

    has_content = False
    for row in rows:
        if row['line_status'] in LINE_CODES:
            has_content = True
            line = out.putloop(rec('SHOPMSG'), rec('SHOPSTATUS'), rec('SS_LINESTATUS'))
            line.put(rec('SS_LINESTATUS',
                         SS_LINESTATUS__REQNO=req_no,
                         SS_LINESTATUS__LINENO=row['line_seq'],
                         SS_LINESTATUS__CODE=LINE_CODES[row['line_status']],
                         SS_LINESTATUS__QTY=row['qty']))
        elif row['line_status'] == 'SHIPPED':
            has_content = True
            shipped_on = row['shipped_on']            # text YYYY-MM-DD in the table
            package = out.putloop(rec('SHOPMSG'), rec('SHOPSTATUS'), rec('SS_PACKAGE'))
            package.put(rec('SS_PACKAGE',
                            SS_PACKAGE__REQNO=req_no,
                            SS_PACKAGE__LINENO=row['line_seq'],
                            SS_PACKAGE__CARRIER=row['carrier'],
                            SS_PACKAGE__TRACKINGNO=row['tracking_no'],
                            SS_SHIPDATE__YEAR=shipped_on[0:4],
                            SS_SHIPDATE__MONTH=shipped_on[5:7],
                            SS_SHIPDATE__DAY=shipped_on[8:10]))

    if not has_content:
        # nothing the web shop needs to know (eg only NEW lines): no output file
        out.ta_info['statust'] = DONE
    • The helper rec() makes a new dict for every put(). Bots adds keys to the dicts you pass to put(); a dict kept in a module variable and used again for the next message gives the error MappingFormatError: Section without "BOTSID".
    • transform.unique('shopstatus_msgid') is a counter of Bots: every document gets a new MSGID.
    • out.ta_info['statust'] = DONE says: no output for this message (for example, only lines that are still NEW).

With nextmessage in the orders grammar, a missing ZIP is a problem of one order, but it is found while the whole file is read, so the whole file is in error. Errors found in a mapping (for example a missing translation) are per order: the other orders of the file are translated.

def show(node, level, lines):
    record = dict(node.record)
    lines.append('    ' * level + 'record ' + record.pop('BOTSID'))
    record.pop('BOTSIDnr', None)

More ideas

  • SFTP instead of folders. Real web shops drop and pick up files on an SFTP server: make shop_xml_in and shop_status_out of type sftp on sftp.example.net (see SFTP channels). Nothing else changes.
  • Confirm receipt to the web shop. Add a fourth link to the order chain (return 'to_receipt' from shoporders_to_html) with an XML grammar for a receipt document and a route part with toeditype xml.
  • Mail the operator about errors. Set up sendreportiferror in bots.ini so that a file in error (part 9) is noticed the same day. See bots.ini.
  • Different web shops. When a second shop sends the same formats, read the shop id with QUERIES (frompartner from MH_FROM__ID) and give translations a Frompartner where the shops differ. See Translations.
  • Schedule it. Run bots-engine --new every few minutes (see Scheduling runs); the status route then reports warehouse changes within minutes.
  • Test before every change. Keep the sample files of this page and compare the outputs after each change (see Acceptance testing).
