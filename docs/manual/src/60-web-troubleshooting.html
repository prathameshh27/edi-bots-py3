The web interface

The web interface (in the Bots 3 documentation called bots-monitor) is where you watch what Bots does, start runs, look at files and change the configuration. This page describes the menu, every screen and every button, and the settings in bots.ini that change how the interface looks.

In plain words

Bots does its work in the background. The web interface is the window on that work: you see which files came in, which went out, what went wrong, and you can tell Bots to run now or to try a file again. You open it in your browser, log in, and use the menu bar at the top.

How it works

The program bots-webserver serves the web interface (see First start and Command line). It reads the same database and the same folders as bots-engine, the program that does the translations and the communication. The web interface itself translates nothing: when you choose an item of the Run menu, the web server starts bots-engine for you (or places a job in the job queue, see Scheduling).

  1. You open the address of the web server, for example http://localhost:8080 (the port is [webserver] port in bots.ini), and log in. After the login Bots shows the home screen (/bots/home).
  2. The menu bar shows only the menus you have the rights for. A user who may only view sees fewer menus than an administrator. See Users and rights.
  3. Most screens are lists (incoming files, outgoing files, runs, documents, process errors, confirmations). They all work the same way: a date range, filters, sorting, pages, and a small menu per line behind the first column.
  4. The configuration screens (routes, channels, partners and so on) are the Django admin screens of Bots; they are described with each topic, for example Routes and Channels.

The home screen

The home screen (also the "about" screen and the system information) shows:

  • A title: Bots Open Source EDI Translator, or your about_title.
  • Links: the Bots documentation, the project website and commercial support; or, if you set support_url, one link to your own support with the text support_text.
  • Current user and Last login.
  • System information: webserver port, platform, machine, python version, django version, bots version, bots installation path, botsenv path, config path, botssys path, usersys path, and the database: DATABASE (alias), DATABASE_ENGINE, DATABASE_NAME, and when set DATABASE_USER, DATABASE_HOST, DATABASE_PORT, DATABASE_OPTIONS; django_db_connection if it is on. The password of the database is never shown.

How filters work

  • The date range starts at today minus maxdays (00:00:00) and ends today at 23:59:59. Change it in the filter row or in the select screen.
  • Lists of choices (route, channel, partner, editype, message type, status) have each value twice: as is (only lines with this value) and with a minus sign (- Error: all lines except this value).
  • Choosing a partner group as partner selects all partners in that group.
  • Text fields (file name, reference, error text, mapping script, content type, test indicator, command line) search for a part of the text. Type several words separated by a space: each must be present. Put a minus before a word to exclude it, for example ORDERS -TEST.
  • Number fields (index, report) find one number; a negative number excludes it.

Selections

A selection is a saved set of filters for one screen. Bots stores it as a small JSON file in botssys/.users/<user number>/selections/<screen>/<name>. Each user has his own selections; other users do not see them. A selection named default is loaded automatically when you open that screen without parameters. If you save without a name, Bots uses default; if default exists already, or the selection has dates, it uses the date and time (for example 20261015_143000). A name may contain letters, digits, - and _ only (no spaces).

The select screen (Select incoming and so on) shows all filters as a form, with Save, delete, clear, Permanent link (the address of this selection, to keep as a bookmark or to put in a custom menu) and Show selection.

How to run the engine from the menu

  1. Open the Run menu. Point at the play icon in the menu bar.
  2. Choose the kind of run.
    • Run (only new): the same as bots-engine --new: all active routes that are in the default run fetch and process new files. Point at it to choose one route (if menu_all_routes is set): only that route runs.
    • Run user-indicated rereceives (--rereceive): processes again the incoming files you marked with Rereceive.
    • Run user-indicated resends (--resend): sends again the outgoing files you marked with Resend.
    • Retry failed out-communications (--automaticretrycommunication): sends again all outgoing files whose sending failed since the last retry (not the ones marked No automatic retry). The very first time you use it, it only remembers where it is and sends nothing.
    • Run cleanup (--cleanup): removes old reports, files and logs now (see Maintenance).
  3. Read the message. Bots shows Bots-engine is started. and opens the Reports screen (or the home screen if you may not see reports). With the job queue enabled the message is OK, job added to queue.: --new or one of the other job queue messages.
  4. Wait, then refresh. The engine runs in the background; the web server does not wait for it. Use the reload button or set a refresh timer on the Reports screen until the new run is there.
Note

Only one engine runs at a time per environment. If one is running, you get Trying to run "bots-engine", but another instance of "bots-engine" is running. Please try again later. New in 4.0: the web server starts the engine with its own Python, so bots-engine does not need to be in the PATH of the web server, and the request returns at once. changed in 4.0

How to process an incoming file again (rereceive)

  1. Open the incoming files. Incoming → Incoming *, or Incoming errors.
  2. Mark the file. Point at the number of the line and choose Rereceive; for several files tick them, choose Rereceive in --- Action --- and click Run. The Re* box of the line is now ticked. Doing it again removes the mark. Rereceive All marks (or unmarks) every line of the current filter, on all pages.
  3. Fix the cause first (grammar, mapping, partner, translation), otherwise the file fails again.
  4. Run. Run → Run user-indicated rereceives. The stored copy of the file goes through its route again, without fetching anything from the partner.

Files that came from a resend have no incoming channel and can not be rereceived. From the Document-in screen you can mark the incoming file of a document with Rereceive too.

How to send an outgoing file again (resend)

  1. Open the outgoing files. Outgoing → Outgoing * or Outgoing errors.
  2. Mark the file. Point at the number and choose Resend, or use the action Resend on ticked lines, or Resend All. A file that is itself a resend (status Resend) is skipped: resend the newest line of that file.
  3. Run. Run → Run user-indicated resends. The old line gets status Resend; a new line with the new result appears, and #send counts the sends.

How to stop the automatic retry of a file

  1. Find the failed file in Outgoing errors.
  2. Choose No automatic retry in the menu of the line (only on lines with status Error), or as action on ticked lines. The status becomes No retry; --automaticretrycommunication leaves it alone. You can still resend it by hand.

How to save and use a selection

  1. Open a list, for example Incoming → Select incoming.
  2. Set the filters, for example From partner PARTNERA and Status Error.
  3. Type a name in the field Selection, for example partnera_errors, and click Save. Bots shows Selection 'partnera_errors' saved.
  4. Click Show selection to see the result.
  5. Later, choose it in the selection list of the screen. To make it the start view of that screen, save it as default.
  6. To delete it, load it and click the bin icon; confirm. Bots shows Selection 'partnera_errors' deleted.

How to keep a screen up to date

  1. Open the screen, for example All runs → Report (per run) *.
  2. Choose an interval in the refresh list next to the selection buttons, for example 5 mins. The screen reloads every 5 minutes with the same filters. Every reload counts as activity, so the session (normally ended after SESSION_COOKIE_AGE = 3600 seconds without activity, see settings.py) stays open while the browser is open.
  3. Tick No menu for a clean view on a second screen. Choose --- to stop.

How to change your password

  1. Click Change password top right, or in the Home menu.
  2. Type the old password and twice the new one, then Change my password.
  3. Expect the confirmation screen. If the link is missing, menu_changepassword = False is set, or your account has no usable password (for example a user made for a single sign-on); ask an administrator, who can set it in SysTasks → Users.

How to brand an environment (test or production)

When you have several environments (see Environments), make each one look different so nobody works in production by mistake.

  1. Open config/bots.ini of the environment in a text editor.
  2. Set the texts and images in section [webserver]: 
    [webserver]
environment_text = TEST
environment_text_color = #c00000
about_title = MyCompany EDI (test)
support_url = mailto:edi@mycompany.example
support_text = EDI support desk
logo_image = branding/logo.png
favicon_image = branding/favicon.ico
  3. Put the images in config/branding/ (a relative path is relative to the config folder). Allowed: .png, .gif, .jpg, .jpeg, .svg, .ico, .webp, at most 512 kB each.
  4. Restart bots-webserver. These values are read once, at the first request after the start.
  5. Check: TEST in red next to your logo, your favicon in the browser tab, your title and support link on the home screen. If an image is not shown, the web server log has Image of bots.ini [webserver] not used: "branding/logo.png".

Watch out

The screens of Bots are under /bots/: use /bots/incoming/?all, not /incoming/?all as the comment in the shipped bots.ini shows. A wrong address shows the empty start page.

How to make shortcuts

Shortcuts are personal or shared links, kept in the user code list shortcut (see Code lists). They can be changed without a restart.

  1. Create the menu once (superuser): click + (Create shortcuts menu) in the menu bar and save the user code type shortcut.
  2. Open the screen you want a shortcut to, with its filters.
  3. Choose Add shortcut to this page in the shortcuts menu, type a name, and save the user code that opens. The fields: leftcode = name, rightcode = address, attr1 = text added to the address, attr2 = sub menu name (custom by default; empty: no sub menu), attr8 = number of the user (empty: shown to every user).
  4. Rename the menu (optional): add a user code with leftcode menuname and the menu title in rightcode. Default title: Shortcuts.
  5. Manage them with Manage shortcuts. --- as address gives a divider line.

How to test the error report mail

  1. Set the mail settings in settings.py (MANAGERS, EMAIL_HOST and the other EMAIL_ settings) and sendreportiferror = True in bots.ini [settings]. Restart the web server.
  2. Choose SysTasks → Send test report.
  3. Expect Sending test mail succeeded. and a mail with subject testsubject. On Sending test mail failed. the web server log has the full error.

How to delete in bulk

Stop

Bulk delete can not be undone. Make a backup plugin and a copy of the database first.

  1. Choose SysTasks → Configuration → Bulk delete.
  2. Tick what to delete:
    • Delete transactions in acceptance testing (ticked by default): runs, reports, incoming, outgoing and data files of acceptance test runs.
    • Delete transactions (ticked by default): all runs, reports, incoming, outgoing and the folder botssys/data. This includes the acceptance runs.
    • Delete botssys/outfiles, Delete botssys/infiles: empty these folders.
    • Delete user code lists, Delete configuration (routes, channels, translations, partners, confirm rules), Delete all user scripts (all of usersys except charsets and the __init__.py files), Delete persist.
  3. Click Bulk delete and confirm. If you ticked configuration, code lists or user scripts, Bots first writes a backup plugin in botssys/backup/. Each part reports, for example Transactions are deleted.

Reports and documents

Bots records every run, every file it receives and sends, and every step in between. These screens show that record: the run reports, the incoming and outgoing files, the documents inside them, the process errors and the confirmations. You use them every day to check that all went well, and to find out why something did not.

In plain words

Think of a parcel service. A run is one round of the van. Incoming lists the parcels it picked up, Outgoing the parcels it delivered, Documents the letters inside the parcels. Each line has a colour: green is delivered, red is a problem. Process errors are problems with the van itself, for example a closed door at the partner (a server that did not answer).

How it works

Every time bots-engine runs, it writes:

  1. One report per run: when, what kind of run (new, rereceive, resend, retry), how many files came in and went out, how many errors. Shown in All runs → Report (per run).
  2. One incoming line (a file report) per received file, with its final status and the files made from it. Shown in Incoming.
  3. A chain of transactions per file: received, stored, parsed, split into documents, translated, merged, enveloped, sent. Each step is one line in the Details screen. The documents (split up and translated messages) are shown in Documents; the sent files in Outgoing.
  4. A process error when something fails outside a file: a channel can not connect, a script crashes. Shown in Process Errors.

All of it belongs to one run report. Reports and their lines are removed by the cleanup after maxdays days (see Maintenance).

Users and rights

Every person who uses the web interface logs in with an own user. What a user sees and may do depends on three flags (active, staff, superuser) and on permissions, given to the user directly or through a group. You need this page when you add a colleague, or when somebody misses a menu.

In plain words

A viewer may look at what came in and went out. An operator may also press "run", "rereceive" and "resend". An administrator may also change the configuration. A superuser may do everything, also install plugins and manage users. You make this happen by ticking permissions, best once per group, and then putting people in the right group.

How it works

Bots uses the user system of Django (the web framework Bots is built on). Users and groups are stored in the Bots database.

  1. Active: only active users can log in. Untick it to block a user without deleting him.
  2. Staff status: may open the configuration screens (the Django admin under /admin/). Without it the Configuration menu is not shown and the View log items in the lists are missing.
  3. Superuser status: has every permission without ticking them, and is the only one who sees SysTasks: plugins, configuration index, bulk delete, users and groups, counters, test mail, logs; and the plugin actions in the configuration lists.
  4. Permissions: per table of Bots four permissions: view, add, change, delete (for example "bots | routes | Can change routes"). Bots uses some of them for the screens outside the configuration too; see the reference below. A user has the permissions of all his groups plus his own.

New in 4.0: Django has a separate "view" permission. A user who only needs to look gets view_ permissions, not change_. When you upgrade a Bots 3 database with bots-updatedb, it gives users and groups the view permission for every table they could change, and gives every active user view_report, view_filereport and view_ta, so they keep seeing what they saw in Bots 3. new in 4.0

How to set up three groups

Make the groups once, then add users to them. You need a superuser (the first one is made at installation, see First start, or with bots-updatedb --createsuperuser).

  1. Open SysTasks → UserGroups → Add.
  2. Make the group Viewers: in Available permissions choose
    • bots | report | Can view report (run reports, logs),
    • bots | filereport | Can view filereport (incoming, outgoing, process errors),
    • bots | ta | Can view ta (documents, details, confirmations, file viewer),
    move them to Chosen permissions and click Save.
  3. Make the group Operators with the three permissions above plus
    • bots | mutex | Can change mutex (the run permission: Run menu, rereceive, resend, no automatic retry, and the route, channel and mapping columns),
    • bots | ta | Can change ta (manual confirm), if they handle confirmations,
    • optionally bots | filereport | Can delete filereport and bots | report | Can delete report (delete lines and runs).
  4. Make the group Admins with all of the above plus view, add, change and delete for routes, channel, translate, partner, partnergroep, chanpar, confirmrule, ccode, ccodetrigger, view and change for uniek (counters), and bots | translate | Can change translate also opens the source viewer for grammars and mappings.

How to add a user who may only view

  1. Open SysTasks → Users → Add.
  2. Type the user name viewer and twice a password, then Save and continue editing.
  3. Fill name and mail address if you like. Leave Active ticked, leave Staff status and Superuser status empty.
  4. Add the group Viewers under Groups and click Save.
  5. Test: log in as viewer. Expect the menus Home, Incoming, Outgoing and All runs; no Run, no Configuration.

How to add a user who may run

  1. Add the user operator as above.
  2. Add the group Operators and save.
  3. Test: the Run menu is there; in Incoming the column Re* and the Rereceive items are there.

How to add an administrator

  1. Add the user admin.
  2. Tick Staff status (needed for the configuration screens) and add the group Admins.
  3. Or tick Superuser status if this person also installs plugins, manages users and uses bulk delete. Keep the number of superusers small.
  4. Test: the Configuration menu (and for a superuser SysTasks) is there.

How to block a user or reset a password

  1. Open SysTasks → Users and click the user.
  2. To block: untick Active and save. The user can not log in; his history stays.
  3. To set a new password: click the link this form under the password field, type the new password twice, save. A user changes his own password with Change password (see The web interface).

Plugins

A plugin is a zip file with a Bots configuration: routes, channels, partners, translations, code lists, and the files that go with them (grammars, mappings, scripts, example files). You use plugins to install ready-made examples, to move a configuration from test to production, to make a backup, and to share a working setup.

In plain words

A plugin is a parcel with everything that is needed for a piece of EDI work. Making a plugin packs your setup into one file; reading a plugin unpacks it into another Bots. It adds and overwrites, it never removes. Routes arrive switched off, so nothing runs before you look at it.

How it works

Inside the zip:

  • botsindex.json: the database part. bots_version (the version that made it), plugins (a list of entries per table: channel, partner, chanpar, translate, routes, confirmrule, ccodetrigger, ccode; on request also uniek, mutex, ta, filereport, report), and files (every file with its SHA-256 check sum). Bots 2 and 3 plugins have botsindex.py instead; Bots 4.0 reads that too. changed in 4.0
  • Files under usersys/ (grammars, mappings, scripts, partner scripts, data files used by mappings) and botssys/ (for example botssys/infile/ with example files).

When Bots reads a plugin:

  1. It writes a backup plugin of the current configuration first: botssys/backup/backup_plugin_<date><time>.zip.
  2. It checks that the file is a zip and reads botsindex.json (or parses botsindex.py without running it). A plugin made by a version older than 3.4 gives a warning: its python code may be Python 2 (see Upgrade from Bots 3 for bots-portusersys).
  3. It writes the database entries, in one database transaction: if anything fails, nothing is written. An entry with the same key (route id and sequence, channel id, partner id; for a translation: from editype, from message type, alt, from partner, to partner; for a confirm rule: all its fields) is overwritten; others are added. Nothing is deleted.
  4. Every route from a plugin is set inactive. Channel paths that start with botssys are changed to the botssys of this environment.
  5. It writes the files: everything under usersys/ (except .pyc, .pyo, __pycache__ and __init__ files) and under botssys/. Existing files are overwritten. Files elsewhere (for example config/), README.md, config/bots.ini, botssys/sqlitedb/botsdb and paths that would end outside the environment are skipped. If writing files fails, the database part is undone.
  6. It reports: Plugin Bots version: 3.2.0, the lists Overwritten files and Skipped plugin files, and Plugin "x.zip" successfully installed.
Watch out

A plugin contains python code that Bots runs. Read plugins only from sources you trust, and read new plugins in a test environment first.

How to read a plugin

  1. Log in as a superuser.
  2. Choose SysTasks → Plugins → Read plugin.
  3. Choose the zip file in Plugin to read and click Read; confirm the question.
  4. Read the messages. Check the overwritten files: were these your own changes?
  5. Activate the routes you want: Configuration → Routes, tick them, action activate/de-activate.
  6. Check the channels (paths, hosts, users, passwords: a plugin from elsewhere has their values) and run a test.

How to make a plugin of everything

  1. Choose SysTasks → Plugins → Make plugin.
  2. Tick what to include (see the reference). The defaults give a normal configuration plugin.
  3. Click Make plugin. Your browser downloads bots_plugin_<date><time>.zip. Nothing stays on the server.

How to make a plugin of a few routes

  1. Open Configuration → Routes (as superuser).
  2. Tick the routes, for example all lines of orders_in.
  3. Choose the action Make bots plugin with selected entries and click the go button. The plugin has the routes, their route scripts, their channels with communication scripts, the partners used, the translations of the route (not for EDIFACT and X12 when there are several) with their mapping scripts, the local python files these import, the grammars (not the standard EDIFACT and X12 grammars), chained translations the mapping returns, and the partner scripts. Make bots plugin, skip translate (grammars, mappings) leaves the translations out.
  4. Expect a download named bots_plugin_routes_<name>_<date><time>.zip (the name only when you selected one entry).

The same action exists in the other configuration lists (channels, partners, translations, code lists and code list types; not counters). In Translations there are also Make translate plugin (mapping(s) without grammars) and Make grammar plugin (grammars only).

How to make a backup plugin

  1. Choose SysTasks → Plugins → Make backup plugin.
  2. Expect Backup plugin "…/botssys/backup/backup_plugin_20261015143000.zip" is written successful. It has the database configuration, the code lists (unless codelists_in_plugin = False) and all of usersys with the character sets. It stays on the server; copy it to a safe place. Bots also makes one before reading a plugin, before reading a configuration index and before a bulk delete of configuration.

How to keep the configuration in version control (configuration index)

A configuration index is the database part of a plugin as a readable JSON file, usersys/index.json. Put usersys under version control (for example git) and every change in routes or channels becomes visible as a change of that file.

  1. Write the index: SysTasks → Configuration → Make configuration index, or on the command line: 
    bots-plugoutindex -c/srv/bots/config
    bots-plugoutindex -cC:\bots\config
    Expect Bots index written: .../usersys/index.json. It contains channels, partners, translations, routes, confirm rules and (unless codelists_in_plugin = False) code lists; no files and no transactions.
  2. Commit usersys in your version control.
  3. To load an index into an environment (for example after a checkout): SysTasks → Configuration → Read configuration index → Confirm read. Bots reads usersys/index.json (if missing: the old usersys/index.py) after a backup plugin, all or nothing. Routes are set inactive, as with a plugin. The confirmation screen mentions index.py; in 4.0 index.json is read first.

An index of Bots 3 (index.py) can be converted:

bots-index2json -c/srv/bots/config /srv/bots/usersys/index.py /srv/bots/usersys/index.json

Expect Converted bots index to json: …. This imports (runs) the old python file: use it only on your own files. Reading an index.py gives the warning Bots index python import is deprecated and will be removed in python 3.15.

How to share a plugin

  1. Make a plugin of the routes you want to share.
  2. Open the zip and check botsindex.json: remove host names, user names and passwords of channels (fields host, username, secret), mail addresses and real partner identifiers, or replace them with examples such as sftp.example.net and PARTNERA.
  3. Remove example files under botssys/infile/ that contain real data.
  4. Add a README.md (it is ignored when reading) that says what the plugin does and which routes to activate.

Troubleshooting method

When something goes wrong, Bots almost always tells you what and where. This page gives a fixed order of places to look, a decision tree, the debug settings, how to reproduce a problem safely with an acceptance test, and how to report a problem so others can help.

In plain words

Start at the top and work down: did the run happen, did a connection fail, did a file fail, did a file get lost on the way? Each question has its own screen. Read the error text slowly: it nearly always names the record, the field, the line and the position. Only when the screens do not tell you enough, turn on more logging.

How it works

Bots writes what happens in three places:

  1. The database, shown in the web interface: the run report, incoming and outgoing lines with their status and error text, process errors. See Reports and documents.
  2. The log files in botssys/logging/: engine/, webserver/, dirmonitor/, jobqueue/. See Logging.
  3. The console (the terminal window) when you start a program by hand: the same log lines, and the protocol debug output of FTP, SMTP, POP3, IMAP and HTTP.

Decision tree

The same tree in words:

  1. No new run in Reports? The engine did not start or stopped at once. Check the scheduler (Scheduling), run bots-engine by hand, read the end of the engine log. Typical: another engine is running, the database is locked, the database is not reachable, bots.ini or settings.py has an error.
  2. Process errors? Read the error: most are connection errors (host, port, user, password, folder, certificate) or an error in a communication or route script. Turn on the protocol debug of that channel type and run the route by hand.
  3. Files in error? The error text tells you the kind (code in brackets, see Error messages). Open Details: an error at Infile or Parsed is about reading the file (grammar, separators, character set); at Document-in it is about the translation (translation not found, mapping error); at Outfile or Merged it is about writing (outgoing grammar, envelope); at Send it is about sending.
  4. Files stuck? A result was made that no route part sends. Compare partners, editype and message type of the last step with the filters of the route parts with an outgoing channel.
  5. #in is 0 although you expected files? The incoming channel looked in the wrong place or with the wrong file name mask, the files were already taken by another process, or the route is not active or not in the default run. Look in the engine log for the line Start communication channel in: ... and the number of files.

How to get more information

  1. Open config/bots.ini of the test environment.
  2. Set the debug settings you need in [settings] (see the reference), for example: 
    [settings]
debug = True
log_file_level = DEBUG
mappingdebug = True
get_checklevel = 2
ftpdebug = 2
  3. Run the route by hand so you also see the console output: 
    bots-engine -c/srv/bots/config --new orders_in
    bots-engine -cC:\bots\config --new orders_in
    If the file was received before, mark it for rereceive and run bots-engine --rereceive.
  4. Read the console and the new engine log. With debug = True each error text in the web interface also has the python trace.
  5. Set the settings back. Debug output slows Bots down and makes large logs; get_checklevel = 2 is slow.
Tip

In a mapping script, inn.root.display() at the start of main prints the incoming message as Bots sees it, and out.root.display() at the end prints the outgoing tree. print() also works; the output appears on the console when you run the engine by hand. See Mappings.

How to reproduce a problem with an acceptance test

An acceptance test runs your real routes on files from a folder, with no communication to partners, a frozen clock and counters that do not move. So a run can be repeated as often as you like and gives the same output. See Acceptance testing for the full description.

  1. Use a test environment, never production (see Environments). A plugin of the route (Plugins) moves the configuration.
  2. Download the failing file from the file viewer (Received step, Download) and put it in a folder, for example botssys/infile/orders/.
  3. Set the test path of the incoming channel (Acceptance test path, field testpath) to that folder, and of the outgoing channel to a folder such as botssys/outfile/orders/.
  4. Switch on acceptance mode in bots.ini: 
    [acceptance]
runacceptancetest = True
  5. Run bots-engine --new orders_in. In acceptance mode channels use their test path, nothing is archived, files are not removed from the test folder, the date and time are always 2013-01-23 01:23:45, and the run is marked Acceptance in Reports.
  6. Change and run again until it works. Optionally a script usersys/routescripts/bots_acceptancetest.py with functions pretest and posttest prepares folders and compares the output.
  7. Clean up: SysTasks → Bulk delete → Delete transactions in acceptance testing, and set runacceptancetest = False.
Note

New in 4.0 is [settings] channels_use_testpath = True: every channel uses its test path (a channel that would connect elsewhere and has no test path is not run), but the clock and counters work normally. Use it for a test environment that must never reach a partner. new in 4.0

How to report a problem

  1. Write down what you did and what you expected, and what happened instead.
  2. Copy the system information from the home screen: bots version, python version, django version, platform, database engine.
  3. Copy the complete error text (with debug = True it includes the python trace).
  4. Add the engine log of that run (View log → Download).
  5. Add the smallest file that shows the problem, with real names, numbers and addresses replaced by examples (PARTNERA, MYCOMPANY).
  6. Add the configuration: a plugin of the route (Make bots plugin with selected entries), or the grammar and mapping files. Remove host names, user names and passwords from botsindex.json first.
  7. Send it to your own support (the link on the home screen when support_url is set), or to the Bots community and commercial support listed on the home screen.
Stop

Never send settings.py, bots.ini with passwords, a whole database or the All transaction files plugin option to a public place: they contain passwords and the data of your partners.

Error messages

This page lists the error messages of Bots 4.0.0, taken from its code, with what each one means and how to fix it. Use your browser's search (Ctrl+F) with the code in brackets, for example [F02], or with a few words of the message.

In plain words

An error message tells you three things: what kind of problem (the word before the colon), which rule was broken (the code in brackets, if there is one), and where (record, field, line, position). Find the message here, read what it means, and follow the fix. Words between < and > are filled in by Bots, for example <record> becomes BGM.

How it works

An error text in the web interface looks like this:

MessageError: Message nr 1, type ORDERSD96AUNEAN008, [F02] line 5 pos 12: Record "UNH-BGM" field "1004" is mandatory.
Message nr 1, type ORDERSD96AUNEAN008, [F05] line 7 pos 3: Record "NAD" field "3036" too big (max 35): "...".
  1. The kind (the python class of the error) comes first: InMessageError (reading a file), MessageError (one or more errors in the content of a file, listed one after the other), OutMessageError (writing), GrammarError, TranslationNotFoundError, MappingFormatError, MappingRootError, CodeConversionError, CommunicationError (and CommunicationInError, CommunicationOutError), ScriptError, BotsImportError, ScriptImportError, PluginError, BotsConfigError, BotsInitError, DbConnectError, PanicError, TraceError and others. As in Bots 3 the text does not show the python module name.
  2. The code in brackets, when there is one. The letter tells the area:
    LetterArea
    AReading the file at the lowest level: start, end, separators, character set (EDIFACT, X12, Excel).
    MSplitting a file with several interchanges (mailbag).
    SStructure: records missing, unknown, in the wrong place, too often.
    FFields: mandatory, too long, too short, not a number, not a date. F01 to F19 and F40 to F47 while reading, F20 to F35 and F50, F51 while writing.
    EEnvelope checks: references and counts of UNB/UNZ, UNH/UNT, UNG/UNE, ISA/IEA, GS/GE, ST/SE, END, MTR.
    GThe file does not start with the root record of the grammar.
    JJSON content.
  3. The message with record, field, line and position. Content errors are collected per file (up to max_number_errors, default 10) and each starts with Message nr <n>, type <messagetype>,.
  4. With [settings] debug = True the python trace follows, which tells a developer where in the code it happened.

Where you see it: errors of a file in Incoming, Outgoing and Details; errors of channels and scripts in Process Errors; start-up errors on the console and in the engine log; errors of the web interface at the top of the screen. See Reports and documents.

How to look up an error

  1. Copy the code in brackets, or the first words after the code.
  2. Search this page (Ctrl+F). Several messages that differ only in one word are in one row, separated by /.
  3. Read "What it means" and open the linked page of the topic.
  4. Go to the place the message names: open the file in the file viewer, go to the line and position, or open the grammar or mapping at the record and field.
  5. Fix, then process again (rereceive for incoming files, resend for outgoing). See Troubleshooting method when the message is not here.

FAQ

Short answers to the questions newcomers ask most, each with a link to the page that explains it in full.

In plain words

If your question is "why did this file fail", start with Troubleshooting method and Error messages. The questions below are about how Bots works and how to do common things.

Basics

What is the difference between a route, a channel and a translation?

A channel is a place to get files from or put files to: a folder, an FTP or SFTP server, a mailbox, a database. A translation says which mapping script turns one kind of message into another (for example X12 850 into a csv for your ERP). A route ties them together: from this channel, read files of this editype, translate, send to that channel. See How Bots works, Routes, Channels, Translations.

What are "editype" and "message type"?

The editype is the family of the format: edifact, x12, csv, fixed, xml, json and others. The message type names the grammar inside that family, for example 850004010 (X12 850, version 004010) or ORDERSD96AUNEAN008. See Grammars and Glossary.

Where do I get grammars for EDIFACT and X12?

From the plugins with standard grammars (read them with SysTasks → Plugins → Read plugin), or write them yourself. See Grammars, EDIFACT, X12 and Plugins.

How do I make Bots run automatically?

Start bots-engine from cron (Linux) or the Windows task scheduler, every few minutes; or let bots-dirmonitor start a route when a file arrives in a folder. Keep bots-webserver running as a service. See Scheduling.

How do I run only one route?

On the command line add the route id: bots-engine --new orders_in. In the web interface set [webserver] menu_all_routes and choose the route under Run → Run (only new). Routes with Not in default run run only this way. See Command line and The web interface.

Can two engines run at the same time?

Not in one environment: a second engine stops with "another bots-engine is running" (exit code 3). Different environments on one machine each need their own [settings] port. The job queue makes runs wait for each other instead of failing. See Scheduling and Environments.

Can I have a test and a production Bots on one machine?

Yes: each environment has its own config, botssys and usersys folders, database, web server port and engine port. Show environment_text = TEST to see the difference. See Environments and How to brand an environment.

Which database should I use for Bots?

SQLite (the default) is fine for most installations. Use MySQL/MariaDB, PostgreSQL or SQL Server when you have high volumes or already run such a server. See Databases.

Daily work

How do I process a received file again?

Mark it with Rereceive in Incoming, then Run → Run user-indicated rereceives. Bots uses its stored copy; nothing is fetched from the partner. See How to process an incoming file again.

How do I send a file again?

Mark it with Resend in Outgoing, then Run → Run user-indicated resends. See How to send an outgoing file again.

Does Bots try again when sending fails?

Within one run a channel tries to connect several times ([settings] maxconnectiontries). Outgoing files that still failed are sent again by a run with --automaticretrycommunication (schedule it, or use the Run menu). For incoming channels, Max failures lets a number of failed runs pass before a process error is reported. See Channels and Scheduling.

What does status "Stuck" mean?

A result was made but no route part picked it up to send it, usually because the filters of the outgoing route part (partner, editype, message type) do not match. See Statuses and colours.

Why was my file not picked up?

Check that the route is active and in the default run, that the path and file name mask of the incoming channel match the file, and that no other program took the file first. The engine log shows each channel and the number of files. See Decision tree and File channels.

What does "Translation not found" mean?

No active translation fits the editype, message type, partners and alt of the document. Check the exact message type in the error and add or correct the translation. See Translations and Error messages.

How do I see the content of a file?

Click the file name in Details (or the number of a line, then the file). The viewer can lay out EDIFACT, X12, XML and JSON and download the file. See The file viewer.

How do I find what happened to one order?

Search on its number in Document-in or Document-out, field Reference. The mapping must set the reference (botskey). See How to follow one order.

What is the "Index" number on every line?

The unique number of the file or step in the database (idta). Incoming and outgoing lines, the details screen and the logs refer to it; use it when you ask for help.

How long does Bots keep files and reports?

Reports, the steps of files and the stored data files: maxdays (30). Archives of channels: maxdaysarchive (180), or per channel. The cleanup runs at the first run of each day (whencleanup = daily). See Maintenance.

How do I get a mail when something goes wrong?

Fill MANAGERS and the EMAIL_ settings in settings.py, set sendreportiferror = True in bots.ini, and test with SysTasks → Send test report. See How to test the error report mail and settings.py.

How do I send or check acknowledgements (997, CONTRL, MDN)?

With confirm rules: they say for which routes, channels, partners or message types an acknowledgement is asked or sent. The results are in All runs → Confirmations. See Acknowledgements and Confirm rules.

Can I test without sending anything to my partners?

Yes: an acceptance test ([acceptance] runacceptancetest = True) uses the test path of each channel, freezes date and counters and archives nothing. For a whole test environment channels_use_testpath = True (new in 4.0) keeps every channel local. See Acceptance testing and How to reproduce a problem.

Administration

How do I give a colleague read-only access?

Add a user without staff status and give the permissions view_report, view_filereport and view_ta (best through a group). See How to add a user who may only view.

How do I move a configuration from test to production?

Make a plugin of the routes in test (Make bots plugin with selected entries) and read it in production. Routes arrive inactive; check channels and passwords, then activate. See Plugins.

Is it safe to read a plugin?

A plugin contains python code and overwrites entries and files with the same name. Read only plugins from sources you trust, and in a test environment first. Bots makes a backup plugin before reading. See Plugins.

Why are my routes inactive after reading a plugin?

On purpose: so nothing runs before you have checked the channels. Activate them in Configuration → Routes with the action activate/de-activate.

Do my Bots 3 grammars and mappings work in 4.0?

Bots 4.0 runs on Python 3. Most grammars work unchanged; mappings and scripts written for Python 2 must be converted. bots-checkusersys reports problems, bots-portusersys converts. See Upgrade from Bots 3.

How do I see more detail about an error?

Set debug = True (python trace in the error), log_file_level = DEBUG, mappingdebug, readrecorddebug, and the protocol debug of the channel type in bots.ini, in a test environment, and run again. See How to get more information.

The web interface says "Bots-engine is started." but nothing happens. Why?

The engine stopped at its start (locked or unreachable database, another engine running, configuration error). Read the engine log or run bots-engine in a terminal. See Troubleshooting method.

Where are the log files?

In botssys/logging/: engine/, webserver/, dirmonitor/, jobqueue/. A superuser opens them with SysTasks → Logs; View log in a line opens the log of that run. See Logging.

How do I put our own name, logo and support address on the screens?

With about_title, support_url, support_text, logo_image, favicon_image and environment_text in [webserver] of bots.ini; restart the web server. See How to brand an environment.

Can I add my own links to the menu?

Yes: section [custommenus] in bots.ini for everybody, or the shortcuts menu (stored in the code list shortcut) per user. See How to add a custom menu and How to make shortcuts.

I lost the password of the only superuser. What now?

On the server run bots-updatedb --createsuperuser for the environment (it asks a name and password) and log in with the new user. See Users and rights and Command line.
