Welcome

This is the manual of Bots EDI Translator, version 4.0.0. It tells you what Bots does, how to install it, how to set it up for your partners, and how to keep it running. Start here if you are new to Bots or to EDI.

In plain words

Your company and its partners exchange orders, invoices and delivery notes as files. Each side wants these files in its own layout. Bots picks up the files, rewrites them into the layout the other side wants, and delivers them. It keeps a record of every file, so you can see what came in, what went out, and what went wrong.

How it works

What Bots is

Bots is a program that receives, translates and sends business documents. It is open source (GNU GPL version 3) and written in Python. Version 4.0.0 runs on Python 3.10 or newer, on Windows and on Linux.

Bots has three parts that you will meet all the time:

  • The engine (bots-engine): the program that does the work. Each time it runs, it fetches files, translates them and sends the results. It runs, finishes and stops. You start it by hand, from the web interface, or on a schedule.
  • The web interface (bots-webserver): the screens in your browser where you set up Bots and look at the results.
  • Your own files: the configuration (config), your grammars and mappings (usersys) and the data and database (botssys). Together these are an environment.

What EDI is, in five sentences

EDI (Electronic Data Interchange) is the exchange of business documents, such as orders and invoices, between companies as structured files instead of paper or e-mail text. Both sides agree on a standard that fixes the layout of each document: in North America this is mostly X12 (an order is an "850"), in Europe and elsewhere mostly EDIFACT (an order is "ORDERS"). Your own systems (the ERP) usually work with simpler layouts, such as csv, fixed-length records, xml or json. A translator such as Bots converts between the standard layout of the partner and the layout of your own systems. Files are wrapped in an envelope with the sender, the receiver and a control number, and the receiver often sends back an acknowledgement to confirm it got them.

How Bots works

This page follows one run of the engine from start to end: how files come in, how they are translated, enveloped and sent, and what Bots writes in its database on the way. Read it once before you set up your first route; it explains most of what you see later in the web interface.

In plain words

Think of a sorting office. A channel is a mailbox: Bots empties the incoming ones and fills the outgoing ones. A route says which mailbox to empty, what to do with the letters, and which mailbox to put the result in. For each letter Bots keeps a log line, and at the end of the day it writes a summary.

How it works

One run of bots-engine goes like this:

  1. Start. The engine reads the configuration (bots.ini, settings.py), connects to its database, and makes sure no other engine runs for this environment (it opens a local port, [settings] port, default 28081). If the last run was cut off (power failure, killed process), it first does a crash recovery.
  2. Choose the routes. With no route names on the command line, the engine runs every route that is Active and not Not in default run, in alphabetical order of the route name. A route with several parts (same name, different Sequence) runs its parts in order.
  3. Receive. For each route part with an Incoming channel, Bots runs that channel: it reads the files from a folder, an FTP or SFTP server, a mailbox, a database or a script, and stores a copy of each file in botssys/data. The route then gives each received file its editype and messagetype (the kind of file, see the glossary), and if set, its partners.
  4. Split (mailbag). For the editypes edifact, x12, tradacoms and mailbag, a file can hold several interchanges. Bots splits it into one file per interchange first.
  5. Translate. What happens next depends on the field Translate of the route:
    • Translate: Bots reads the file with the incoming grammar (the description of the file layout) and checks it. It splits the file into messages (documents). For each message it looks up a translation rule that says which mapping script to use and what to make. The mapping script copies the data into a new message, which Bots writes with the outgoing grammar.
    • Pass-through: the file is not read; it goes to the outgoing channel as it is.
    • Parse & Pass-through: Bots reads and checks the file with its grammar, but sends the original.
    • Nothing: the files of this route part are only received.
  6. Envelope and merge. Translated messages for the same partner and the same kind are put together (merged) into one file, and Bots adds the envelope: for X12 the ISA and GS segments with control numbers, for EDIFACT the UNB segment. csv, xml and json files get no envelope by default.
  7. Send. The outgoing files are passed to the Outgoing channel of the route part, which writes them to a folder or sends them to a server or mailbox. With Defer ticked, sending waits for a later route part that uses the same channel.
  8. Acknowledgements. If a confirm rule says so, Bots sends an acknowledgement for received files (X12 997, EDIFACT CONTRL, e-mail MDN), or marks sent files as waiting for one.
  9. Report. At the end Bots traces every received file through all its steps, writes a file report per file and one run report, and, if set in bots.ini, sends an error report by e-mail. Then it cleans up old data (once a day, whencleanup).

How the engine ends

The engine prints the run report and ends with an exit code that a scheduler can check:

Exit codeMeaning
0The run had no errors.
1A system error: wrong command line, no database connection, a severe error in Bots.
2The run went through, but there were errors in files or process errors.
3Nothing was done: another engine is running for this environment, or the database has no engine tables.

new in 4.0 The engine always ends. If a library or a user script leaves a thread running, the engine waits at most [settings] maxsecondsexit seconds (default 30), writes what is still running to the log, and ends anyway.

How to follow one file through a run

  1. Open Incoming in the menu bar (the icon with the tooltip Incoming). Each line is one received file of the latest runs.
  2. Look at the status column: a green mark is Done, a red one is Error.
  3. Click the number (the idta) at the start of the line to open the detail screen. It shows the tree of the file: received, parsed, the messages in it, the translated messages, the outgoing file, and its sending, each with its idta, status and error text.
  4. Click a file name in that tree to see the content of the file at that step.
  5. Open All runs → Report (per run) to see the counts of the whole run.

Glossary

The words of Bots and of EDI that this manual uses, in alphabetical order. Other sections link here the first time they use a term.

In plain words

EDI has many short codes and Bots has its own words for its parts. When a word on a screen or in an error message is not clear, look it up here.

How it works

Each entry gives the meaning in one or two sentences and, where useful, the place in Bots where you meet it. Words in code are names of fields, settings or files.

Terms

997
The X12 Functional Acknowledgment: the message a receiver sends back to say an X12 group arrived and whether it was correct. Bots can send one for each received group, and can wait for one for each sent group. See Acknowledgements.
acceptance test
A run in which Bots does not talk to the outside world: each channel uses its Acceptance test path (a folder), and the clock and the counters are frozen so that every run gives the same output. Switched on with [acceptance] runacceptancetest = True in bots.ini. See Acceptance testing.
acknowledgement
A message that confirms the receipt of another message. In Bots: X12 997, EDIFACT CONTRL and e-mail MDN. Bots calls this a confirmation.
alt (alternative translation)
A free text that selects one of several translations for the same editype and messagetype. A route can set it, and a mapping can return it to start a second translation of the same message (chained translation).
BOTSID
The field in a grammar and in a mapping that holds the record ID (for example ST, BEG, UNH, or HDR in a csv file). Every record in a mapping is addressed with it: {'BOTSID': 'BEG', 'BEG03': None}.
botskey
A key that a mapping sets for a message, usually the order or invoice number (out.ta_info['botskey'] = ...). It is shown as the reference of the document in the web interface and can be used in outgoing file names ({botskey}).
bots.ini
The main configuration file of an environment, in the config folder: sections such as [settings], [webserver], [jobqueue], [directories]. See bots.ini.
botssys
The folder of an environment where Bots keeps its working data: the received and made files (data), the logs (logging), the SQLite database (sqlitedb/botsdb) and the files of the web interface (static). By convention also infile and outfile for test files. See Environments.
channel
A way in or out of Bots: a folder, an FTP, FTPS or SFTP server, a mailbox (POP3, IMAP4, SMTP), HTTP(S), a database, or a script. A channel is either in or out. Set up in Configuration → Channels. See Channels.
channels_use_testpath
new in 4.0 A setting in bots.ini ([settings]) for a test environment: every channel reads and writes its Acceptance test path instead of the real server; a channel that would connect to another machine and has no test path is not run. Unlike an acceptance test, the clock and the counters run normally.
code list (user code)
A table of codes that a mapping can look up, for example your unit codes and the partner's unit codes. Set up in Configuration → User Codes list. See Code lists.
communication script
A Python file in usersys/communicationscripts with the same name as a channel. It changes how that channel works, or, for type communicationscript and db, does the whole communication. See Communication scripts.
config
The folder of an environment with bots.ini and settings.py. Every command of Bots is told which one to use with -c<folder> or the environment variable BOTS_CONFIG_DIR.
confirm, confirmation, confirm rule
Bots' word for acknowledgements. A confirm rule says for which files Bots asks for or sends a confirmation (by route, channel, partner or messagetype). The screen All runs → Confirmations shows which sent files are confirmed. See Confirm rules.
CONTRL
The EDIFACT acknowledgement message, the EDIFACT counterpart of the X12 997.
counter
A number that Bots keeps in its database and raises each time it is used: interchange control numbers, message numbers, the * in file names. Seen and changed in SysTasks → View/edit counters. See Counters.
csv
A text file with one record per line and the fields separated by a character such as a comma or semicolon. An editype in Bots. See csv and fixed.
defer
A field of a route part: the outgoing files are made ready but not sent yet; a later route part with the same outgoing channel sends them all together.
directory monitor (dirmonitor)
A program, bots-dirmonitor, that watches folders and starts a route as soon as a file arrives, instead of on a schedule. See Scheduling.
EDI
Electronic Data Interchange: the exchange of business documents between companies as structured files. See Welcome.
EDIFACT
The international EDI standard of the United Nations (UN/EDIFACT). Messages have six-letter names (ORDERS, INVOIC, DESADV, CONTRL), segments end with ' and fields are separated by +. See EDIFACT.
editype
The kind of file, which decides how Bots reads and writes it: csv, db, database (old), edifact, email-confirmation, excel (incoming only), fixed, idoc, json, jsonnocheck, mailbag, raw, templatehtml, tradacoms, xml, xmlnocheck, x12. Grammars and mappings are stored in a folder per editype.
engine
The program bots-engine that receives, translates and sends. It runs once and stops. See How Bots works.
envelope
The header and trailer around one or more messages that say who sends, who receives, and give a control number: ISA/GS for X12, UNB for EDIFACT, STX for Tradacoms. Bots makes the envelope of outgoing files and reads it for incoming files. See Envelopes.
envelope script
A Python file in usersys/envelopescripts/<editype> that changes or replaces the envelope Bots makes. See Envelope scripts.
environment
One complete, separate Bots setup: a config, a usersys and a botssys folder, usually side by side in one environment directory. Test and production are two environments. See Environments.
extra (install option)
An optional part you choose when you install Bots with pip, written in square brackets: bots-ediint[sftp,mysql]. It installs the Python libraries a feature needs. See the list of extras.
field
One value in a record, such as an order number. In a grammar each field has an ID, mandatory or not, a length and a format.
filereport
The database table with one row per received file and its overall result; shown in Incoming and Outgoing.
fixed
A text file in which every field has a fixed position and length. An editype in Bots.
functional group
In X12, the GS ... GE envelope around messages of one kind. GS01 holds the functional identifier code, for example PO for orders and IN for invoices; in Bots this is the syntax parameter functionalgroup of the grammar.
grammar
A Python file that describes a file layout: the records, their order (structure), the fields of each record (recorddefs) and settings (syntax). Stored in usersys/grammars/<editype>/<messagetype>.py. Bots reads incoming files and writes outgoing files with grammars. See Grammars.
idta
The number of a row in the ta table: every step of every file or message has one. It is the number you see on the left in Incoming and in the detail screen, and the file name under botssys/data.
interchange
One envelope with its content: in X12 from ISA to IEA, in EDIFACT from UNB to UNZ. A file can hold several interchanges; Bots splits them (see mailbag).
ISA / GS / ST
The three levels of an X12 file. ISA ... IEA is the interchange envelope (sender, receiver, control number, test or production). GS ... GE is the functional group. ST ... SE is one message (transaction set), for example an 850 order.
job queue
A program, bots-jobqueueserver, that takes requests to run the engine and runs them one after the other, so that runs never overlap. See Scheduling.
mailbag
An editype for a file with several interchanges, possibly of different standards. It is also the step in which Bots splits edifact, x12 and tradacoms files into one file per interchange.
mapping (mapping script)
A Python file with a function main(inn, out) that copies data from the incoming message (inn) to the outgoing message (out). Stored in usersys/mappings/<editype of the incoming file>/. See Mappings.
MDN
Message Disposition Notification: an e-mail that confirms another e-mail was received. Bots can ask for one and send one for mail channels.
merge
Putting several translated messages for the same receiver into one outgoing file under one envelope. Controlled by the syntax parameter merge of the outgoing grammar.
message (document)
One business document: one order, one invoice. A file can hold many. In X12 a message is a transaction set (ST ... SE), in EDIFACT UNH ... UNT.
messagetype
The name of the grammar to use within an editype, for example 850004010 (X12 850, version 004010), ORDERSD96AUN (EDIFACT ORDERS D.96A), or orders_erp for your own csv layout. For incoming EDIFACT and X12 files the route uses the messagetype edifact or x12: Bots finds the real messagetype in the file.
mpath
The path to a record or field in a mapping, written as a list of dicts from the top record down: inn.get({'BOTSID': 'HDR'}, {'BOTSID': 'LIN', 'ITEM': None}).
nextmessage
A part of a grammar that tells Bots where one message ends and the next begins in an incoming file, for example at every HDR record in a csv file.
partner
A company you exchange EDI with, with an ID (for example PARTNERA) that Bots matches with the IDs in envelopes and that routes, translations and confirm rules can select on. Partners can be put in partner groups (for example Retailers). See Partners.
pass-through
A route that receives a file and sends it on without translating it (Translate = Pass-through). Parse & Pass-through first checks the file with its grammar.
plugin
A zip file with configuration (routes, channels, partners, translations ...) and the files of a usersys, to move a setup between environments or to install examples. Read and made in SysTasks → Plugins. See Plugins.
preprocessing
A step before the translation that changes incoming files, for example unzipping, or extracting text from a PDF. See Preprocessing.
process error
An error of Bots itself rather than of a file, for example a channel that cannot connect. Shown in All runs → Process Errors.
record (segment)
One line or group of fields in a file. EDI standards call it a segment (BEG, PO1, UNH, NAD). In a grammar every record has an ID, the BOTSID.
report (run report)
The summary of one run of the engine, in the database table report; shown in All runs → Report (per run).
rereceive, resend
Doing a file again. Rereceive processes a received file again from the start (after you fixed a grammar or mapping); resend sends an outgoing file again. You mark the files in the web interface and start Run → Run user-indicated rereceives or resends.
route
The instruction for the engine: which incoming channel to read, what kind of files these are, whether to translate them, and which outgoing channel to use. A route can have several parts with the same name and a different Sequence. See Routes.
route script
A Python file in usersys/routescripts with the same name as a route. Its functions run at fixed points of the route, or replace the route. See Route scripts.
settings.py
The second configuration file of an environment, in the config folder: the database of Bots, mail settings for error reports, time zone, language, sessions. See settings.py.
status, statust
Two values of each step of a file in the database: status is the step reached (Received, Infile, Parsed, Document-in, Document-out, Merged, Outfile, Send), statust the result (Open, Error, Stuck, Done, Resend, No retry). See Statuses.
syntax
The settings in a grammar (separators, character set, envelope, version, merge and many more), in the dict syntax. A partner can have its own syntax in usersys/partners/<editype>/. See Grammar syntax.
ta
The main table in the database of Bots: one row (with an idta) for each step of each file and message, linked from parent to child. See What Bots writes in its database.
testindicator
A mark in the envelope that says whether an interchange is a test or real: in X12 ISA15 (T or P), in EDIFACT UNB field 0035 (1 for test). Bots reads it from incoming files; a mapping can set it for outgoing files; a route can send only files with a given test indicator.
Tradacoms
An older UK retail EDI standard. An editype in Bots. See Other editypes.
translation (translation rule)
A row in Configuration → Translations that says: a message of this editype and messagetype (and optionally this alt and these partners) is translated with this mapping script into that editype and messagetype. See Translations.
UNB / UNH
The two levels of an EDIFACT file. UNB ... UNZ is the interchange envelope (sender, receiver, control reference, test indicator). UNH ... UNT is one message, for example ORDERS. An optional UNA segment in front gives the separators.
usersys
The folder of an environment with everything you write yourself: grammars, mappings, partners, routescripts, communicationscripts, envelopescripts, charsets. It is a Python package, so every folder in it needs a file __init__.py. See Environments.
web interface (bots-monitor)
The screens of Bots in a browser, served by bots-webserver. The Bots 3 documentation calls it bots-monitor. See Web interface.
X12
The EDI standard of ASC X12, mostly used in North America. Messages have numbers (850 order, 810 invoice, 856 ship notice, 997 acknowledgement); segments usually end with ~ and fields are separated by *. See X12.
xml, json
Structured text formats used by many ERP systems and web services. Editypes in Bots; the nocheck variants (xmlnocheck, jsonnocheck) do not check the content against a grammar. See xml and json.

How to run Bots in the background

In production, the web server should run all the time and the engine should run on a schedule, also when nobody is logged in. Windows Task Scheduler can do both. More choices (job queue, directory monitor) are in Scheduling.

  1. Choose an account for Bots: a local or domain account that may read and write the environment folder (C:\edi\bots\production) and the folders of your file channels.
  2. Make the web server task. In a Command Prompt run as administrator: 
    schtasks /Create /TN "Bots webserver production" /SC ONSTART /RU MYCOMPANY\bots /RP * ^
  /TR "C:\bots4\Scripts\bots-webserver.exe -cC:\edi\bots\production\config"
    /RP * asks for the password of the account. Replace MYCOMPANY\bots by your account.
  3. Allow it to run long. Open Task Scheduler, open the task, tab Settings, and clear Stop the task if it runs longer than. By default Windows stops a task after 3 days.
  4. Make the engine task, here every 5 minutes: 
    schtasks /Create /TN "Bots engine production" /SC MINUTE /MO 5 /RU MYCOMPANY\bots /RP * ^
  /TR "C:\bots4\Scripts\bots-engine.exe -cC:\edi\bots\production\config"
    If a run is still busy when the next one starts, the second engine ends with exit code 3 and does nothing.
  5. Start the web server task now: schtasks /Run /TN "Bots webserver production", and open http://localhost:8080.
Note

Instead of Task Scheduler you can use a service wrapper: a tool that runs any program as a Windows service. Give it the program C:\bots4\Scripts\bots-webserver.exe, the argument -cC:\edi\bots\production\config, the account of step 1, and let it restart the program when it stops. Bots itself does not install a Windows service.

Watch out

A path with spaces must be quoted including the option: "-cC:\EDI Data\bots\production\config". Or set the system environment variable BOTS_CONFIG_DIR to the config folder and leave out -c.

How to uninstall

  1. Stop the web server, job queue and directory monitor, and delete or disable their tasks: schtasks /Delete /TN "Bots webserver production", and the same for the engine task.
  2. Remove the program: C:\bots4\Scripts\pip uninstall bots-ediint, or delete the whole folder C:\bots4 (this also removes all libraries of the virtual environment).
  3. Keep or remove your environments. Uninstalling does not touch config, botssys and usersys. These hold your configuration, database, files and scripts. Make a backup first, then delete the environment folders only if you no longer need them.

Environments

An environment is one complete Bots setup with its own configuration, scripts, database and files. This page explains the three folders of an environment, how each Bots command finds the environment to use, and how to run several environments, such as test and production, on one machine.

In plain words

The program Bots is installed once. Your work lives in separate folders: one for settings, one for your grammars and mappings, one for data. Each set of folders is an environment. You tell every Bots command which set to use.

How it works

The three folders

An environment directory holds three folders. Bots makes all three when it makes a new environment.

FolderWhat is in itMade from
configbots.ini (the settings of Bots), settings.py (database, mail, time zone, web sessions), and an empty __init__.py.copies of the files in bots/install of the program; a new random SECRET_KEY is written into settings.py, and bots.ini gets the full paths of botssys and usersys.
usersysWhat you write: grammars/<editype>, mappings/<editype>, partners/<editype>, envelopescripts/<editype>, routescripts, communicationscripts, charsets. How a command finds its environment

Every command of Bots (bots-webserver, bots-engine, bots-jobqueueserver, bots-dirmonitor, bots-updatedb …) looks for the config folder in this order:

  1. The option -c on the command line, written without a space: -c/srv/bots/env/production/config or -cC:\edi\bots\production\config. A relative path is taken from the current folder.
  2. The environment variable BOTS_CONFIG_DIR, if there is no -c.
  3. The default environment ~/.bots/env/<name>/config (on Windows %USERPROFILE%\.bots\env\<name>\config), where <name> is the value of the environment variable BOTSENV, or default. If this folder does not exist, Bots makes the whole environment there without asking.

The environment directory is the folder above config. Bots then reads bots.ini and finds the other two folders with [directories]:

  • usersys: a full path is used as it is. A relative path (such as usersys, as in a bots.ini of Bots 3) means the folder of that name in the environment directory, if it has an __init__.py.
  • botssys: a full path is used as it is; a relative path is taken from the environment directory.

Relative paths elsewhere, for example the Path of a file channel (botssys/infile/orders), are also taken from the environment directory: the engine changes to that folder when it starts. changed in 4.0 In Bots 3 they were relative to the folder of the program.

Watch out

A command started without -c and without BOTS_CONFIG_DIR silently uses (or makes) the default environment of the user who runs it. A scheduled task that runs as another user then works on another environment than you expect. In production, always give -c or set BOTS_CONFIG_DIR.

First start

How to start the web server, log in for the first time, make users for your colleagues, and change a password. Do this right after the installation.

In plain words

You start a small web server that belongs to Bots and open it in your browser. A new Bots comes with one administrator account. You log in with it, give it a new password, and make an account for each person who works with Bots.

How it works

  1. The web server. bots-webserver reads the environment, copies the files of the web interface to botssys/static, and serves the web interface on all network interfaces of the machine at the port of [webserver] port (default 8080). It runs until you stop it.
  2. The first user. The empty database that every new environment gets has one user: bots, a superuser (allowed everything). Its password is botsbots, as documented for Bots since version 3.
  3. Other users. Users are kept in the database of the environment, so each environment has its own users. A superuser makes them in the web interface. Without the web interface, bots-updatedb --createsuperuser makes a new superuser from the command line.
  4. Rights. What a user sees depends on his rights: a superuser sees all menus; other users see only the menus their rights allow. See Users and rights.
Stop

The password botsbots is known to everybody who has read the documentation of Bots, and the web server can be reached from the network. Change it at the first login, before you put anything in Bots.

How to start the web server and log in

  1. Start the web server with the config folder of your environment: 
    bots-webserver -c/srv/bots/env/production/config
    Expected output: 
    2026.10.15 09:00:01 STARTINFO [bots.webserver] Starting ...
2026.10.15 09:00:03 STARTINFO [bots.webserver] configdir: "/srv/bots/env/production/config".
2026.10.15 09:00:03 STARTINFO [bots.webserver] using plain http (no ssl).
2026.10.15 09:00:03 STARTINFO [bots.webserver] Serving at port: "8080".
    Leave this window open. Ctrl+C stops the web server.
  2. Open http://localhost:8080 in a browser on the same machine (or http://<server name>:8080 from another machine). You see the Bots page with Log in in the menu bar.
  3. Log in with user name bots and password botsbots. Bots opens the home screen.
  4. Change the password at once: menu Home (the house icon on the left) → Change password. Type the old password, then the new one twice, and click Change my password. You see a page that confirms the change.

The home screen

The home screen (/bots/home) shows the title Bots Open Source EDI Translator (or the [webserver] about_title you set), links to documentation and support, and a table with:

  • Current user and Last login;
  • Webserver port, Platform, Machine, Python version, Django version, Bots version;
  • Bots installation path (the program), Botsenv path, Config path, Botssys path, Usersys path;
  • the database: Database, Database_engine, Database_name and, for a database server, user, host, port and options.

Use it to check that you work in the environment you expect. The menu bar has icons; hold the mouse over an icon to see its name: Home, Incoming, Outgoing, All runs, Configuration, SysTasks (superusers only) and Run. On the right is a switch for the light or dark theme. Every screen is described in Web interface.

How to make a user

  1. Open SysTasks → Users → Add.
  2. Type the Username, for example operator, and the password twice. Click Save.
  3. Fill in on the next screen, under Permissions:
    • Active: ticked, or the user cannot log in.
    • Staff status: ticked if the user must see the Configuration menu (routes, channels, partners …).
    • Superuser status: only for administrators. A superuser has every right and sees SysTasks.
    • Groups and User permissions: the rights of a user who is not a superuser. For example, an operator who may look at results and start runs needs Can view report, Can view filereport, Can view ta and Can change mutex (the right to run the engine) of the application Bots EDI Translator.
  4. Click Save. Log in as the new user in another browser (or a private window) to check what he sees.
Tip

Give rights to groups (SysTasks → UserGroups → Add), for example a group operators and a group viewers, and put users in a group. Users and rights lists every right.

How to make an administrator from the command line

Use this when nobody can log in any more, for example when the password of the only superuser is lost.

  1. Stop scheduled engine runs for a moment: the command refuses to work while an engine runs.
  2. Run: 
    bots-updatedb -c/srv/bots/env/production/config --createsuperuser
    It first checks the database (The database is up to date.), then asks for Username, Email address and the password twice.
  3. Log in with the new user, and set a new password for the old user in SysTasks → Users.

Tutorial: your first route

In this tutorial you make Bots pick up files from one folder and put them, unchanged, in another folder. It takes about 15 minutes and teaches you channels, routes, a run of the engine and the result screens. You need an installed Bots and a user who may change the configuration (for example bots).

In plain words

You tell Bots: "look in this folder; whatever .csv file you find, move it to that folder". Then you put a file in the first folder, press Run, and see the file appear in the second folder and in the screens of Bots.

How it works

  1. An incoming channel of type file reads every file that matches *.csv in botssys/infile/orders, and removes it there after reading.
  2. A route takes these files and, with Translate set to Pass-through, sends them on without reading their content.
  3. An outgoing channel of type file writes each file to botssys/outfile/orders with a new name: order_ plus a counter.

Relative paths in channels are taken from the environment directory, so botssys/infile/orders is the folder infile/orders in the botssys of your environment.

How to make the two channels

  1. Open Configuration (the gear icon) → Channels → In → Add incoming channel.
  2. Fill in:
    • Idchannel: local_orders_in
    • In/out: in (already set); Type: file
    • Remove: ticked. Without it, the file stays in the folder and is read again at every run.
    • Path: botssys/infile/orders
    • Filename: *.csv
    Click Save. The channel appears in the list.
  3. Open Configuration → Channels → Out → Add outgoing channel.
  4. Fill in:
    • Idchannel: local_orders_out; Type: file
    • Path: botssys/outfile/orders
    • Filename: order_*.csv. Bots replaces the * with a counter of this channel: order_1.csv, order_2.csv …
    Click Save.

How to make the route

  1. Open Configuration → Routes → Add.
  2. Fill in:
    • Active: ticked
    • Idroute: orders_in; Sequence: 1
    • Incoming channel: local_orders_in (file)
    • Fromeditype and Frommessagetype: leave empty. A pass-through route does not need them.
    • Translate: Pass-through
    • Outgoing channel: local_orders_out (file)
    Click Save.

How to test it

  1. Make the folder botssys/infile/orders in your environment directory (the Botssys path on the home screen shows where botssys is), and put a file in it, for example test_order.csv with any text: 
    HDR,PARTNERA,PO1001,20261015
LIN,1,ITEM-100,10,EA,4.50
  2. Run the engine: in the web interface, Run → Run (only new). You see the message Bots-engine is started. and the list of runs. Or on the command line: 
    bots-engine -c/srv/bots/env/production/config
    The end of the output is: 
    ... START     [bots.engine] Running route: orders_in 1
... START     [bots.engine] Start communication channel in: local_orders_in (file)
... DONE      [bots.engine] Finished communication channel in: local_orders_in (file)
... START     [bots.engine] Start communication channel out: local_orders_out (file)

... DONE      [bots.engine] Finished route: orders_in 1
... INFO      [bots.engine] Bots Report; type: new, time: ..., duration: ...
    1 files received/processed in run.
    1 files without errors,
    1 files send in run.
  3. Check the folders. botssys/infile/orders is empty; botssys/outfile/orders has order_1.csv with the same content.
  4. Check the web interface.
    • All runs → Report (per run): the last run, type new, with 1 received and 1 sent.
    • Incoming: one line for test_order.csv, route orders_in, channel local_orders_in, status Done.

Tutorial: your first translation

In this tutorial you translate purchase orders from your ERP, as a csv file, into X12 850 orders for PartnerB. You write three grammars and one mapping, add two partners, two channels, a translation and a route, and run it. It takes about an hour. Do Tutorial: your first route first.

In plain words

Bots needs to know what the ERP file looks like (the incoming grammar), what an X12 order looks like (the outgoing grammar and its envelope), and which value goes where (the mapping). Then a route tells Bots to take the ERP files, translate them, and put the result where PartnerB picks it up.

How it works

  1. The incoming channel erp_orders_in reads the csv files the ERP writes to botssys/infile/erp_orders.
  2. The route orders_out says these files are editype csv, messagetype orders_erp. Bots reads them with the grammar usersys/grammars/csv/orders_erp.py. The grammar says that every HDR record starts a new order, so one file can hold many orders.
  3. For each order Bots looks up the translation rule for csv / orders_erp. It names the mapping orders_erp_to_x12 and the result: editype x12, messagetype 850004010.
  4. The mapping usersys/mappings/csv/orders_erp_to_x12.py builds the 850: ST, BEG, DTM, PO1 per line, CTT, SE. It also sets the sender (MYCOMPANY) and receiver (PARTNERB).
  5. Bots writes the 850 with the grammar usersys/grammars/x12/850004010.py, merges the orders for the same receiver, and adds the ISA/GS envelope with the grammar usersys/grammars/x12/x12.py, with control numbers from its counters.
  6. The outgoing channel partnerb_x12_out writes the file to botssys/outfile/partnerb. In real life this would be an SFTP channel such as partnerb_sftp_out.
Note

The X12 grammars in this tutorial are cut down to the segments the example uses, so that you can read them in full. For real partners, use complete grammars, for example from the plugins on the Bots website, and the implementation guide of your partner. See X12.

  1. Look at the ERP file. This is what the ERP writes: a header line HDR per order (partner, order number, order date, wanted delivery date), and a line LIN per order line (line number, item, quantity, unit, price). Dates are YYYYMMDD. The second order has no delivery date. 
    HDR,PARTNERB,PO1001,20261015,20261022

    def main(inn, out):
    # Sender and receiver: Bots uses these for the ISA and GS envelope.
    out.ta_info['frompartner'] = 'MYCOMPANY'
    out.ta_info['topartner'] = inn.get({'BOTSID': 'HDR', 'PARTNER': None})

    # The order number: shown in the web interface as the document reference.
    po_number = inn.get({'BOTSID': 'HDR', 'PO_NUMBER': None})
    out.ta_info['botskey'] = po_number

    # ST: start of the message. ST02 is the control number of this message.
    st02 = out.ta_info['reference'].zfill(4)
    out.put({'BOTSID': 'ST', 'ST01': '850', 'ST02': st02})

    # BEG: 00 = original order, SA = stand-alone order.
    out.put({'BOTSID': 'ST'},
            {'BOTSID': 'BEG',
             'BEG01': '00',
             'BEG02': 'SA',
             'BEG03': po_number,
             'BEG05': inn.get({'BOTSID': 'HDR', 'PO_DATE': None})})

    # DTM 002: requested delivery date, only when the ERP gives one.
    delivery = inn.get({'BOTSID': 'HDR', 'DELIVERY_DATE': None})
    if delivery:
        out.put({'BOTSID': 'ST'}, {'BOTSID': 'DTM', 'DTM01': '002', 'DTM02': delivery})

    # PO1: one segment per order line.
    for lin in inn.getloop({'BOTSID': 'HDR'}, {'BOTSID': 'LIN'}):
        po1 = out.putloop({'BOTSID': 'ST'}, {'BOTSID': 'PO1'})
        po1.put({'BOTSID': 'PO1',
                 'PO101': lin.get({'BOTSID': 'LIN', 'LINE_NUMBER': None}),
                 'PO102': lin.get({'BOTSID': 'LIN', 'QUANTITY': None}),
                 'PO103': lin.get({'BOTSID': 'LIN', 'UNIT': None}),
                 'PO104': lin.get({'BOTSID': 'LIN', 'PRICE': None}),
                 'PO106': 'VN',
                 'PO107': lin.get({'BOTSID': 'LIN', 'ITEM': None})})

    # CTT: the number of order lines.
    out.put({'BOTSID': 'ST'},
            {'BOTSID': 'CTT', 'CTT01': out.getcountoccurrences({'BOTSID': 'ST'}, {'BOTSID': 'PO1'})})

    # SE: number of segments from ST to SE (SE included), and the same control number as ST02.
    out.put({'BOTSID': 'ST'}, {'BOTSID': 'SE', 'SE01': out.getcount() + 1, 'SE02': st02})
    • inn.get(...) reads one value: the path goes from the top record down, and the field you want has the value None. It gives None if the field is empty.
    • out.put(...) writes values; a record is made when it does not exist yet.
    • inn.getloop(...) goes through every LIN; out.putloop(...) makes a new PO1 each time.
    • out.ta_info['reference'] is a message number from a counter of Bots. out.getcount() counts the segments written so far.
    • PO106 VN says PO107 is the vendor's item number.
    All functions are in Mapping functions.

Upgrade from Bots 3

How to move a Bots 3 installation (Python 2) to Bots 4.0.0 (Python 3): the tools that do most of the work, what you do by hand, how to test before the switch, and what is different for the users. Everything works on copies: Bots 3 is only read and can keep running until the day you switch.

In plain words

One command copies your old setup into a new folder for Bots 4: it converts your scripts to Python 3, copies and upgrades the database, and carries your settings over. It then tells you which lines of your scripts to look at. You fix those, test with copies of real files, and then switch the schedules from the old Bots to the new one.

How it works

One environment of Bots 3 (its config, usersys and botssys, usually inside the folder of the Bots 3 program) becomes one environment of Bots 4. The tool bots-portenv does five steps; each step is also a tool of its own:

  1. Make the new environment (config, botssys, usersys). The target folder must not exist, or be empty.
  2. usersys is copied and converted to Python 3 (bots-portusersys): print, except X, e, has_key, xrange, unicode, imports of a file in the same folder, and so on. The conversion does not change what a script means. Lines that are valid Python 3 but may behave differently are listed in port-review.txt in the new environment directory. A file that is not UTF-8 and has no coding line is written as UTF-8.
  3. The SQLite database of Bots 3 is copied into botssys/sqlitedb/botsdb and the copy is upgraded (bots-updatedb). Routes, channels, partners, translations, confirm rules, code lists, users, counters and the history are all there.
  4. The configuration is carried over (bots-portconfig): every option of the old bots.ini that Bots 4 knows gets its value in the new bots.ini; from the old settings.py the mail settings for error reports, managers, time zone, language, session settings and secret key are added to the end of the new settings.py.
  5. The new usersys is checked (bots-checkusersys): every Python file is compiled, every grammar is read with the checks of a translation, every script is imported. The result is on screen and in port-check.json.

The files that Bots 3 received and sent (botssys/data) are not copied; the history in the database is. Exit code of bots-portenv: 0 all done, nothing to look at; 1 done, with things to look at; 2 not done.

How to prepare

  1. Install Bots 4.0.0 in its own virtual environment with the extra bots3 (see Windows or Linux); add mysql or postgresql if Bots 3 used such a database or your scripts import MySQLdb: 
    python3 -m venv /opt/bots4
/opt/bots4/bin/pip install "/tmp/bots_ediint-4.0.0-py3-none-any.whl[bots3]"
    Do not install it in the Python 2 of Bots 3.
  2. Find the Bots 3 folders. Usually the folder of the Bots 3 program, for example /opt/bots3/bots or C:\Python27\Lib\site-packages\bots, with config, usersys and botssys in it. A second environment next to it has config2, usersys2, botssys2.
  3. Stop Bots 3 for a moment, or make sure no engine runs, while the database is copied. Or work from a backup copy of the Bots 3 folders.

How to make the new environment

  1. Run bots-portenv with the folder of Bots 3 and a new folder for the environment: 
    bots-portenv --bots3=/opt/bots3/bots /srv/bots/env/production

How to test before the switch

  1. Make the channels safe before the first run, so that the copy does not fetch from or send to partners. The easiest way is a test environment made with --local-folders: 
    bots-portenv --bots3=/opt/bots3/bots --local-folders /srv/bots/env/test
    Every folder of a file channel is made inside the new environment (<env>/channels/<path as it was>; /home/edi/in becomes <env>/channels/home/edi/in); every other channel (FTP, SFTP, mail, database) gets a test folder <env>/channels/test/<in or out>/<channel>; and bots.ini gets channels_use_testpath = True. A channel without a test folder is not run at all.
  2. Start the web interface of the copy (bots-webserver -c<env>/config), log in with your Bots 3 user, and look at routes, channels and the history.
  3. Put files that were received earlier in the incoming folders, run bots-engine -c<env>/config, and compare the results with what Bots 3 made.
  4. If possible, let the new environment get a copy of the live input for some days and write to folders.
  5. Before going live, remove channels_use_testpath from bots.ini and set the real folders.
Watch out

Do not rely on the acceptance-test mode (runacceptancetest) alone: it only replaces a channel that has an Acceptance test path. A channel without one connects to the partner. Use --local-folders, or give every channel of the copy a test path or a local folder before the first run.

How to switch, per environment

  1. Stop the scheduler entries, job queue and directory monitor of Bots 3. Wait until a running engine ends.
  2. Back up the Bots 3 database and usersys.
  3. Run bots-portenv again into a fresh folder, so that the database is current, and do again what you did by hand: the fixes in the mappings (or have them in Bots 3 already) and the folders of the file channels.
  4. Copy botssys/data of Bots 3 to botssys/data of the new environment if you want to view, resend or rereceive old files. The layout is the same.
  5. Start the new web server, job queue and directory monitor, and point the scheduler at the new bots-engine.
  6. Check the first run: the control number of the first interchange per partner, and the report.
Note

To go back: stop the new Bots and start the old scheduler entries; nothing in Bots 3 was changed. Files that Bots 4 received and sent in between are not in the history of Bots 3, and its counters did not move: set the counters of Bots 3 (table uniek) to the values of the new environment before its first run, or a partner gets a control number twice.

How to upgrade when Bots 3 used MySQL or PostgreSQL

  1. Run bots-portenv with --no-database. The new environment gets an empty SQLite database.
  2. Make a copy of the Bots 3 database on the database server.
  3. Set DATABASES in the new settings.py to that copy (see Databases).
  4. Check what will be done: bots-updatedb -c<env>/config --check shows This database is: made by bots 3. and the changes.
  5. Upgrade the copy: bots-updatedb -c<env>/config --yes-i-have-a-backup. It ends with The database is up to date.
